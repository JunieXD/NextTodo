# App 更新

各个 App 都从自己登录的服务器拿更新，不经应用商店，所以 App 的版本总是跟着服务端走。更新文件打包在服务端镜像里，放在网页静态文件的 `/app/` 下，服务端不加接口；文件里的下载地址都是相对路径，同一个镜像部署在哪个域名下都能用。

| | 网页部分 | 原生部分 |
|---|---|---|
| Android | 热更新：只下载变了的文件，下次打开 App 生效，新版本打不开就退回 | 下载新 APK，由系统弹出安装确认 |
| 桌面 | 网页打包在 App 里，随整包更新 | Tauri 官方更新插件：后台下载整个新版本、校验签名，重启生效 |
| iOS | 网页打包在 App 里，随整包更新 | App 不能自己安装：提示有新版本，在 SideStore 里更新 |

- 平时的改动几乎都在网页部分，连服务器的 Android 只在原生部分（`apps/android`、Capacitor 配置和插件）改了时才要装新 APK；本机模式的网页部分和服务端都在安装包里，每次发布都要装，见[本机模式](../local.md#更新)。桌面 App 每次发布都是整包，几 MB。
- 只从登录的服务器下载（[直接用 HTTP](../design.md#直接用-http) 时经 HTTP），和网页端一样信任这台服务器。APK 由系统校验签名，必须和已装的一致；桌面更新包用单独的更新密钥签名，App 里带着公钥校验。
- 每次构建除了服务端，还构建 Android 正式包和桌面更新包，连同版本说明一起放进镜像的 `/app/`。细节见 [Android](../android.md#更新) 和[桌面 App](../desktop.md#更新)。
- 本机模式没有服务器，从 GitHub Releases 取更新，见[本机模式](../local.md#更新)。iOS 总是从 GitHub 取：服务器上没有 iOS 的安装包，见 [iOS](../ios.md#更新)。
- **App 比服务器新**：iOS 从 GitHub 更新，各端的安装包也可能是从官网直接下载的，所以 App 可能比登录的服务器新。新版本发出的改动，旧服务器可能不认，保存失败。所以不是管理员的用户，在连服务器的 App 上（网页就是服务器给的，不会比它新；本机模式没有这回事）也读服务器的版本：打开时和之后每天最多一次，进设置“关于”时不论多久前查过都再查一次，但不问 GitHub；网页部分（Android 是热更新后的）比它新时，用提示条说一次“服务器的版本比 App 旧，部分改动可能无法保存，请联系管理员升级服务器”，同一台服务器的同一个版本只说一次；设置“关于”里多一行“服务器版本”，下面写“比 App 旧，请联系管理员升级服务器”。管理员不另说：他们已经会收到“服务器可升级”的提醒。
- 设置页“关于”只显示一个版本号：正在用的这一份的版本，写法和服务器、Release 一样，是 `0.1.<提交数>`。浏览器里叫“网页版本”，App 里叫“App 版本”。Android 的网页部分单独热更新，常常比安装包新，两者不同时“App 版本”下面另写一行“安装包 0.1.<提交数>”；桌面 App、iOS App 和本机模式的网页就在安装包里，版本总是相同，不另列。
- 自动检查失败时不打扰，下次照常再查。设置页“关于”里点按“App 版本”一行，立即检查一次，不受检查间隔限制；这一行下面显示检查的结果：正在检查、已是最新版本（附上次检查的时间）、新版本已下载（Android 的网页部分，下次打开时生效），或者失败的原因：
  - 连不上服务器或 GitHub：“无法连接服务器（或 GitHub），请检查网络后重试”；
  - 服务器上暂时没有可用的更新文件，或下载期间换了版本：“暂时无法获取新版本，请稍后重试”；
  - 新版本下载了却装不上：“新版本无法安装，请从官网下载最新版本”。
  原生部分只报这三类之一（桌面的 `Failure`，Android 插件拒绝时的 `code`），具体的错误记进日志。

## 更新日志

更新以后第一次打开时，弹窗告诉用户这次更新了什么：从这台设备上次用的版本到现在，中间每个发布的版本都列出来。

- 内容写在仓库根目录的 `CHANGELOG.md`：每个发布的版本一节，标题是版本号和日期（`## 0.1.212 · 2026-11-15`），新的在前；下面分新功能、改进、修复（`###`），每条都在其中一组下面，是一句纯文字（不用 Markdown）的短话，写用户看得到的变化，只说变了什么，不展开用法和细节，不写内部的重构，也不写下载和升级服务器的方法。写法简洁、正式、不口语化，用户一眼看得懂：直接说变化，不写套话；新功能写“新增……”“支持……”，修复写“修复……的问题”。发布前写好这一节、提交，再构建：网页端把整个文件打包进去，`deploy/release.sh` 取最上面一节作为 GitHub Release 的说明，它的版本号不是这次要发布的版本时不发布。
- 弹窗做在网页端，网页、Android、iOS、桌面 App 和本机模式都一样。网页部分的版本比这台设备记下的新时，主界面出来后弹一次，列出两者之间（不含记下的，含现在的）每个版本的内容；这之间没有发布过的版本（比如自己部署的两次发布之间的提交）就不弹。用户关掉弹窗时，或者不用弹时，记下现在的版本；记下的只往新里改，退回旧版本（如 Android 的网页部分新版本打不开时）不改。
- 没有记录时，这次打开前在这台设备上登录过的，是从不记版本的 0.1.201 或更早的版本升级上来的，当作记下的是 0.1.201；没登录过的是第一次打开，不弹，只记下。开发版（版本是 `package.json` 的 0.1.0）不弹也不记。从外面打开（小组件的快速添加，点提醒、小组件或菜单栏小窗里的事项）时这次不弹，下次回到 App 时再弹，不等 App 下次启动（Android 上 App 常常一直在后台）；弹窗开着时从外面打开，它让开，同样下次回到 App 时再弹。
- 记录存在设备上，不经服务器：每台设备各弹一次。
- 弹窗标题“已更新到 0.1.212”，下面一行次要文字“自 0.1.201 以来的更新”，跨了几个版本时接着写“· 3 个版本”。各版本的内容合在一起，按新功能、改进、修复分组，组名后面写条数，组内新的版本在前；跨了几个版本时，每条后面用次要文字标出它是哪个版本的。最多列 10 个版本，多于 10 个时第一行写“· 12 个版本，列出最新 10 个”，最后是“还有 2 个更早的版本”，点了在原处接着列出。底部固定一个“知道了”，不随内容滚动。
- 设置“关于”里有“更新日志”一行，弹出全部版本的内容，新的在前，每个版本一节，节标题是版本号和日期，节内同样按新功能、改进、修复分组。
- 这两个弹窗在电脑上比别的弹窗宽，随窗口在 440 到 640 之间变化。
