# Android

Android App（包括小米澎湃 OS）：Capacitor 外壳加载打包在安装包里的网页端，加上截止提醒和桌面小组件。总体要求见[总体设计](design.md#android包括小米澎湃-os)，网页端见[网页端](web.md)。

## 结构

| 位置 | 内容 |
|---|---|
| `apps/web/capacitor.config.ts` | Capacitor 配置。网页端的代码和依赖只有一份，App 用的插件也装在 `apps/web` |
| `apps/android` | 原生工程（Capacitor 的 `android.path` 指到这里）：外壳、小组件（Kotlin + Jetpack Glance）、提醒和提醒卡片（Jetpack Compose + Material 3）、给网页调用的小插件 |
| `crates/android` | 本机模式的服务端，编译成动态库打进 APK，见[本机模式](local.md#android) |

网页端用 `Capacitor.isNativePlatform()` 区分自己是在浏览器里还是在 App 里，只有连接服务器的方式和下面几项 App 专有的功能不同，界面完全一样。

页面跑在系统的 WebView 里。没有谷歌服务的华为手机用华为自己的 WebView，内核较旧，网页端因此支持到 Chromium 99，见[网页端](web.md#浏览器)。

页面铺满全屏，状态栏和底部导航栏盖在页面上，安全区由 Capacitor 的 SystemBars 写进 CSS 变量；这要 WebView 140 起，页面也声明了 `viewport-fit=cover`。系统栏是透明的：Android 15 起系统强制如此，之前的版本由启动画面的主题（`Theme.SplashScreen`）设成透明。WebView 更旧时（不少国产手机的系统 WebView 还是旧的）它改为给窗口留出系统栏的位置，页面不铺到下面，留出的地方露出窗口的底色。所以网页每次换主题、主题色时，把页面的底色（`--surface`）和深浅交给原生：

- 窗口设成同样的底色，看起来仍是一整片，不会是一条灰带；
- 系统栏的图标按页面的深浅取浅色或深色，App 选的主题和系统的不同时也看得清；
- 转屏等配置变化时 SystemBars 会把这两样改回系统的，原生随即再设一次。

## 连接服务器

也可以不连服务器，在本机使用，见[本机模式](local.md)。

App 的页面来自 `https://localhost`，和服务器不同源，所以不用 Cookie：

- 登录页多一个“服务器地址”栏，第一次登录时填写，不写协议时按地址选 `http://` 或 `https://`，见[直接用 HTTP](design.md#直接用-http)。
- 登录得到的会话令牌和服务器地址存在 Capacitor Preferences（Android 的 SharedPreferences，App 私有）；小组件从同一处读取。App 不参加系统备份（`allowBackup="false"`），令牌不会进云端备份。
- HTTP 请求加 `Authorization: Bearer <令牌>`，经 Capacitor 的原生 HTTP 发出（`CapacitorHttp`），不受跨域限制，服务端不需要 CORS。Capacitor 不给 POST 等写请求转发 `AbortSignal`，所以网页端请求的 20 秒期限在 App 里只对 GET 有效，登录、注销等写请求要等系统的网络超时。
- WebSocket 在 `hello` 里带令牌（见 [API](api.md#同步协议)）。
- 设备名是“NextTodo App · Android”。
- 退出登录时先删令牌，再清小组件、取消所有提醒（包括通知栏里已经弹出的）、删本机数据；服务器地址保留，下次登录不用再填。下次启动发现没有令牌时，先清掉小组件和提醒；有没做完的退出（“正在退出”的记录）就接着删本机数据，否则是登录失效（比如小组件先收到 401 删了令牌），本机数据和待发改动留着，同一账号再登录时补发。退出记录写下后、令牌删掉前被杀掉的，下次启动补完退出时也删令牌、清小组件和提醒。
- 退出时连不上服务器的，令牌照样删掉，服务端的这次登录留着，可以在别的设备的设置里“已登录的设备”注销（网页端会在下次打开时补上注销，App 删了令牌就补不了）。
- 登录失效（服务端不再接受令牌）时，和网页端一样保留本机数据和待发改动，同一账号再登录时补发；令牌、小组件和提醒照样清掉。打开 App 时才发现的（本机没有数据，问服务端得到 401）也一样。
- 登录页改了服务器地址时，内存里之前登录留下的令牌作废，不会发给新的服务器。
- 服务端告诉小组件会话已失效（401）时，如果期间没有重新登录，小组件删掉令牌，显示“打开 NextTodo 登录”；已经重新登录的，旧会话的 401 什么也不改。
- 邀请链接用服务器地址（App 里页面的来源是 `https://localhost`）。
- Capacitor 的桥接日志关掉（`loggingBehavior: "none"`），否则调试版会把登录密码和令牌写进 logcat。
- 返回键（含侧滑返回）一次退一步：先关掉对话框、弹窗、详情，再退出文件夹，最后退到后台；底部栏的页面之间不来回，见[界面](ui.md#返回)。

## 截止提醒

网页算出提醒，交给原生排定、弹出，不依赖推送。不用 `@capacitor/local-notifications`：它给通知加的按钮点了一律打开 App，做不到不进 App 就完成。

- 会话开始时、本地副本变化后（第一次变化后 2 秒内处理一次，合并这期间的变化）、过了零点、到了开始时刻和 App 回到前台时，网页给有[提醒](design.md#提醒)的未完成事项算出每个提醒的时刻（同一事项同一时刻的只算一个），整份交给原生（`NextTodo` 插件），和桌面交给 Rust 一样。时间已经过了的也交：通知栏里已经弹出的通知还留不留、[稍后提醒](#稍后提醒)还算不算数，都按这份列表定。
- 每项带着事项 ID、提醒时刻、重复事项的这一次（`occurrence`，见 [API](api.md#改动)）、通知的标题和内容（[隐藏通知内容](design.md#提醒)时只写“有事项到期”），以及能不能直接完成：到提醒时刻还在等前置的不能（等的[重复事项](design.md#重复)到那时开始了新的一次，也算在等）；只是还没到[开始时间](design.md#开始时间)的带上开始时间，到点时由原生按手机上的时间判断。App 没在运行时别处的改动（比如在电脑上加了前置）要等 App 下次运行才算进来。
- 通知以事项 ID 为标签区分：编号是各自主人的，共享的文件夹里的事项可能和自己的同号。一个事项有几个提醒时，通知栏里只留最新到点的一条：后一个到点时换掉前一个，照样响铃、弹横幅。
- 一条提醒由事项 ID 和提醒时刻认出：稍后提醒、锁屏时到点等解锁再弹的、通知上的“完成”都只管这一条。在通知上完成时，这一次的其余提醒一起去掉，重复事项下一次的留着。
- 原生记着在这台手机上的通知、卡片和小组件上完成的每一次：事项、重复事项的这一次，和这个改动成了哪个改动序号（还没发出的没有）。交来的列表带着本地副本的改动序号；早于这次完成的（比如通知上的完成已经发出，App 离线打开时副本里还没有它），或者完成还没发出时，交来的提醒和汇总里去掉这一次的，免得它们回来。交来不早于它的列表以后就不再记着；改动被拒绝了的随即不记。较旧的服务器上的网页交接时不带序号，这时只去掉还没发出的，已经发出的不再记着：之后在别处重新打开的，不会一直没有提醒。
- 原生把列表存在 SharedPreferences，只设一个闹钟（`AlarmManager`），定在最近的提醒时刻，所以提醒不限个数。有“闹钟和提醒”权限（`SCHEDULE_EXACT_ALARM`）时是精确闹钟，没有时是普通闹钟，系统可能推迟几分钟。
- 原生记着处理到了哪个时刻。闹钟响时和每次交接时，弹出这个时刻之后、现在之前到点的提醒，再记下现在。交接时只弹上一份列表里就排着的：闹钟晚到或被系统扣住的照样弹，刚在 App 里设的、改过的，时间已经过了的不弹。开机后（`BOOT_COMPLETED`）按存着的列表重设闹钟，关机期间到点的一起弹出。
- 列表里没有了的，通知栏里已经弹出的通知也收回：事项完成、删除或改了提醒以后，旧通知不再留着。提醒时刻没变、已经是重复事项另一次的也收回：这一次完成或跳过了，下一次的提醒正好在同一时刻。提醒时刻没变、显示的跟现在不一样的（改了标题或截止时间、加了前置，或到了开始时间、该有“完成”了），已经弹出的通知在 App 下次交来列表时按现在的内容和按钮更新，不再响铃。
- 提醒排的是具体时刻。改了手机时区，要等 App 下次回到前台才按新时区重排。
- 第一次交来不为空的列表时请求通知权限（`POST_NOTIFICATIONS`）。没有精确闹钟权限时不弹系统设置；设置里提示并给出打开系统设置的按钮，允许后回到 App 时按精确闹钟重排。
- 更新提醒或小组件失败时，提示条告诉用户，下次变化时再试。
- 退出登录时清空列表、稍后提醒和通知栏里已经弹出的通知。
- [每日汇总](design.md#提醒)随同一次交接交来（`setReminders` 的 `digest`：隐藏通知内容开没开，和每天的时刻、列着的事项，每项带事项 ID、重复事项的这一次和标题），存在一起，由同一个闹钟排定，按同样的规则弹出：交接时只弹上一份里就排着的。交来的从前一天起：没有精确闹钟时，前一天很晚的汇总可能被系统推到零点以后才响。几天的一起到点（比如关机了几天）只弹最近的一天。标题和内容由原生按网页的写法生成：在通知、卡片或小组件上完成一项时，排着的汇总里去掉这一次的它，没有剩下的那天就不发。通知用自己的渠道“每日汇总”，重要性为高；标签固定，后一天的换掉前一天的；点开打开“接下来”，没有按钮，不上[提醒卡片](#弹窗提醒)。已经弹出的说的是到点那一刻，交接时不收回、不更新；只是打开了隐藏通知内容时，列着标题的收回。

### 通知

- 用自己的通知渠道“截止提醒”，重要性为高：到点在屏幕顶部弹出横幅，几秒后收进通知栏；锁屏上也显示。澎湃 OS 还要允许“悬浮通知”才有横幅，见[澎湃 OS](#澎湃-os)。原来插件建的渠道（`default`）和它存的提醒，升级后第一次启动时删掉。
- 铃声和振动用系统的：设置“提醒”里“通知”一组的“铃声和振动”，小字写“在系统设置中选择”，点“打开设置”直接打开系统里“截止提醒”这个渠道的设置。打开了[弹窗提醒](#弹窗提醒)的，提醒还会走“截止提醒（弹窗时）”，这时打开的是本 App 的通知设置，列着各个渠道，两个都能设；还没发过通知的渠道，系统可能收在“显示未使用的类别”里。没允许通知时渠道页里没有铃声和振动，也打开本 App 的通知设置，先在那里允许。App 里不另做一套铃声和振动的选择。
- 标题是事项标题，内容是截止时间和文件夹，重复的事项再加“已完成 12 次”。点通知进入 App 并打开这个事项（在设置页的先回到“接下来”；小组件里点事项也一样）。
- 两个按钮：
  - “完成”：不打开 App，通知随即收起，改动见[原生发出的改动](#原生发出的改动)。还在等前置或没到开始时间的没有这个按钮：点通知进 App，按 App 里的规则先确认。
  - “稍后提醒”：在屏幕底部弹出[提醒卡片](#弹窗提醒)，直接显示推迟多久的选项。这张卡片是透明背景的 Activity，由用户点按打开，不需要悬浮窗权限；它压在正在用的应用上面，背后变暗，点卡片外面或按返回键收起，不推迟。

### 稍后提醒

- 选项：15 分钟、30 分钟、1 小时、3 小时、自定义（5 到 55 分钟，每档 5 分钟；或 1 到 24 小时）。选好后通知栏里的这条收回，到时候同一条提醒再弹一次，内容和按钮都一样，还能再推迟。
- 只推迟这台手机上的这一次提醒：不改截止时间，不同步，别的设备不受影响。推迟记在原生的 SharedPreferences 里。
- 推迟期间交来的列表里还有这条提醒（同一时刻）的，推迟照旧；事项完成、删除或改了截止时间、提醒，推迟作废，按新的来。同一事项的下一个提醒到点时，推迟的这条也作废，弹出新的。

### 弹窗提醒

设置“提醒”里的开关，默认关。打开后，到点在屏幕底部弹出提醒卡片，不点就不收起，比横幅更不容易错过。

- 自己弹出卡片要“显示在其他应用上层”的权限（`SYSTEM_ALERT_WINDOW`，澎湃 OS 叫“悬浮窗”），只能在系统设置里给。打开开关时还没有，就打开本 App 的这一项系统设置，允许后回到 App 开关才打开；之后权限被收回的，这一行提示去允许，期间用横幅。开关存在原生的 SharedPreferences 里，App 经 `NextTodo` 插件读写。
- 到点时屏幕亮着、已解锁、没开勿扰，当场弹出。锁屏或熄屏时先发横幅，解锁时再把这期间到点的弹出来：通知还在（没在通知上处理或划掉），也没在别处完成、删除、改时间或推迟的。开着勿扰时只发横幅，之后也不补弹。解锁是系统的“用户解锁”广播，只有 App 进程在运行时才收得到，所以和提醒一样要允许自启动、省电策略设为“无限制”；收不到的（进程被结束过），等下一次到点或打开 App 时补弹。
- 当场弹卡片时通知照样进通知栏，关掉卡片后还能从那里处理；照常响铃、振动，但不弹顶部横幅，同一个提醒在屏幕上只出现一次。这样的通知发在另一个渠道“截止提醒（弹窗时）”，重要性为默认：有声音，没有横幅。解锁时补弹的，通知是锁屏时已经发过的横幅，不再发一次，也不再响。
- 卡片是悬浮窗（`TYPE_APPLICATION_OVERLAY`），不是 Activity：澎湃 OS 不许 App 从后台打开 Activity，有悬浮窗权限也不行，还要“后台弹出界面”；悬浮窗只要悬浮窗权限。
- 卡片浮在正在用的应用上面，不抢焦点：卡片外面照常能点、能滑，返回键也交给下面的应用，卡片要点 × 或按钮才收起。它也接收不了键盘输入，所以自定义推迟用加减按钮。卡片开着时，系统在通知栏里显示“NextTodo 正在其他应用上层显示内容”，卡片收起后消失。
- 内容：左边是事项的圆圈（等待中的是灰色），右边是标题（最多两行），下面一行是截止时间和文件夹，重复的事项加“已完成 12 次”，等待中的加“等 2 项”或“明天开始”。右上角 × 收起卡片。点标题这一块打开 App 里的这个事项，卡片收起。
- 按钮靠右：“稍后提醒”（色调按钮）和“完成”（实心按钮）。等待中的事项没有“完成”，换成“打开”，进 App 处理。
- 点“完成”：勾选框变成实心对勾、标题划线，停留 0.9 秒再收起，和 App 里一样；改动和通知上的“完成”相同。
- 点“稍后提醒”：卡片原地换成选项，圆圈换成返回。自定义是一个数字（加减按钮）和“分钟”“小时”两档，再点“确定”。从通知上的“稍后提醒”打开的卡片直接是这一页。
- 几个提醒同时到点：一次显示一项，右上写“还有 2 项”；完成或推迟一项后换下一项，× 收起全部。卡片开着时又到点的排在后面；同一事项的下一个提醒到点时，卡片上换成它，和通知栏一样。卡片上的提醒在通知、小组件或 App 里完成、删除、改了时间或推迟了的，随即从卡片上去掉，免得再点一次“完成”让重复的事项多顺延一次；事项别的地方变了的，卡片随之更新，比如加了前置，“完成”换成“打开”；App 到了开始时刻交来列表时（见[小组件](#小组件)的数据来源），到了开始时间的换回“完成”。从通知上的“稍后提醒”打开的卡片也一样。
- 颜色、字号和按钮同[界面](ui.md)里的弹窗，圆角 28；跟随系统的深浅色，和小组件一样（原生读不到 App 里选的主题）。

## 小组件

四个 Jetpack Glance 写的小组件：“接下来”列出现在能做的，“日程”列出今天起 7 天每天截止的，“一周”上面是 7 天的日子，下面是选中那天的，“时间轴”按钟点排一周。外观在设置里调，四个一样，见[小组件的设置](#小组件的设置)。

“接下来”和“日程”最小能缩到 1 格（桌面格子大的平板上也能放小）。窄了、矮了按实际尺寸去掉放不下的，列表照常能滚：

- 高度不到 110dp（大约 1 格高）时没有标题栏，不管[设置](#小组件的设置)里开没开；点不了刷新和 `+`，靠 App 交来的列表和自动刷新。
- 宽度不到 220dp（多数手机上 2 格宽及以下）时，标题后面不写关联进度，行右边不写截止时间（“日程”也不写“以后的一次”），标题占满；“接下来”的圆圈照常能点。
- 宽度不到 130dp（多数手机上 1 格宽）时，标题只剩几个字，认不出是哪一项：“接下来”不画圆圈，免得点错完成，每行只有标题，点了打开详情；也没有标题栏，放不下按钮。日期标题和“还有 N 项”都只占一行。
- “一周”“时间轴”要排 7 天，仍至少 4 格宽、3 格高。

小组件的背景都是 20dp 的圆角：一张圆角的图，着色成背景色，Android 11 及以下（如 MIUI 12）也是圆角。Android 12 起，里面的内容（如滚到边上的列表）还会沿圆角裁掉；之前的版本做不到，Glance 的 `cornerRadius` 在那里不起作用。

### 接下来

- 布局随尺寸变（Glance 的 `SizeMode.Exact`，按实际尺寸排；很小时见[上面](#小组件)）：高度不到 260dp（多数桌面上不到 3 格，包括默认的 4×2）时每项一行，标题在左、截止时间靠右，不显示文件夹，4×2 能放下约 4 项；更高时每项两行，第二行是文件夹和截止时间。有前置或后续的事项，标题后面跟着淡色的[关联进度](design.md#关联进度)“2/5”，标题太长时先省略标题。
- 最多列 20 项，后面还有的在末尾写“还有 N 项”，点了打开 App；列出的都在小组件或通知上完成了、新列表还没来时，只剩这一行。小组件的内容一次整个交给桌面，一项约 14KB，超过 1MB 桌面就不收、整个小组件显示不出来；4×4 的小组件一屏约 9 行，20 项够滚两屏。
- 截止时间逾期红色、今天琥珀色，规则同网页；[后续的截止](design.md#后续的截止)同 App：没设截止的写“后续 11月30日”，晚于后续的截止后面写琥珀色的“晚于后续”（两行时在第二行右端，和关联进度对齐）；左边的圆圈点一下完成，点这一行的其他地方打开 App 里的详情；点标题回到 App 的首页；右上角 `+` 弹出[快速添加小窗](#快速添加小窗)，刷新按钮立即刷新。
- 圆圈和打开详情的区域在结构上并列，不互相嵌套：打开详情的区域覆盖整行（连同上方的分隔线），在前；圆圈叠在它的左端，可点的范围从小组件左边缘到标题起点。澎湃 OS 的桌面和原生的不同：点在一个套着另一个可点元素的元素上，执行的是里面那个元素的动作；点在不属于任何可点元素的空隙上，执行的是这一行里第一个动作，行外的空隙也会被交给某个动作（曾经点最右侧边缘执行了 `+`）。所以两个动作不能嵌套，整个小组件也不留空隙：
  - 四周的边距放在各个可点区域里面：标题行占满顶部，“接下来”、刷新和 `+` 三块首尾相接，`+` 一直到右边缘；每一行从左边缘到右边缘。
  - 没有事项时，“暂无可做的事项”（未登录时是“打开 NextTodo 登录”）占满标题以下，点了打开 App。
  - 列表下面垫着一层，占满标题以下，点最后一项下面的空白打开 App；它和列表并列，不包着列表，免得点事项时被当成套着可点元素的元素。
- 事项之间有淡色分隔线，从文字起点开始（小组件画不出 App 里的半像素线，用 1dp、比 outline-variant 更淡的颜色）。
- 点圆圈后这一项立刻显示为完成（实心对勾、标题划线变灰），和 App 里一样在原位停留 0.9 秒（服务端确认得更慢就等到确认，连不上服务器时存下就算），然后从列表移走，再刷新列表；服务端拒绝时恢复原样并提示。Glance 无法做动画，用这个状态代替：正在完成的事项连同它在列表里的位置记在内存里，停留期间来了不含它的新列表，它也留在原位；App 进程被系统结束时，这个状态和正在进行的完成一起消失，不会留下一直显示完成的事项。
- 数据来源：
  - 小组件跟着这台手机上“接下来”的[文件夹筛选](ui.md#接下来的文件夹筛选)。App 每次本地副本变化后，把“接下来”的列表写给小组件（经 `Widget` 插件存入 SharedPreferences 并通知刷新），格式同 `next` 工具数据里的 `tasks`，带事项编号，一起写入的还有选中的文件夹的路径；小组件存下整个列表，只列前 20 项，列出的完成了、新列表还没来时，后面的补上来。列出的事项和登录状态都没变、画面上随时间变的标注（“今天”“明天”“逾期”等）也和上次重绘时一样，就不重绘（按下一个零点或截止时刻判断，时钟回拨、换了时区也判断得出；交来的列表比存下的旧、没有写入时，标注变了也重绘存下的列表）：Glance 在主线程上绘制，App 每次启动都交来列表，重绘会推迟 App 的第一帧。
  - 小组件自己每 15 分钟（WorkManager 周期任务，联网时）和点刷新按钮时，用令牌调用 `POST /tools/next` 取最新列表（`folders` 是 App 交来的路径，不筛选时不带；选中的文件夹在别处改了名或删了、回复说找不到时，保留现有的列表，等 App 交来新的路径；`limit` 用 20，后面还有几项按回复里的 `total` 算；`today`、`time` 是手机上的日期和时间，[开始时间](design.md#开始时间)按它们算）。App 开着时，到了下一个开始时刻（我的事项里还没到开始时间的、有后续没结束的[重复事项](design.md#重复)这一次还没开始的，最早一个）和过了零点，也重写一次列表，因为到了开始时间的事项要出现，又要等重复事项的要消失，[要赶的截止](design.md#后续的截止)也可能变；手机时间或时区往回调过了某个开始时间，也重写。App 交来列表时一并交来下一个开始时刻，小组件到时自己取一次列表，App 没在运行也会出现；小组件每次取列表，回复里的 `next_start` 又排好下一次，一个接一个的开始时间都赶得上，在别处新设的也一样。到时用闹钟叫醒，和[截止提醒](#截止提醒)一样：有精确闹钟权限时准时，没有时系统可能推迟几分钟；重启手机或更新 App 后闹钟没了，等下一次刷新再排上。开始时刻是手机上的钟第一次走到它的时候。
  - 每份列表都带着它对应的服务端改动序号（App 的是本地副本的 `seq`，服务端的是 `next` 回复里的 `seq`），和列表一起存下；比已存的旧的不写，一样新的照写。App 刚启动、或在后台被冻结后恢复时，本地副本可能还没跟上服务端，它的列表会比小组件自己取到的旧，按序号就不会把小组件改回旧内容。退出登录时写入的空列表不带序号，什么都能替换它，它也替换任何列表。换了筛选、App 交来的列表却比存着的旧时，也不写入，小组件联网后按新的筛选自己取一次。
  - 取回来时令牌已经换了（退出或换了账号）的也丢掉。小组件自己对列表的改动依次进行，检查令牌、序号和写入在一起，旧会话取回的列表不会写进新会话。
- 勾选完成经[原生发出的改动](#原生发出的改动)提交（`task.update`，`done: true`，带上手机上的当天日期 `today`；已经在别处完成的照样算成功），和通知、提醒卡片上的“完成”是同一套代码。成功后从原生的提醒列表里去掉完成的这一次提醒、收回已经弹出的通知（App 可能没在运行）；等服务端答复期间 App 已经交来的下一次提醒（重复的事项）留着。存下的列表早于这次完成时，把这一项连同完成的改动序号另外记下、不再显示（列表本身不改，仍是它那个序号时的样子；早于这次完成的列表写进来也照样隐藏它），直到存下的列表不早于这次完成，再刷新；还没发出的完成也一样不再显示这一项。重复事项记的是完成的那一次，只隐藏那一次：完成的是过时的一次（比如点了旧通知），或者后来交来的列表里已经是下一次（离线时 App 先按自己的副本往下排），照样列出。
- [重复](design.md#重复)的事项也这样完成：显示完成、移走，刷新后带着下一次的截止时间回到列表，和 App 里一样，顺延到明天以后的标着“今天已完成”。旧的提醒照样取消，下一次的提醒等 App 下次运行时排上（App 在后台连着同步时当场就排）。
- 没登录时显示“打开 NextTodo 登录”。

### 日程

[日历](design.md#日历)的今天起 7 天，放在桌面上：

- 按天分组，组标题是“今天”“明天”，再往后是“周日 11月22日”；没有事项的日子不列。最前面另有一组“已逾期”：截止日期在今天以前、还没完成的。每行左边是标题，右边是具体时间（只有日期的不写）；逾期的时间红色，同“接下来”小组件；[重复](design.md#重复)事项以后的每一次也列在那天，标题后面淡色写“以后的一次”。高度够时每项两行，第二行是文件夹，按 260dp 分，同“接下来”小组件。
- 只看不勾，没有圆圈：点一行打开 App 里的详情；点标题“日程”打开 App 的日历页（`nexttodo://calendar`）；右上角的刷新按钮立即刷新。勾选在 App 和“接下来”小组件里。
- 最多列 30 项，后面还有的在末尾写“还有 N 项”，点了打开日历页，理由同“接下来”小组件。都没有时写“这 7 天没有截止的事项”，点了打开日历页。
- 外观（见[小组件的设置](#小组件的设置)）、可点区域的排法（不嵌套、不留空隙）和分隔线同“接下来”小组件。
- 数据来源同“接下来”小组件：跟着这台手机上“接下来”的文件夹筛选；App 每次本地副本变化后写入（带改动序号，旧的不覆盖新的，换了筛选而交来的比存下的旧时立即自己取一次；格式同 [`agenda`](agent.md#工具) 工具的数据）；小组件自己每 15 分钟（联网时）和点刷新按钮时调用 `POST /tools/agenda`（`days` 是 7，`today`、`time` 是手机上的日期和时间，`folders` 同上）。几个小组件共用一个周期任务，“接下来”和日程各取各的；只放了“一周”时也取“接下来”的列表，为了其中的下一个开始时刻，见[一周](#一周)。
- 存下的列表按日期记：过了零点，过去那天的“以后的一次”不再列，那天还没完成的挪进“已逾期”；手机的时间或时区往回调过了零点的，“已逾期”里还没到期的挪回它那天；7 天里新到的那一天等下一次取列表时补上。是否重绘同“接下来”小组件，按下一个截止时刻或零点判断；到了那个时刻自己重绘一次，不用联网（定时器不唤醒手机，熄屏时等亮屏；没有精确闹钟权限时最多晚 10 分钟；放上小组件、重启手机、更新 App 时重新排上；改了时间或时区时立即按现在重绘，再排上）；点刷新时先按现在重绘一次，没联网也是。
- 在“接下来”“一周”小组件、通知和提醒卡片上完成的，存下的列表还早于这次完成时也不再列出（它以后的几次照列），和“接下来”小组件的做法一样，用同一套记录。
- 退出登录时清空，显示“打开 NextTodo 登录”。

### 一周

和 App [日历](ui.md#日历)的周视图一样按天看，放在桌面上，至少 4 格宽、3 格高：

- 标题行：“一周”（点了打开日历页）、刷新、`+`。
- 下面一排 7 天，默认从今天起，也可以在[设置](#小组件的设置)里改成本周的周一到周日；一天一列：上面一行是周几（“二”“三”），今天写“今”；下面是日期数字，在一块圆角方块里。今天的数字用主色；选中的那天方块是主色实心、数字反白。那天有截止的事项时，数字下面有小圆点，最多 3 个，有逾期的用 error 色，同日历；选中的那天圆点也反白（红色压在主色上看不清），逾期的看下面列表里的红色时间。点一天选中它，下面的列表换成那天的。
- 选中的那天开头一行写“今天”“明天”“周四 11月26日”，下面是那天的事项，行同“日程”小组件，左边多一个圆圈：
  - 现在这一次截止在那天、可做的：点圆圈完成，同“接下来”小组件（显示完成、停留、移走，经[原生发出的改动](#原生发出的改动)提交）。
  - 等前置或没到开始时间的：灰色虚线圆圈，同 App；圆圈不能点，点这一行打开 App 里的详情，在那里按 App 的规则先确认，同[弹窗提醒](#弹窗提醒)的“打开”。
  - 重复事项以后的一次：同样是灰色虚线圆圈，标题后面淡色写“以后的一次”，只写时间，同日历。
  - 选中今天时，最前面单独一组“已逾期”（组标题红色，同“日程”小组件），时间红色；下面才是“今天”一组，今天没有截止的就没有这一组。
  - 周一到周日时，今天以前的日子列那天截止、还没完成的，时间红色，圆圈同上；做完的不列，同“日程”小组件只列要做的，那天做了什么在 App 的日历里看。小圆点也只算没完成的，都是 error 色。选中今天时的“已逾期”照样列出全部，本周前几天的也在里面。
  - 点一行的其他地方打开 App 里的详情。那天没有事项时写“这天没有截止的事项”（今天以前的日子写“这天没有没完成的事项”），点了打开日历页。最多列 30 项，后面还有的写“还有 N 项”，同“日程”小组件。
- `+` 弹出[快速添加小窗](#快速添加小窗)，加到选中的那天，同日历里的快速添加：截止就是那天，带上只有日期的事项的默认提醒，没有 ✦。
- 哪些能勾随开始时间变（到了开始时间的能勾了，等的重复事项开始了新的一次又要等）：同“接下来”小组件，到了下一个开始时刻自己取一次列表，联网时（为此点刷新时也取“接下来”的列表，其中有下一个开始时刻）；没联网时按存下的画，等联网或 App 交来新的。
- 选中哪天记在每个小组件自己的状态里（Glance 的 `GlanceStateDefinition`），点了立即重绘；过了零点、选中的那天不在这 7 天里了，回到今天。
- 数据、刷新、文字大小、可点区域的排法（不嵌套、不留空隙）同“日程”小组件，和它共用存下的列表：存的是今天起 7 天和已逾期的，只列选中那天的；周一到周日时今天以前的日子从已逾期的里按截止日期挑出来，不另取。

### 时间轴

和 App 日历的[时间轴](ui.md#日历)一样按钟点看一周，放在桌面上，至少 4 格宽、3 格高：

- 标题行：“时间轴”（点了打开 App 日历的时间轴，停在小组件里选中的那天，`nexttodo://calendar/time/2026-11-26`）、刷新、`+`。
- 下面一排 7 天，同“一周”小组件：哪 7 天跟着[设置](#小组件的设置)里“一周”的日子，周几和日期，今天写“今”；点一天选中它（主色实心的方块），`+` 加到那天。没有小圆点：下面就是事项本身。
- 再下面一行“全天”（高 22dp）：只有日期的事项，每天一格一个小标签（标题一行，放不下省略），一天有几项时写“3 项”。7 天都没有只有日期的事项时没有这一行。
- 下面是钟点，每小时一行，高 40dp，左边 30dp 写“9:00”（都跟着文字大小缩放），整点一条淡线。小组件的列表每次打开都在最上面，不能像 App 里那样滚到现在，所以不从 0 点画：从 8:00、现在这个钟点和这 7 天里最早一项有时刻的事项那个钟点中最早的起，到 20:00、现在这个钟点和最晚一项那个钟点中最晚的止。这 7 天总有今天：现在这个钟点的“9:00”用主色写，今天那一列叠一层很淡的主色。放着时间轴小组件时，“日程”“一周”“时间轴”到了整点也自己重绘一次，同[日程](#日程)按截止时刻和零点的重绘；放上第一个、拿掉最后一个时立即按现在重绘。
- 事项块：有具体时间的放进截止时刻所在的钟点，占满那一格（四周各留 1dp），圆角 6dp，写标题，10sp、最多两行，放不下省略；一格有几项时合成一块，写“3 项”。颜色按状态，同 App 的时间轴：可做、逾期、等待中、重复事项以后的一次（只有一圈线），合成的块取最要紧的。块不能勾，勾选在“一周”和“接下来”小组件里。
- 点块打开 App 里的详情；点“3 项”和全天的“N 项”打开 App 日历的时间轴，选中那天（App 里关了时间轴视图的打开周视图；开着弹窗的先收起，同点小组件上的事项）。点空着的一格弹出[快速添加小窗](#快速添加小窗)，加到那天的那个钟点（全天一行的加到那天），同 App 时间轴里选一个钟点再添加；点左边的钟点同点标题。
- 桌面一次收下整个小组件，内容大了会画不出来（一直转圈）：空着的一格只用一个元素，整点的线画成整行的背景，事项块离格子边的 1dp 在背景图里；只按一个尺寸画（Glance 的 `SizeMode.Single`），不像其他小组件按实际的几种尺寸各画一份。
- 画哪些事项同“一周”小组件：只画要做的，今天起 7 天截止的，周一到周日时今天以前的日子是还没完成的（逾期的颜色）；做完的不画，在 App 的日历里看。
- 数据、刷新、外观、选中哪天的记法、可点区域的排法同“一周”小组件，和它共用存下的列表。

### 小组件的设置

设置里 Android 才有的一类“小组件”：上面是预览，下面是选项，改了立即生效，桌面上的小组件随即重绘。四个小组件用同一套，存在小组件自己的 SharedPreferences 里，App 经 `NextTodo` 插件读写。

- 预览：画成“接下来”小组件，列着现在“接下来”的前 3 项；垫在一半浅、一半深的圆角底板上（同设置的分组），透明度和文字颜色在浅色、深色的壁纸上各是什么样都看得到。往下滚动时预览留在顶上。
- 背景颜色：跟随系统（默认，就是现在的：浅色时白底，深色时深底）、白色、黑色、自定义。自定义同[文件夹颜色](ui.md#文件夹的颜色和图标)的自定义：调色盘和 RGB。
- 不透明度：滑块，0–100%，每档 5%，默认 100%；0 是只剩文字，直接压在壁纸上。
- 文字颜色：自动（默认）、白色、黑色、自定义（同上）。自动时按背景取黑字或白字；背景不透明度低于 50% 时文字主要压在壁纸上，看不出壁纸的深浅，就按系统的深浅（深色时白字），看不清的自己选。次要的文字和分隔线用同一个颜色，淡一些。逾期的红色、今天的琥珀色和主色的圆圈不随文字颜色变，按背景深浅用浅色或深色主题里的（自定义的文字颜色按它自己的深浅）；判断深浅用 WCAG 的相对亮度，取黑字和白字对比度相等的分界。
- 标题栏：三个开关“标题”“刷新按钮”“添加按钮”，默认都开（“日程”没有添加按钮，不受它影响）。只留按钮时标题栏矮一些，按钮靠右；都关掉时没有标题栏，列表从顶上开始，上面留的一点边距点了同点标题。关了刷新按钮的，靠 App 交来的列表和 15 分钟一次的自动刷新。
- 文字大小：小、标准、大，字号和行距按比例缩放（0.88、1、1.15 倍），仍跟着系统的字体大小。
- “一周”的日子：从今天起 7 天（默认）、本周一到周日，“一周”和“时间轴”小组件都按它，见[一周](#一周)。
- 不做背景图片：小组件的内容整个交给桌面，图片算在 1MB 里（见“接下来”小组件）；上面的文字也难看清，半透明的颜色已经能衬出壁纸。

## 快速添加小窗

不打开 App 就记下一条：一张卡片从屏幕底部弹出，盖在正在用的 App 上面，背后变暗，里面就是[快速添加栏](ui.md#其他)（同一套输入区、回形针、✦、目标文件夹和发送按钮，弹出时就是展开的两层，也能粘贴附件）。

- 入口：
  - 小组件上的 `+`（“一周”“时间轴”的加到选中的那天），“时间轴”上空着的一格（加到那天的那个钟点）；
  - 长按 App 图标的菜单里的“快速添加”（静态快捷方式，悬浮球、桌面手势这类第三方工具也能调用）；
  - 下拉控制中心的开关“快速添加”（Quick Settings 磁贴，用户在编辑控制中心时自己加上；锁屏时先解锁）；
  - 系统的分享：在别的 App 里分享文字、图片或文件，选“NextTodo”。
- 弹出时输入框获得焦点，键盘随即弹出。网页自己聚焦输入框弹不出键盘，由原生（插件的 `showKeyboard`）弹出；窗口还没拿到焦点时，等拿到再弹。
- 和“接下来”的快速添加栏是同一份草稿、同一个目标文件夹：默认是上次选的，也可以在设置里固定一个，像收集箱那样，见[快速添加栏](ui.md#其他)。
- 发送后卡片里显示“正在保存…”，服务端收到（附件也传完）后收起，回到原来的 App，小组件随即更新。AI 整理的配置存在这台设备上的，还要等它把请求交给服务端（见 [AI 整理](ai.md#保存位置和安全)），另一个请求正在整理时不等；服务端不接受这份配置的，提示原因，不再等。
- 没联网时存在手机上就收起。App 开着的（在后台也算），小窗收起时把还没发出的交给它，联网后由它发出；没开的，下次打开 App 或小窗时发出。
- 被服务端拒绝的不收起，提示原因，事项加上了、附件被拒绝的也是。
- 点卡片外面、按返回键或离开（切到别的 App、锁屏）随时收起：没发送的留在草稿里；已发送的等存进手机再收起，没发出的同样交给 App；分享来的还在读的，等读完放进输入框。存不进手机（如存储空间满了）又还没发出的不收起，提示原因，发出后或再点一次时再收起。
- 分享来的：文字接在草稿后面，分享时带的标题（`EXTRA_SUBJECT`，如网页的标题）在前，各占一行；图片和文件作为附件，规则同[附件](ui.md#附件)，读不出的提示原因，其余照常。只收 `content://` 的、不是 NextTodo 自己的（分享的 App 授权读取的，或本来就公开可读的）；超过附件大小上限的不复制，会先压缩的照片除外。配置了 AI 整理的切到 AI 整理，分享来的多是一段话或截图；没配置的切回直接添加，多行的文字合成一行。离线时按这台设备上次知道的服务端配置，不知道的当作没配置。
- 要去别的页面的（如去设置里选 AI 整理的模型），打开 App 到那一页（`nexttodo://page/<路径>`），小窗收起。
- 没登录时卡片里只有“打开 NextTodo 登录”，点了打开 App；App 打不开时（如本机模式出错）写明原因和“打开 NextTodo”。
- 做法：一个透明、背后变暗的 Activity，在自己的任务里、不进最近任务；装着自己的 WebView，加载同一份网页 App 的另一个页面，只画这张卡片。和电脑的[菜单栏小窗](desktop.md#菜单栏小窗)一样，是同一个网页 App 开在另一个窗口里，登录、本地副本和草稿同 App 共用（同源的存储），也照常同步。
  - 离开时不由原生立即关掉，由页面在看不见时（`visibilitychange`）等存好再关：刚发送就离开，页面还没写完。
  - 两个窗口同时开着时各发各的，同一个改动服务端按 ID 只收一次。小窗收起前把发件箱里还没确认的改动经同源的 `BroadcastChannel` 交给 App 的窗口（`handed`），App 的窗口当作自己的接过去；没有 App 的窗口时，它们留在本机的发件箱里，下次启动时发出。
  - Capacitor 的 `BridgeActivity` 启动时会换上自己不透明的主题，要换回透明的；页面不给这个窗口设系统栏的颜色。
  - 附件缓存只在 App 的主窗口打开时清理：小窗打开时清理，会删掉主窗口刚交给别的 App 打开的文件。分享来的文件复制到缓存里另一个目录，下次分享时清掉。
  - 用 App 上次启动时选定的网页版本（见[更新](#更新)）；小窗自己不换版本。
  - 小窗还开着时又被打开（被没盖满屏幕的窗口挡着，还没停下）：换成新的内容，页面重新载入。
  - 从点下去到键盘弹出（模拟器）：App 的进程不在时约 1.4 秒，在时约 0.45 秒。只画一张卡片、不登录不同步的页面是约 1.1 秒和 0.3 秒，差得不多，所以用完整的网页 App。

## 原生发出的改动

小组件勾选完成、通知和提醒卡片上的“完成”都不经过 App 的网页，由原生直接调用 `POST /mutations`，用同一套代码：

- 重复的事项完成时带上这一次（`occurrence`，见 [API](api.md#改动)），取自点的那条通知、那张卡片或小组件上的那一项：列表过时、这一次已经在别处完成或跳过了的，服务端不会把下一次也完成掉。服务器比 App 旧、还不认 `occurrence` 时，重复事项的这种完成会被拒绝，属于[App 比服务器新](design.md#app-更新)的情况。
- 改动 ID 由原生生成。连不上服务器、服务端出错（5xx）、超时或限流（408、429）时先存下（SharedPreferences，记着是哪个用户的），联网后按顺序补发（WorkManager，间隔逐次加长；本机模式下不要求联网，[借网盘同步](local.md#借网盘同步)时要求），补发完刷新小组件；同一个 ID 重发不会重复生效。用户由 App 在登录时（写入令牌之前）和会话开始时告诉原生；登录的不是这些改动的用户时，它们随即删掉，不会用新账号的令牌发出。
- App 打开会话时和回到前台时，把这个用户还没发出的改动接过去，和自己的改动一样先在本地生效、再发出。不接过去的话，App 离线打开时看不到它们，重复的事项可能被再勾一次、多顺延一次。原生这边也留着，照样补发，发出后才删，两边都发的由服务端按 ID 去重：App 存下它们之前被结束也不会丢，小组件也由此知道勾选完成成了哪个改动序号。
- 当场被服务端拒绝的（4xx，登录失效除外），小组件恢复原样并提示，通知和提醒卡片上的“完成”提示原因；补发时才被拒绝的，丢掉这个改动，发一条通知（渠道“未生效的改动”）写明是哪一项、什么原因，点开进 App。
- 退出登录、换了账号、本机数据换了[代号](local.md#数据代号)时，删掉没发出的；登录失效时留着，同一用户再登录后由 App 接过去，和网页端的待发改动一样。

## 写进系统日历

在系统日历里和别的日程一起看到带截止时间的事项。本机模式和连接服务器都能用，默认关闭，在设置的“系统”里打开。

- **写进哪个日历**：打开后默认写进 App 新建的“NextTodo”日历（本机账号，只在这台手机上，不上传）。这个日历对日历 App 是只读的：不能往里加日程，也不能改 NextTodo 写的（改了也不会改回事项）。可以在同一行换成手机上已有的、能写入的日历（Google、小米等账号的），下方说明写进去的日程会随这个账号同步到云端。换日历或关闭时，先删掉 NextTodo 写过的日程和“NextTodo”日历；别的应用往“NextTodo”日历里加了日程的，这个日历留着。所选的账号日历不在了（比如账号被移除）或不能再写入，这一项就当关闭；还留在那里的日程，等下次退出登录或换日历时删掉。
- **多台手机**：每台各写各的。几台都写进同一个账号日历，每个事项会有几份；只在一台上选账号日历，其他的用各自的“NextTodo”日历。
- **写哪些**：选中的文件夹里未完成、带截止时间的事项，一项一个日程，还在等前置的也写。只有日期的是那天的全天日程，有具体时间的是截止那一刻（开始和结束相同）。重复的事项只写当前这一次，顺延后改到新的日期，不写成日历的重复规则：NextTodo 的“从完成那天算”日历表达不了。
- **哪些文件夹**：默认写全部事项。打开后“系统日历”一组里多一行“写入的文件夹”，右边写“全部”，或选中的文件夹名，几个用“、”隔开，太长的省略。点开是和“移动到”一样的文件夹列表，自己的在前，共享给我的另成一组，每行一个勾选框：
  - 勾一个文件夹，写它和它所有子文件夹里的事项；子文件夹随之勾上，不能单独取消。勾“根目录”就是全部事项，包括共享给我的文件夹里的。
  - 勾了、取消了马上生效，日历随之增删，关掉列表就行，没有“确定”。一个都没勾时什么都不写，这一行写“未选”。
  - 按文件夹 ID 记：文件夹改名、移到别处照样算；删掉了就当没选。
  - 只存在这台手机上，按账号分开记：换个账号登录，默认还是全部。和所选的日历一样，退出登录后留着，免得再登录时没选的文件夹一下子都写进日历。
- **写什么**：日程标题是事项标题，说明里只写所在文件夹和“来自 NextTodo”，不写描述；不加日历自己的提醒，提醒仍由 NextTodo 弹出，免得响两次。日程标为“空闲”，共享日历的人看到的忙闲不受影响。
- **何时更新**：和[截止提醒](#截止提醒)同时：会话开始、本地副本变化后（2 秒内合并处理）和 App 回到前台时，网页端算出应有的日程交给原生（`DeviceCalendar`），和已写的比较，增删改差异。日历和提醒、小组件分开排队，日历出错不影响提醒。换日历时只给当前的会话写入：已经结束的会话（比如在等权限弹窗时被别处退出登录）不再写。事项完成、删除、截止时间清掉后，日程随之删除。App 没在运行时不更新，比如在小组件里勾掉的，等 App 下次运行时才从日历里删掉。改了手机时区，有具体时间的日程按新时区的当地时间重写。
- **认出自己写的**：事项 ID 到日程 ID 的对应存在 App 私有的 SharedPreferences 里。用户在账号日历里删掉或改了某个日程的，下次更新时按事项重新写入。写的日程还带着 App 的包名（`CUSTOM_APP_PACKAGE`）作标记：“NextTodo”日历里对应不上、但带着标记的（比如写完还没记下 App 就被结束，或以前安装写的）也删掉，没有标记的不碰。账号日历里只删记着的：别的设备上的 NextTodo 写进同一个账号的日程带着同样的标记，删不得；所以那里写完还没记下 App 就被结束的，会留下一个多余的日程，要用户自己删。打开这一项时也先删掉以前安装留下的“NextTodo”日历。
- **退出登录、离开本机模式**：删掉写过的全部日程和“NextTodo”日历，所选的日历留着，下次登录或进入本机模式后照常写入。删除出错时提示，不挡退出；留下的日程对应关系还在，下次登录后的第一次更新删掉。
- **权限**：打开时请求读写日历的权限（`READ_CALENDAR`、`WRITE_CALENDAR`）；被拒绝就不打开，这一行改为提示到系统设置里允许。之后在系统设置里收回权限的，暂停更新，已写的日程留在日历里，这一行提示去允许；这期间退出登录也删不掉日程，对应关系留着，再允许后的下一次更新删掉不再需要的。

## 附件

- 页面上传、下载[附件](design.md#附件)的文件用 WebView 自己的 `fetch`（`window.CapacitorWebFetch`），连服务器和本机模式都一样。CapacitorHttp 把请求体和回复整个经原生和网页之间的桥传递，官方文档说数据量大时会出问题；服务端的附件接口为此允许来源 `https://localhost` 跨域，见 [API](api.md#附件)。
- 打开和保存文件：文件取自页面的 `files` 表（没有就先下载），所以下载过的离线也能打开，还没上传完的也能。页面把它分块（每块 512 KB，base64）交给插件的 `writeAttachment`，写进缓存目录的 `attachments/<附件 ID>/<名称>`：一次经桥传整个文件会出问题。先写在旁边，最后一块写完才换上，别的 App 读到的总是完整的文件；页面一次只交一个文件。附件 ID 按 UUID 解析，文件名由 Rust 的同一个函数给出，规则见[桌面 App](desktop.md#附件)。写完再调：
  - `openAttachment`：经 FileProvider 用 `ACTION_VIEW` 交给别的 App，授予临时的读权限；没有能打开的 App 时报“没有能打开这种文件的应用”。
  - `saveAttachment`：用 `ACTION_CREATE_DOCUMENT` 让用户选位置，复制进去。
  - 这些文件在下次启动 App 时删掉。
- 拍照用 `<input type="file" accept="image/*" capture="environment">`，由 Capacitor 的 WebView 打开系统相机。

## 更新

总体见[总体设计](design.md#app-更新)。

**版本**：原生版本是改过原生部分的提交数（`apps/android`、`apps/web/capacitor.config.ts`）加 2，写进 APK（`BuildConfig`）。`versionCode` 仍是全部提交数，只增不减；`versionName` 是 `0.1.<全部提交数>`，和同一次构建的桌面 App 一样。

- `apps/web/package.json` 不计入：只改网页依赖或脚本的提交，不必让 Android 用户重装 APK。Capacitor 插件的增删和升级由 `cap sync android` 写进 `apps/android/capacitor.settings.gradle`：模块路径带着插件和 `@capacitor/core` 的版本号。
- 发版构建在 `cap sync android` 之后，发现 `apps/android` 下有没提交的改动就停下，免得插件变了却没算进原生版本。直接用 `pnpm android:build` 打的包不检查。
- 加 2 是接续：原来的算法还计入 `apps/web/package.json`，加 2 让换算法前后的原生版本相同（58），不倒退，也不用为换算法重装 APK。

**网页热更新**：

- 构建网页时生成 `app/web.json`：`{version, native, files}`。`version` 是构建它的提交，`native` 是构建时的原生版本，即这份网页要求的最低原生版本，`files` 是全部文件的路径。它随网页部署到服务器，也打进 APK。
- 打开 App、回到前台时和运行期间（每小时最多一次）请求服务器的 `/app/web.json`。版本号必须是提交号（它也是目录名），和当前不同、原生版本够用时，在 App 私有目录 `files/web/<version>/` 准备新版本：`assets/` 下的文件名由 Vite 按内容生成，当前版本里已有的直接复制，其余从服务器下载。全部下载成功、并且再取一次 `web.json` 版本没变（下载期间服务器没换版本）才算准备好，否则下次再试。换了服务器登录时，检查重新开始。
- 下次打开 App 时生效：打开前把 Capacitor 的 `serverBasePath` 指向新目录。网页显示出第一个页面（登录页或主界面）后报告就绪（`webReady`），这时新版本才算可用，删掉更早的目录。新版本打开后 30 秒内没报告就绪的，当场退回它要替换的版本（或 APK 里的）并重新加载，不再尝试这个版本；不等下次启动，因为再点图标往往只是回到同一个界面。期间又下载好的版本等下次启动再试。
- 装了新 APK 后，Capacitor 自动改用 APK 里的网页（`isNewBinary`），之前下载的版本作废、删掉。

**原生更新**：服务器上的 `/app/android.json` 是 `{native, versionName, url}`，和网页热更新各查各的，一个失败不影响另一个。它的原生版本比已装的新时（本机模式从 GitHub 取，比的是版本号，见[本机模式](local.md#更新)），设置页“关于”里显示“有新版本”，并在打开 App 时用提示条提醒一次；点“下载安装”把 APK 下载到缓存目录（每次一个新文件，整个 App 同时只下载一个；安装器可能还没读，本次运行下载的都留着，之前运行留下的在下次下载时删掉），交给系统安装器。第一次需要在系统设置里允许本 App“安装未知应用”（`REQUEST_INSTALL_PACKAGES`）。

设置页“关于”里显示的版本（网页部分的，和安装包不同时另写安装包的），以及点按“App 版本”立即检查更新，见[总体设计](design.md#app-更新)。

## 澎湃 OS

系统会清理后台，小组件的定时刷新和提醒需要 App 被允许“自启动”、省电策略设为“无限制”。不是“无限制”时，App 退到后台几秒就被冻结，到点的闹钟被系统扣住，等下次打开 App 才响（澎湃 OS 4 实测，只开“自启动”、只加系统的电池优化白名单都不够）。提醒要在屏幕顶部弹出横幅，还要在“截止提醒”这类通知里允许“悬浮通知”，新装的 App 默认不允许；打开[弹窗提醒](#弹窗提醒)的，还要允许“悬浮窗”。App 第一次启动时显示一张说明卡片，按钮打开本 App 的系统设置页；在设置里也能再次查看。

“应用联网”（俗称“禁止联网”）关掉了手机当前用的网络时（连着 WLAN 时关了 WLAN，用数据时关了数据），App 的所有连接都被系统当场拒绝，连本机的 `127.0.0.1` 也算，[本机模式](local.md#启动)就连不上 App 内置的服务端；关的不是当前用的网络时不受影响（澎湃 OS 4 实测）。系统的联网状态里看不出这一点，只能从连接被拒绝（`EACCES`）认出来。

## 构建和签名

- 需要 Android SDK（`ANDROID_HOME`）和 JDK 21（Capacitor 8 的 Gradle 版本还不支持更新的 JDK）。
- 本机模式的动态库由 Gradle 在构建前编译（任务 `rust`，调用 `cargo ndk`），还需要 SDK 里的 NDK、`rustup target add aarch64-linux-android` 和 `cargo install cargo-ndk`。
- `pnpm android:build`（在 `apps/web` 下）：构建网页端、`cap sync android`，再用 Gradle 打 release APK。
- release 版由 R8 去掉用不到的代码和资源（`minifyEnabled`、`shrinkResources`），APK 从约 20.6 MB 减到 11.7 MB，下载和更新更快。不改类名和方法名（`proguard-rules.pro` 里的 `-dontobfuscate`）：代码本来开源，日志里的调用栈不用映射文件就能读，只多约 0.1 MB。Capacitor、WorkManager、Glance 自带保留规则，本机模式库的 JNI 方法由默认规则保留，不用另加。调试版不压缩，R8 删错东西只在 release 版出现：加了插件、反射或 JNI 后，装 release 版走一遍。
- 正式版用自签名的密钥签名，直接安装。密钥库和密码不进仓库：路径和密码从环境变量 `NEXTTODO_KEYSTORE`、`NEXTTODO_KEYSTORE_PASSWORD` 读取。
- 版本号见[更新](#更新)。发布用的 APK 由 `deploy/build.sh` 构建，放进服务端镜像，也上传到 GitHub Releases，见[部署](deploy.md#构建发布)。

## 测试

- 网页端的逻辑（提醒时间计算、小组件列表）用 Vitest 测。
- 原生部分在模拟器上实际操作验证：登录、同步、离线修改、提醒到点弹出、小组件显示和勾选、写进系统日历（用 `adb shell content query --uri content://com.android.calendar/events` 看写进去的日程）。
- 小组件的点击还要在澎湃 OS 真机上验证：桌面处理列表点击的方式和原生不同，模拟器上测不出来。真机上装测试版（调试版的包名临时加后缀，和正式版并存），用 `adb reverse` 连本机的开发服务器，不碰正式数据。
- 提醒的横幅、通知上的按钮、提醒卡片和小组件打开快速添加时弹出键盘也要在澎湃 OS 真机上验证：系统另有省电策略、悬浮通知和悬浮窗的开关，模拟器上测不出来。测试版要和正式版一样设好[这些开关](#澎湃-os)；用 `adb` 设的电池优化白名单和自启动代替不了省电策略。
- 澎湃 OS 上用 `adb install` 装测试版，每次都要在手机上点“继续安装”，手机锁着时直接取消。
