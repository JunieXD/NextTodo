# NextTodo 总体设计

## 定位

待办应用，核心是事项之间的先后关系：事项和依赖组成一张有向无环图，首页随时列出“现在能做的事”。文件夹可以无限嵌套，用来分开不同的项目。手机优先，网页、Android、iOS、macOS、Windows 实时同步，离线也能用。agent 通过 API、命令行和 MCP 管理整个待办。支持多个账号，朋友凭邀请码注册；文件夹可以共享给同一台服务器上的其他人，几个人分工做一个项目，见[共享](#共享)。不想部署服务器的，App 可以只在本机使用，见[本机模式](local.md)。

## 概念和规则

### 文件夹

- 可以无限嵌套，也可以没有文件夹，事项直接放在根目录。默认不建任何文件夹。
- 同一层的文件夹不能重名，名字里不能有 `/`，所以每个文件夹都能用路径（如 `/工作/网站改版`）唯一指明。
- 同一层的文件夹按手动顺序排列。
- 删除文件夹会连同里面的子文件夹和事项一起删除：界面上先确认，删除后能撤销。
- 文件夹可以选颜色和图标，一眼认出是哪个：颜色有 14 种预设，也可以自己调；图标是 40 个预设，见[界面](ui.md#文件夹的颜色和图标)。只用在文件夹的图标上，不染别处。没选的照旧。随文件夹同步，共享的文件夹里大家看到的一样；共享的文件夹本身的颜色和图标只有共享人能改（见[共享](#共享)）。
- 复制文件夹会连同里面的子文件夹、事项、附件，以及它们之间的先后关系，一起复制一份，用来把一套流程当模板反复用，比如签合同要走的审价、盖章、法人签字。
  - 副本里的事项都是待办：完成过的变回待办，重复的事项完成次数清零。开始、截止、提醒和重复原样保留。连到文件夹外面的依赖不复制。
  - 颜色和图标一起复制。
  - 副本放在原文件夹的同一层，名字用原名，同一层已有就叫“签合同 副本”，再有就是“签合同 副本 2”……；原名太长时截短，留出“ 副本”的位置，不超过名称的 100 个字。别人共享给我的文件夹复制到我的根目录。
  - 附件的文件另存一份，描述里对这些附件的引用改指副本里的附件。
  - 负责人：副本还在同一个共享的文件夹里的保留，否则去掉。共享的文件夹复制出来的副本不共享。
  - 一次复制是一个批次，能撤销；最多 1000 个操作（文件夹、事项、依赖和附件各算一个）。

### 事项

| 字段 | 说明 |
|---|---|
| 编号 | 每个用户从 1 开始递增的短编号（如 `#42`），由服务端在收到时分配，方便命令行和 agent 引用。离线新建的事项同步后才有编号。共享的文件夹里的事项用共享人的编号，见[共享](#共享) |
| 标题 | 必填，单行 |
| 描述 | 可选，Markdown（GFM，支持 `- [ ]` 清单），可以引用附件 |
| 附件 | 可选，截图、照片和其他文件，见[附件](#附件) |
| 文件夹 | 可选，不填就放在根目录 |
| 负责人 | 可选，可以有多个，只有[共享](#共享)的文件夹里的事项能设；没设时所有成员都能做 |
| 完成时间 | 为空表示待办，有值表示结束了：做完了，或者[放弃](#放弃)了（另记一个“放弃”）。状态只由这两个字段决定 |
| 截止时间 | 可选：一个日期，可以再加具体时间（精确到分钟）；也可以是“前置完成后几天内”，见[前置完成后的截止](#前置完成后的截止) |
| 提醒 | 可选，设了截止时间才能设，可以有多个：截止时或提前若干分钟（要有具体的截止时间），或截止那天、提前几天的几点，见[提醒](#提醒) |
| 重复 | 可选，只有设了截止时间才能设：每 N 天、每 N 周、每 N 个月或每 N 年，按周的可以选周几，按月的可以选几号，可以设重复到哪天，见[重复](#重复) |
| 顺序 | 手动顺序，作为依赖顺序之外的次级排序 |

### 依赖

- `A → B` 表示 A 完成后才能做 B，A 是 B 的**前置**，B 是 A 的**后续**。
- 可以跨文件夹连，但只能连在同一处：私人的事项之间（不在任何[共享](#共享)的文件夹里），或同一个共享的文件夹里的事项之间。在同一处移动事项时依赖不变。
- 不能成环：服务端在每次加依赖时检查，成环就拒绝，并返回环上的事项。
- 删除事项时，连着它的依赖一起删除。

### 派生状态

| 状态 | 条件 |
|---|---|
| 可做 | 待办，所有前置都已完成或放弃，并且到了[开始时间](#开始时间)（没设的不用等）。[重复](#重复)的前置做过这一次就算完成 |
| 等待中 | 待办，还有前置没结束，或者还没到开始时间 |
| 已完成 | 有完成时间，没有放弃 |
| 已放弃 | 有完成时间，标为放弃 |

前置没完成也能直接把事项标为完成（现实里经常有跳步），界面上会先确认一次。重新打开一个已完成的事项，它的后续可能因此变回“等待中”。

### 放弃

没做成、以后也不做了的事项标为“放弃”。和删除不同：删除给加错了、本不该有的事项用；放弃的留着，看得到当初有这件事、什么时候放弃的。

- 和完成一样算结束：不在“接下来”、小组件和提醒里，不再逾期。在[已完成](#已完成)里和完成的放在一起，标“已放弃”；点勾选圈同样恢复成待办。
- 放弃的前置不再挡着后续：这一步不用等了。还有没结束的后续时，确认框问“只放弃这一项”还是“连同 3 项后续一起放弃”（后续的后续也算，已经结束的和隔着它的不算），一个改动，撤销时一起回来。
- 重复的事项放弃就是整个结束，不再有下一次；只是这次不做，用[跳过](#重复)。
- [关联进度](#关联进度)照常算它一步。[日历](#日历)里照常列在截止那天，样子是放弃的；热力图只数完成的。
- 前置还没结束也能直接放弃，不用确认：放弃不会让谁误以为前面做完了。
- agent 用工具 `drop`，命令行 `nexttodo drop`；事项的 `status` 多一种 `dropped`，见 [agent 接入](agent.md#工具)。

### 开始时间

有的事要到某个时候以后才能做：每月 1 号才能领的券，只能在到期前一个月内办的续费，晚上 8 点才开抢的票。事项可以设开始时间，没到就像等前置一样等着。

- 和截止时间一样，开始时间是日期加可选的几点几分；不设几点的从那天 0 点开始。可以只设开始、不设截止；两个都设时，开始不能晚于截止：没设几点的截止算到那天结束，同一天两个都设了几点的，开始的不能晚于截止的。
- 设的时候可以按日期选，也可以按截止往前数：截止当天、截止前 N 天，再加几点（“截止前 3 小时”就是选那天的几点）。只是选法，存的仍是日期和几点；之后改截止日期，开始不跟着动。重复的事项顺延时间隔不变（见下文），所以“截止前 2 天”每一次都是截止前 2 天。
- 重复的事项做完后带着下一次的截止留在“接下来”，每天、每周的例行事项会堆在“7 天内”“以后”里。所以“接下来”里有没设开始时间的重复事项标着“今天已完成”、等着下一次时，顶上出现一张提示卡，说明可以设成截止前几天才显示，点“设开始时间”打开这一项的开始时间，按截止往前数。点了卡上的按钮，或在这台设备上设过开始时间，就不再出现；每台设备、每个账号各算各的。见[界面](ui.md#弹窗对话框提示条)。
- 开始之前是“等待中”：不进“接下来”和小组件，在文件夹里灰着，标“11 月 14 日开始”“明天 9:30 开始”“20:00 开始”（写法同截止时间）；到了那时自动变成可做。它的后续照常等它。前置也没完成的，两样都满足才可做。
- 开始之前也能直接标为完成，和前置没完成时一样先确认一次。
- 到了开始时间不提醒，[提醒](#提醒)只按截止时间设。
- 重复的事项顺延时，开始日期跟着顺延，和截止日期相隔的天数不变，几点不变：每年续费、到期前 30 天开始的，每年都是到期前 30 天；每月 1 号领券的，开始和截止都是 1 号。勾掉以后它回到等待中，到下一次的开始时间再出现。
- “现在”是设备上的日期和时间，和[重复](#重复)的“今天”一样。服务端不知道用户的时区，工具可以带上用户当地的 `today` 和 `time`，命令行和小组件总是带上本机的日期和时间；只带 `today` 的，那天开始的都算已经到了；都不带的按 UTC 算，见 [agent 接入](agent.md#工具)。

### 前置完成后的截止

有的事要在前一步做完后几天内做：发票开出后 30 天内报销，报告出来后 7 天内复诊，合同签完 3 天内付款。前一步哪天做完事先不知道，写不了日期；用[复制文件夹](#文件夹)反复走的流程更不能写死日期。所以截止时间也可以设成“前置完成后 N 天内”：

- N 是 0–365，0 就是前置完成的当天；可以再加几点几分（“前置完成后 3 天内 18:00”）。
- 等前置时还没有截止日期：文件夹里标“前置完成后 3 天内”，不进日历和日程，不提醒，不算逾期。
- 前置都完成的那一刻定下截止日期：那天加 N 天，几点照设的。“那天”是完成最后一个前置的设备上的日期，同[重复](#重复)的“今天”。定下以后就是普通的截止时间：提醒、逾期、日历、小组件、每日汇总都照常，写成“11月27日截止”，详情里另注“前置完成后 3 天内”。
- 设了[开始时间](#开始时间)、开始那天更晚的，从开始那天算，截止就不会早于开始。N 是 0、两个都设了几点的，开始的几点不能晚于截止的，设的时候检查，同开始和截止的规则。
- 设的时候前置已经都完成了，或者没有前置，当场按今天定下；去掉最后一个没完成的前置（去掉连线，或删掉那一项）时，也按那天定下。
- 前置重新打开、或者连上了没完成的前置，事项变回等待，定下的日期去掉，下次前置都完成时重新算。撤销完成前置的那次改动，定下的日期一起撤销。只在这些改动发生时定下或去掉。做过的[重复](#重复)前置挡着它时，日期不去掉：到了下一次、撤销它后来的一次完成、把它连上，都只是又到了它的一次。
- 提醒按定下的截止时间算，等前置时就能设；提前多久的要设了几点。第一次设时带上[默认提醒](#提醒)，同给事项设截止时间。
- 不能和[重复](#重复)一起设：重复要从一个具体的截止日期往后推。手动改成某个日期，就不再是“前置完成后”的了。
- [复制文件夹](#文件夹)时照原样复制：副本里的事项都是待办，前置也在副本里的回到等待、没有截止日期；没有前置的按复制那天定下。
- agent 和命令行写作 `due_after: 3d`、`3d 18:00`，也可以按周写 `2w`，见 [agent 接入](agent.md#引用)。AI 整理也会写：原文说“拿到发票后 30 天内报销”，前置是“拿到发票”，见 [AI 整理](ai.md#提示词和结果)。

### 后续的截止

有截止的事往往要先做完几件没写截止的准备：周五交报告，之前要查资料、写初稿。准备的事自己没设截止，实际上也得赶在报告之前做完；前置的截止比后续的还晚，多半是设错了。

- 事项要赶的截止，是它自己的截止和它挡着的没结束的后续（后续的后续也算）的截止里最早的一个。只沿着还挡着后续的事项往后算：隔着已结束的事项，或者隔着这一次已经做完、下一次还没开始的[重复](#重复)事项，就不再往后算。后续的截止是[前置完成后](#前置完成后的截止)、还没定下日期的不算。
- “[接下来](#接下来)”按要赶的截止分组、排序：自己没设截止、后续 11 月 30 日截止的，排进 11 月 30 日所在的组，和 11 月 30 日截止的事项按同一时刻排；后续已经逾期的，排进“已逾期”。
- 行上照常写自己的截止；没设的写“后续 11月30日”，颜色同截止时间（逾期红色、今天琥珀色）。设了、但比后续的晚的，截止后面写警示色的“晚于后续”。
- 详情的截止一行下面写是哪一项：没设的“后续“写初稿”11月30日截止”，晚于后续的用警示色写“晚于后续“写初稿”的截止（11月30日）”。
- 只管排序和提醒设错：不进日历，不提醒，事项自己不算逾期；“日程”“一周”“时间轴”小组件和每日汇总照旧只看自己的截止。
- `next` 工具按同样的顺序返回，要赶后续截止的事项多一个 `due_by`（截止时间和那一项的编号、标题）；“接下来”小组件同 App。见 [agent 接入](agent.md#工具)。

### 提醒

还款日前一天核算钱够不够、当天再提醒一次还款；开会前 1 天准备材料、前 15 分钟出发。一个事项可以设任意多个提醒，有两种：

| 种类 | 什么时候 | 能设在 |
|---|---|---|
| 提前多久 | 截止时，或提前若干分钟、小时、天，最多 30 天 | 有具体截止时间的事项 |
| 按日子 | 截止那天或提前几天（最多 30 天）的几点，如“当天 09:00”“前一天 20:00” | 有截止日期的事项，只有日期的也行 |

- 提醒跟着截止时间走：改了截止日期或时间，提醒随之移动；去掉截止的具体时间时，提前多久的提醒一起去掉，按日子的留着。重复的事项每一次都按同样的提醒。
- 同一个事项同一时刻的几个提醒只弹一次。
- 最多 100 个，只为挡住误用，界面上不限。
- **默认提醒**：设置“提醒”里分别选有具体时间的和只有日期的事项默认带哪些提醒，存在这台设备上，默认都不带。给还没有截止时间的事项设截止时间时预先选好，可以改。[AI 整理](ai.md#提示词和结果)出的事项也带上：提交（或重试）整理的设备把它的默认提醒一起交给服务端，原文说了怎么提醒的按原文。agent 不用默认提醒，要提醒就自己写。
- **隐藏通知内容**：设置“提醒”里的开关，存在这台设备上，默认关。打开后提醒的通知只写“有事项到期”，不写标题、截止时间和文件夹，锁屏上被人看到也不泄露；点开照常打开这个事项。Android 的[弹窗提醒](android.md#弹窗提醒)也一样。
- **每日汇总**：设置“提醒”里的开关和时间，存在这台设备上，默认关，时间默认 21:00。打开后每天到这个时间，有今天截止或已经逾期、还没完成的[我的事项](#共享)时发一条通知：标题“今天还有 3 项未完成”，内容是它们的标题，用顿号隔开，截止早的在前；都做完了就不发。和截止提醒一样，不受“接下来”的文件夹筛选影响。点开进入“接下来”，没有“完成”和稍后提醒。隐藏通知内容时只有标题。
  - 网页算出今天起 7 天每天的汇总，和提醒一起交给 App：之后几天的按现在的数据算，到那天还没做完、那天截止的都在里面。在这台手机的通知、提醒卡片或小组件上完成的，排着的汇总里随即去掉；App 没运行时别处的改动要等它下次运行才算进来，同提醒；7 天没运行，之后就不汇总了。打开隐藏通知内容后，手机上已经弹出、列着标题的汇总收回；桌面的通知插件收不回已经弹出的通知，只隐藏以后的。
- 网页不提醒；Android、iOS 和桌面 App 怎么弹出见各自的文档。

### 关联进度

经前置、后续连在一起的事项，可做时在“接下来”、小组件和 `next` 工具里标出它是第几步、共几步，如“2/5”。按先后关系数步数：

- 第几步：这一项前面最长的一串前置有几项，再加一。同时能做的几项是同一步。
- 共几步：经过这一项、从头到尾最长的一串有几项。
- 只看连线，不看完成了没有，已完成的也算一步：勾掉一项、跳着做，别的事项的数都不变。连线可以跨文件夹。

| 情况 | 显示 |
|---|---|
| 一条线 A → B → C → D → E | A 是 1/5，B 是 2/5，E 是 5/5 |
| A 之后 B、C 可以同时做，D 等 B 和 C | A 是 1/3；B、C 都是 2/3；D 是 3/3 |
| X、Y、Z 都做完才能做 D，D 之后是 E | X、Y、Z 都是 1/3；D 是 2/3；E 是 3/3 |
| 两件事共用一个前置：“开通账号”之后，甲有 2 步，乙有 3 步 | 甲的是 2/3、3/3，乙的是 2/4、3/4、4/4；“开通账号”本身是 1/4 |
| 长短两条线汇到一项：P → Q → R → T，还有 S → T | S 是 1/2，T 是 4/4，按长的那条 |

- 没有前置、后续的事项不标。只标在可做的事项上：文件夹页有轨道画出先后，不标。
- 网页离线时也要显示，所以和依赖状态一样，核心库（Rust）和网页端（TypeScript）各算一份，用同一套测试数据校验。

### 重复

- 有截止时间的事项可以设重复：每 N 天、每 N 周或每 N 个月（N 为 1–365，N 为 1 时叫每天、每周、每月）。每年就是每 12 个月，不单独存：12 个月的倍数写成每年、每 N 年，2 月 29 日按下面月末的规则在平年取 2 月 28 日。清除截止时间时，重复一起清除。
- 按周重复的可以选在周几，如每个工作日（周一到周五）、每周一三五、每两周的周二和周四；不选就是截止日期那天是周几，和每周一次一样。
- 也可以选“每个法定工作日”：周一到周五，去掉[放假](#节日和放假)的日子，加上补班的周末，给日报、打卡这类上班才做的事用。顺延同选了周几的，推到下一个法定工作日（按截止日期算的，晚于原来的截止、不早于今天；从完成那天算的，晚于今天）。例如 2027 年春节 2 月 5 日到 13 日放假，1 月 31 日和 2 月 14 日（都是周日）补班：2 月 4 日勾掉，下一次是 2 月 14 日。
  - 只能整组用，不能自选周几，也不能每隔几周：补班的那天顶的是周几的班，通知里没有写，“每周一三五”这类没法跟着调。
  - 只管顺延：截止日期是设的、改的，照设的存，落在放假的日子也不挪；换了新的表，已经定下的截止日期也不改，只影响以后怎么顺延。
  - 按设备或服务端带的[放假和补班的表](#节日和放假)算，表里没有的日子只看是不是周一到周五。
  - 表的版本不同时（新一年的安排刚公布，还没都升级），各算各的：连服务器的，完成由服务端算，离线完成的那一次同步后日子可能改一次，接着离线又完成的下一次可能对不上、不算，事项回到服务端算的那一次；跳过这一次由跳过的设备算，可能落在放假的日子，不会再改。[本机模式](local.md#借网盘同步)经网盘同步时，以做这个改动的设备算的为准。
  - 旧版本的 App 不认识它，当作每周一到周五；在旧版本的截止时间弹窗里保存（只改提醒也算）就变回每周一到周五。旧版本的服务端不收，这个改动保存失败。
- 按月重复的可以选在几号，如每月 1 号和 15 号、每月 27 和 28 号；不选就是截止日期那天是几号，和每月一次一样。某个月没有选中的日子（29–31 号）时取那个月的最后一天，所以选 31 号就是每月最后一天；几个选中的日子落到同一天时只算一次。
- 重复的事项一直是待办（设了重复到哪天的，做完最后一次就完成，见下文）：标为完成时不记完成时间，而是把截止日期顺延到下一次，具体时间和提醒不变。它不进“已完成”；每次顺延都在改动记录里，可以撤销，详情里也能“撤销上一次完成”，见[界面](ui.md#弹窗对话框提示条)。
- 每次这样完成都记下来：事项上存完成的次数和最近一次的日期（完成那台设备上的当天）。最近一次是今天、截止已经到明天以后的，界面上标“今天已完成”，让人知道今天做过了，下一次照常顺延；补上漏掉的一次以后截止还在今天的不标，今天这次还要做；详情里显示完成过几次和最近一次的日期。撤销一次完成时，次数和日期一起改回去。去掉重复以后，记录仍然保留。
- 每次完成还另记一条完成记录：完成的是截止在哪天的那一次，在哪天完成（同上，设备上的当天），晚了几天、提前几天由这两个日子看出来。做完[重复到](#重复)的最后一次也记，“结束重复并完成”不记，和次数一样。同一次（同一个截止日期）完成了几回就记几条，比如按完成那天算的提前完成了、下一次还是同一天截止，又完成了一回；或者改回原来的截止日期又勾了一次。
  - 撤销那次完成时记录一起撤销；删除事项时一起删除，撤销删除时一起回来；谁看得到事项，谁就看得到它的记录，事项移进、移出共享的文件夹时跟着走。
  - 详情里点“已完成”一行看完成记录，[日历](#日历)的热力图也用它。记录从有这个功能的版本开始记，更早的完成只算在次数里。
- 读一本书、练一门技能这类没有截止的长期事项，也用重复来打卡：截止设为今天、每天重复，每天做了就勾一下。全部做完时选“结束重复并完成”：一步去掉重复并标为完成，事项进入“已完成”，这一步不算一次打卡。
- 漏掉了、不打算补的那一次，用“跳过这一次”：按下面的规则顺延到下一次（开始日期一起顺延；还没到截止就跳过的，从截止日期算，从完成那天算的也一样，不会往前挪），但不算完成，次数和完成记录都不变，可以撤销。已是最后一次的（下一次晚于[重复到](#重复)的那天）没有这一项，用“结束重复并完成”。
- 下一次从哪天算，每个事项自己选：

  | 方式 | 下一次 | 例子 |
  |---|---|---|
  | 按截止日期（默认） | 从原来的截止日期起推一个间隔，还早于今天就继续推，推到今天为止：漏掉的几次勾一下就补上，今天这次照常要做 | 每天背单词，昨天的今天才勾，下一次是今天；每周一开例会，周三才勾，下一次是下周一，到下周一才勾，下一次就是当天；周五提前勾掉下周一的，下一次是下下周一 |
  | 从完成那天 | 今天加一个间隔 | 每 30 天换滤芯，晚了 5 天才勾，下一次是今天起 30 天后 |

- 选了周几或几号的，上表的“推一个间隔”换成“推到下一个选中的日子”：起点那一周（那个月）后面还有选中的日子就取最近的一个，没有就跳到 N 周（N 个月）后那一周（那个月）里第一个选中的日子；一周从周一开始。例如每个工作日写日报，周五勾掉，下一次是下周一；周三才勾掉周一那次，按截止日期算，下一次是当天（周三）。每月 27 和 28 号各做一次的，27 号勾掉，下一次是 28 号；28 号勾掉，下一次是下个月 27 号。

- 没选几号的按月推时取下个月的同一天，没有这一天（29–31 日）的月份取最后一天；原来的截止日期是月末的，下一次也取月末。
- 按月、按年的重复可以按[农历](#农历)，用于农历生日、节日、初一十五这类事，如“每年农历八月十五”“农历每月初一、十五”：
  - 按农历的一定选了几号（初一到三十），默认是截止日期那天的农历日子。所以不会因为大小月漂移：初一就是初一，三十在小月取二十九；要“每年除夕”就选三十。
  - 每 N 个月数的是农历月，闰月也算一个月。12 个月的倍数（每年、每 N 年）数的是农历年，落在同名的月份，不落在闰月：闰月里的生日，以后每年在同名的那个月过。
  - 推到下一个选中的日子的规则和公历一样：起点那个月后面还有选中的日子就取最近的一个，没有就跳到 N 个月（N 年）后的那个月。
  - 截止日期要在农历的范围里；顺延超出范围时，这次就是最后一次。
- 重复可以设“重复到”哪天（含这天），不设就一直重复。用于有期限的计划，比如备考：每天练一套卷子，练到考试前一天。
  - 按上面的规则算出的下一次晚于这天的，这次就是最后一次：照常算一次完成（次数加一、记下日期），然后去掉重复、标为完成，事项进入“已完成”。
  - 过了这天，最后一次还没勾的照常逾期，不自动完成：自动完成就是替用户打了卡。勾掉照样算一次；不想算的，用“结束重复并完成”。
  - 截止日期不能晚于重复到的日子，改截止时间时晚了就报错。
- “今天”是标为完成的那台设备上的日期，命令行用本机的日期。
- 先后照常：前置没完成时勾选同样先确认。已完成和放弃的事项不能设重复，要先重新打开。
- 重复的事项完成过以后，在它现在这一次开始之前，对后续来说都算完成；这一次开始后，后续重新等它。设了[开始时间](#开始时间)的从开始时间算，没设的从截止日期那天 0 点算。还没完成过的照常挡着后续。

  | 情况 | 结果 |
  |---|---|
  | 每天背单词 → 每天做阅读 | 背完，阅读马上可做；阅读做完后，明天又要先背单词 |
  | 每周买菜 → 做顿大餐（不重复） | 这周买过菜，大餐可做；拖到下周还没做，又要先买菜 |
  | 新建的每周例会 → 写纪要 | 例会还没完成过，纪要等着 |
  | 例会逾期没开 | 纪要等着 |
  | 每天背单词 → 做阅读，昨天的今天才背 | 勾掉补上昨天的，今天这次已经开始，阅读还等着；行上也不写“解锁 1 项” |
  | 每天练一套卷子（重复到考试前一天）→ 参加考试 | 练完最后一套，练卷子就完成了，考试从此可做 |

- 顺延时它解锁的后续和普通的完成一样闪一下、写进提示条。[排序](#排序)和[关联进度](#关联进度)只看连线和完成时间，不受这条影响。
- 设了[开始时间](#开始时间)的，顺延时开始日期一起顺延，和截止日期相隔的天数不变，几点不变。
- 网页离线时也要当场顺延，所以算法在核心库（Rust）和网页端（TypeScript）各有一份，用同一套测试数据校验两边一致。
- AI 整理成事项时，原文明确说了周期的（“每周一开例会”“每个工作日写日报”）设上重复，说了到哪天为止的一起设上重复到，见[提示词](ai.md#提示词和结果)；没说周期的（“经常锻炼”）、只是描述情况的、事情本身只做一次的（“写个脚本每周自动备份”）不设。[整理文件夹](ai.md#整理文件夹)时用户在要求里说了才设。

### 农历

- 按紫金山天文台和香港天文台公布的历表，范围是农历 1900–2100 年（公历 1900 年 1 月 31 日到 2101 年 1 月 28 日）。表从 ICU4X 的中国历（`ChineseTraditional`，和这两家的历表一致）导出，每年一个数，记各月大小、闰几月和正月初一是哪天，存在 `crates/core/src/lunar.json`，核心库和网页端共用这一份，用同一套测试数据校验两边一致。
- 不用浏览器自带的农历（`Intl` 的 `chinese` 历）：它用天文算法近似，这个范围里有十几个月的初一差一天，如 2027 年春节算成 2 月 7 日（应为 2 月 6 日）。
- 写法：月份是正月、二月……十月、冬月、腊月，闰月前加“闰”；日子是初一到初十、十一到二十、廿一到廿九、三十。
- 用在[按农历的重复](#重复)、agent 和 AI 整理写的农历日期（`农历八月十五`，换算成今天起最近的那一天，见 [agent 接入](agent.md#引用)）和月历上：选日子的月历在每天的数字下面写农历日子，初一写月份；有[节日或节气](#节日和放假)的写它。

### 节日和放假

日历上写出节日和节气，标出国家规定的放假和补班，安排事项时一眼看到哪天过节、哪天不上班。

- 节日：公历的元旦、妇女节、劳动节、儿童节、教师节、国庆节；农历的除夕（腊月的最后一天）、春节、元宵节、端午节、七夕、中秋节、重阳节、腊八节，闰月里的不算。一天有两个的（如中秋节和国庆节）写农历的：公历节日每年在同一天，农历的每年不同，更要日历写出来。
- 节气：1900–2100 年的 24 个节气。表用 JPL 的 DE440 历表算出：太阳视黄经每到 15° 的倍数，取那时北京时间的日子。和寿星天文历的算法逐个对过，只有 3 个离午夜不到一分钟、差了一天，取 DE440 的。每年一串数字，依次是小寒到冬至在当月的几号，存在 `crates/core/src/terms.json`。清明节就是清明这个节气。
- 放假和补班：照国务院每年的《关于部分节假日安排的通知》，一个节日一条，写放假的头一天、最后一天和补班的日子，存在 `crates/core/src/holidays.json`。放假的日子包括其中的周末，普通的周末不标。从 2026 年起；下一年的安排每年 11 月前后公布，随之后的版本更新（Android 的网页部分自动更新），还没公布的年份不标。
- 农历的位置只写一样，依次取节日、节气、农历初一的月份、农历的日子。放假和补班另外标，见[界面](ui.md#日历)。
- 写在日历的月、周视图和时间轴的日期行、选中那天的标题和选日子的月历上；agent 用 [`agenda`](agent.md#工具) 看到。[每个法定工作日](#重复)的重复也按这张表算。
- 港澳台和海外的放假不同：设置的“外观”里可以关掉放假和补班的标记，节日和节气照常写；关掉后不再提供[每个法定工作日](#重复)的重复（见[界面](ui.md#弹窗对话框提示条)），已经设了的照常顺延。
- 核心库和网页端各算一份，读同一份表，用同一套测试数据校验两边一致。

### 附件

截图、照片、PDF 这类和事项放在一起的文件。

- 每个附件属于一个事项，或一条还没整理完的 [AI 整理](ai.md#附件)请求，有名称、类型和大小，单个不超过 20 MB，同一项里按添加的先后排列。
- 添加：详情里的“添加附件”（手机上可以拍照、选相册或文件），在详情、描述编辑框或快速添加栏里粘贴，电脑上拖进来，见[界面](ui.md#附件)。
- 名称：选的和拖进来的文件用原来的文件名。粘贴的图片，和系统起的看不出内容的名字（`image.png`、`IMG_20261117_093212.jpg`、`Screenshot_2026-11-17-09-32-12-345_com.tencent.mm.jpg` 这类只有固定前缀、数字和日期的）一样，改叫“图片 1.png”“图片 2.jpg”：同一项里下一个没用过的号，扩展名不变。只认这几种固定的写法，不去猜别的名字。名称可以改，最长 200 字，不能含 `/` 和 `\`，也不能是 `.` 或 `..`；存到电脑或手机上时，系统不允许的字符换成 `_`，太长的截短。
- 引用：描述里可以引用附件，写成 Markdown 链接 `[名称](attachment:<附件 ID>)`，名称里的 `[`、`]`、`\` 前面加 `\`。预览时它是一个小标签：图标加附件现在的名称（改了名也跟着变），点开就是这个附件。只认这个事项自己的附件：附件已删除，或者 ID 是别处的，标签变灰，写引用里的名称。在描述编辑框里粘贴或拖进文件，加为附件的同时在光标处插入引用；附件的菜单里也有“在描述中引用”。
- 删除附件可以撤销，撤销的不必是上传的人；删除事项、文件夹或 AI 整理请求时，它们的附件一起删除，撤销时一起回来。谁看得到事项，谁就看得到它的附件：事项移进、移出共享的文件夹时附件跟着走，新看到的人收到它，看不到了的人那里它被删除。
- 压缩图片：上传前在设备上把 JPEG 照片重新编码（质量 0.85），长边超过 2560 像素的缩到 2560。手机照片从 3–8 MB 降到 0.5 MB 左右，拍摄地点等 EXIF 信息也随之去掉。PNG 截图和其他格式原样上传。默认压缩，管理员可以在设置里改为一律上传原图，见[设置](ui.md#设置)。
- 同步：附件的名称、类型、大小和属于哪一项，和其他数据一样走[改动](#改动)，离线时也能添加、改名和删除，可以撤销。文件本身单独上传：先存在设备上、立即显示，联网后在后台上传；上传完，加附件的改动才发给服务端，所以服务器上有的附件一定有文件。上传被服务器明确拒绝时（如超过反向代理允许的大小），这个附件和一个被拒绝的改动一样撤回，并提示原因。别的设备第一次显示时才下载，下载过的存在设备上，离线也能看。见[网页端](web.md#附件)。
- 存储：服务端把文件存在数据目录的 `files/` 里，数据库只存附件的信息，每天的快照不会把文件复制 7 份。删除的附件，文件再留 90 天（和改动记录一样），这期间撤销还找得回来。存文件只经过服务端的一个模块（`crates/server/src/files.rs`），按 ID 写入、读出和删除，以后改存到 S3 这类对象存储只换这一层。
- AI 整理可以把图片一起发给能识别图片的模型，见 [AI 整理](ai.md#附件)。

### 排序

- 文件夹内：待办事项按依赖拓扑排序，没有先后约束的事项之间按手动顺序排。先后约束也算经过文件夹外未完成事项的间接依赖（A → 外面的 X → B，A 仍排在 B 前面）；中间的事项已经完成时，这条路径不再约束。已完成的折叠在底部，最近完成的在前；设置里可以让最近完成的几项划掉后留在原处，不折叠（默认不留，见[设置](ui.md#设置)）。
- 手动拖动排序只能在不违反依赖的范围内移动，越界时弹回并提示原因。
- “接下来”：只列“可做”的事项。有[要赶的截止](#后续的截止)的（自己的截止，或者后续更早的截止）按时间从早到晚排在前面（只有日期的算当天最晚），其余按所在文件夹的顺序和手动顺序排。文件夹的顺序是从根目录开始把文件夹树从上往下展开，父文件夹在子文件夹前面；共享给我的文件夹排在自己的后面，按“共享给我”一组的顺序。

### 共享

几个人分工做一个项目：把一个文件夹共享给同一台服务器上的其他账号，里面的事项、子文件夹和依赖大家都能看、能改，各人的“接下来”只列自己要做的。

- **共享什么**：一个文件夹，连同里面的子文件夹、事项和依赖。根目录不能共享；共享的文件夹里不能再有共享的文件夹，也不能放进别的共享的文件夹。
- **和谁**：同一台服务器上的账号。共享人（这个文件夹的主人）在共享面板里输入对方的用户名添加，立即生效，不用对方同意；成员随时可以退出。同一个人共享出去的文件夹不能重名，成员那里的路径（`@alice/装修`）才唯一。[本机模式](local.md)没有共享。
- **权限**：成员只有一种，和共享人一样，里面的一切都能看、能改：添加、修改、完成、删除事项和子文件夹，连依赖，设负责人。共享的文件夹本身只有共享人能改名、改颜色和图标、移动、删除和管理成员。
- **在哪里看到**：共享人那里，文件夹留在原处，换成共享的图标，标题旁是成员的头像。成员那里，它不在自己的文件夹树里，而是单独一组“共享给我”，注明是谁共享的；路径写成“Alice 的装修 / 水电”。
- **归属和编号**：共享的文件夹里的东西都属于共享人，成员在里面新建的事项也用共享人的编号。事项移进别人共享的文件夹时改属共享人、换成共享人的编号；成员把事项移出到自己的文件夹时改属这个成员，同样换编号；撤销移动时换回原来的编号。
- **负责人**：共享的文件夹里的事项可以设负责人，从共享人和成员里选，可以有多个。没设负责人的，所有成员都能做。
- **我的事项**：私人的事项，加上共享的文件夹里没设负责人、或负责人里有我的事项。“接下来”“已完成”、截止提醒、小组件、[写进系统日历](android.md#写进系统日历)和 agent 的 `next` 只看我的事项；文件夹页、关系图和搜索照常列出看得到的全部，交给别人的也在里面。
- **依赖只连在同一处**：私人的事项之间，或同一个共享的文件夹里的事项之间，免得有人看到一项在等看不到的事。事项或文件夹移进、移出共享的文件夹时，连到外面的依赖去掉，新地方的人以外的负责人也去掉（移到私人的文件夹时负责人全部去掉），提示条写明去掉了什么，撤销移动时一起恢复。第一次共享时同样去掉连到外面的依赖，共享面板里事先写明有几条。
- **成员退出或被移除**：从这个人负责的事项上去掉这个负责人；这个人提交、还没整理完的 [AI 整理](ai.md)请求改放到自己的根目录，整理这个文件夹的请求删除。这些和退出、移除是同一个改动。最后一个成员也离开时，文件夹回到私人的，负责人全部去掉。退出的人看不到这个文件夹了，不能撤销退出，要共享人重新添加。
- **删除**：共享的文件夹只有共享人能删除，删除后所有成员那里都没有了，撤销后一起回来。
- **谁改的**：别人的改动实时出现，不弹提示条，只有和我有关的两种例外：别人把我设为负责人，别人完成的事项解锁了我的事项。详情底部的来源和改动记录写明是谁改的（“Bob”“Bob 的 Claude Code”）。
- **撤销**：看得到一个批次的全部改动、也有权做这些改动，就能撤销它，别人的批次也行：Bob 的 agent 在共享的文件夹里改错了，共享人和其他成员都能撤销。添加、移除成员只有共享人能撤销。
- **离线**：离线时改的东西，联网前已经看不到了的（被移出共享，或事项被别人移走），联网后被拒绝，撤回本地效果并说明原因。
- **AI 整理**：在共享的文件夹里提交的整理请求用提交人自己的模型配置，只有提交人看得到请求，整理出的事项大家都看得到；原文说了谁负责时设上负责人，见 [AI 整理](ai.md#提示词和结果)。

### 接下来

首页。列出[我的事项](#共享)里所有“可做”的，每项显示所在文件夹路径、截止时间和[关联进度](#关联进度)，已逾期的标红。还没到[开始时间](#开始时间)的不在这里，到了自动出现。Android 小组件显示的也是这份列表。

- 按[要赶的截止](#后续的截止)分组：已逾期、今天、7 天内、以后、无截止时间，空的组不显示。组标题点一下收起，再点展开；收起时标题后面写几项。收起哪些组记在这台设备上，每个账号一份。
- 有后续的事项可以就地展开后面的一串事项，看做完它通向哪里、哪一步另有前置，见[界面](ui.md#接下来里的后续)。
- 做完的[重复](#重复)事项带着下一次的截止留在这里，不想提前看到的设[开始时间](#开始时间)，可以按截止往前数几天；第一次遇到时有提示，见[开始时间](#开始时间)。
- 可以只看某些文件夹：选一个、几个或全部（默认），选了一个文件夹就包括它的子文件夹。用来分开场景，比如电脑上只看“工作”。见[界面](ui.md#接下来的文件夹筛选)。
- 选择存在各自的设备上，和主题一样；小组件和菜单栏小窗跟着这台设备的选择。截止提醒不受影响，照常提醒所有事项。
- agent 的 `next` 用 `folders` 参数做同样的筛选，见 [agent 接入](agent.md#工具)。

### 已完成

所有文件夹里完成和[放弃](#放弃)的[我的事项](#共享)，最近结束的在前，按结束的日期分组，每项显示所在文件夹，放弃的标“已放弃”。点勾选圈就恢复成待办，不小心勾掉、又不记得在哪个文件夹的事项从这里找回；也可以[批量操作](ui.md#批量操作)，一次重新打开或删除多项。手机上从“接下来”页右上角进入，电脑上在左栏。

### 日历

按日期看事项：哪天要做什么，过去每天做了多少。手机上是底部栏的第二项，电脑上在左栏“已完成”下面。

- 上面是月历，可以切换成一周或全年：
  - 月：周一开始、固定 6 行，每天的数字下面写[农历](#农历)，或者[节日、节气](#节日和放假)，放假和补班的日子另有标记。也可以在格子里写事项的标题，看得更细，见[界面](ui.md#日历)。那天截止、还没结束的[我的事项](#共享)用小圆点表示（最多 3 个），重复事项以后的每一次也算；过去的日子按那天完成了几项涂上深浅不同的主色（热力图）。
  - 周：只显示选中那天所在的一周，格子同月历，下面的列表多出地方。
  - 年：一年 12 个月的热力图，每月一个小月历，一天一格，颜色深浅同上；点一天回到月历的那一天。
  - 时间轴：按钟点排的一周，像日程表，看一周里什么时候要交什么。有具体时间的事项画在截止的钟点，只有日期的在顶上的“全天”一行；点空白处往那个钟点添加。事项没有时长，开始时间说的是“之前不能做”，也不当成时长画。默认显示，不需要的可以在设置的“外观”里关掉。见[界面](ui.md#日历)。
- 下面是选中那天的事项：
  - 选中今天时，最前面是已逾期的：截止在今天以前、还没完成的，同[日程小组件](android.md#日程)和 `agenda`。
  - 截止在那天的：现在这一次截止在那天的照常显示，可以勾，逾期的标红；重复事项以后的某一次落在那天的写“以后的一次”，不能勾，点开是这个事项。
  - 那天完成的：普通事项按完成时间在这台设备上是哪天，重复事项按[完成记录](#重复)。做完最后一次而完成的重复事项只列一次，算在那次记录的那天。数据里分不出是做完最后一次、还是结束重复并完成的：结束重复并完成时截止日期正好有完成记录的（按完成那天算的提前完成过，下一次还是同一天截止），也算在那条记录的那天。
- 可以往选中的那天添加事项：截止就是那天，带上默认提醒。
- 完成了几项：那天列出的完成的事项和完成记录一共几项。热力图分 4 档：1 项、2–3 项、4–6 项、7 项及以上。
- 都在设备上算，离线也能看。以后的每一次按重复的规则从现在的截止日期往后推，推到看的那个月为止，设了重复到的到那天为止；“从完成那天算”的按每次都在截止那天完成来推。和[排序](#排序)一样，核心库和网页端各算一份，用同一套测试数据校验。
- Android 另有[日程小组件](android.md#日程)，列出今天起 7 天的；agent 用 [`agenda`](agent.md#工具) 看同样的内容。

### 文件夹

- 根目录和文件夹一样：有子文件夹（就是顶层的文件夹）、事项、已完成区和快速添加。手机上“文件夹”页就是根目录，总是列表，带全部事项的搜索；电脑上左栏的文件夹树以根目录为顶层。别人共享给我的文件夹在手机“文件夹”页和电脑左栏都单独一组“共享给我”。
- 先列子文件夹，再列事项。左侧用“轨道”画出事项之间的先后关系。等待中的事项显示为灰色，并标注“等 N 项”。
- 右滑完成，左滑删除或进入更多操作，长按拖动排序，或拖进别的文件夹（电脑上也能拖到左栏的文件夹树上），见[拖动](ui.md#拖动)。
- “…”菜单里的“批量操作”一次选中多项，完成、串起来（按列出的顺序连成一串）、移动或删除，一步就能撤销，见[批量操作](ui.md#批量操作)。
- 底部有快速添加栏。
- 共享的文件夹：标题旁是成员的头像，点开共享面板；有负责人的事项右侧是负责人的头像。见[界面](ui.md#共享)。

### 关系图

- 显示当前文件夹（可选包含子文件夹）里的事项和依赖。连到文件夹外的依赖显示为半透明节点，标注所在文件夹。
- 有快速添加栏，同列表：新加的事项出现在图里，闪一下，可以接着加或连线。
- 布局全自动，用 ELK 分层布局：手机上从上到下，电脑上从左到右。连线不穿过节点，交叉尽量少，链条尽量直，可做的事项排在第一层。不保存节点位置。
- 可以平移和缩放：手机上单指拖动、双指捏合，电脑上用触控板或鼠标。
- 冗余连线默认不画：已有 A→B→C 时就不画 A→C，但数据里保留。
- 已完成的事项默认隐藏，可以切换显示。
- 选中一个节点时，高亮它的全部前置链和后续链。
- 编辑：
  - 点“连线”进入连线状态，依次点前置和后续两个节点建立依赖，可以接着连下一条，点“完成”退出；点连线弹出删除确认；点节点打开详情。电脑和手机相同。

### 详情

标题、完成勾选、所在文件夹（点了移动，旁边的按钮跳到那个文件夹，见[在文件夹中显示](ui.md#交互细节)）、负责人（共享的文件夹里）、截止时间（含提醒和重复；没完成的后面写还有多久或逾期多久，见[界面](ui.md#弹窗对话框提示条)）、重复的事项完成过几次、“跳过这一次”和“结束重复并完成”、[放弃](#放弃)、描述（编辑和预览切换）、[附件](#附件)、前置和后续列表（可以搜索添加、单独移除），底部显示创建和最后修改的来源（本人、别的成员，或谁的哪个令牌）。

点标题就地编辑，光标落在点的位置（用键盘打开的在末尾）；回车或点别处保存，Esc 放弃。正在编辑时关掉详情（下拉、返回键、换成别的事项），标题和描述也会保存。

编辑标题或描述时，它在别处（agent、另一台设备）被改了的话，保存时弹窗说明谁改的、显示对方的版本，让用户选“保留对方的”或“用我的覆盖”。关掉弹窗按覆盖处理：覆盖后提示条上可以撤销，放弃的修改却找不回来。

### 搜索

按标题和描述搜索看得到的全部事项（包括共享给我的文件夹里的），结果显示文件夹路径。

### 设置

单独的页面，按管的是什么分类别，每类一个子页：账号（本机模式下是备份和恢复）、改动记录、[隐私锁](#隐私锁)（网页和桌面）、外观、列表和添加、提醒、小组件（Android）、系统（Android 和桌面）、AI 整理、agent 接入（令牌和命令行）、服务器（仅管理员：升级、邀请注册、附件；本机模式下只有附件）、关于。见[界面](ui.md#设置)。

### 隐私锁

公司的电脑有时别人会用：离开一会儿，坐过来的人不该看到我的事项；回来时解锁要快。

- 网页和桌面 App 上有，本机模式也有；手机有系统的锁屏，不做。在设置“隐私锁”里打开：设 4 到 6 位数字的 PIN，同时得到一个恢复码。只在这台设备上生效（网页是这个浏览器），不同步。
- **什么时候锁**：这台设备上的 NextTodo（网页的所有标签页，桌面的主窗口和菜单栏小窗）闲置到设定的时间就锁定，可选 1、5、15、30 分钟，默认 5 分钟。闲置是这么久没有在它上面按键、移动或点按鼠标、触摸，窗口在后台、电脑睡着了都算。所以关掉页面或 App 隔久了再打开，也是锁着的。也可以立即锁定：设置里的“立即锁定”，桌面 App 的菜单栏或托盘图标菜单里的“锁定”。
- **锁定时**：所有窗口和标签页只显示锁屏，刷新也不解开。正在编辑的标题和描述先保存。同步和提醒照常，提醒和每日汇总的通知只写“有事项到期”，同[隐藏通知内容](#提醒)。没登录时没有锁：登录页上没有事项，登录后也不再要 PIN。
- **解锁**：输入 PIN，所有窗口和标签页一起解锁。连错 5 次以后不能再输 PIN，要用恢复码，连服务器时也可以用账号密码；忘了 PIN 也这样解锁，解锁后要设一个新的 PIN。恢复码只在生成时显示一次，设置里可以换一个新的，旧的随即失效。两样都没有了的，按官网的[隐私锁](https://juniexd.github.io/NextTodo/guide/basics#lock)清掉这台设备上的网页数据，锁就去掉了：已经同步到服务器、写进本机模式服务端的数据不受影响，还没同步的改动和快速添加的草稿会一起清掉，官网写明了先联网同步。
- 这是防止别人看见，不是加密：数据还在这台设备上，懂行的人能绕过它。设置里写明这一点。
- PIN 和恢复码只存[慢哈希](#哈希用途)：很多人的 PIN 和银行卡的一样，存原文的话，翻看浏览器存储的人就看到了。
- 网页[经 HTTP 打开](web.md#经-http-打开)时没有隐私锁：算哈希的浏览器接口只在安全上下文（HTTPS 和 `localhost`）里有。

## agent 接入

所有入口都走同一条改动管线（见[同步](#同步)），agent 做的改动会实时出现在所有设备上。

### 令牌

在设置里生成，自己起名（如“Claude Code”），分只读和读写两种。令牌只在生成时显示一次，同时给出填好服务器地址和令牌的接入写法，点一下就复制：Claude Code 和 Codex 的 MCP 配置、命令行的环境变量（macOS、Linux 和 Windows 两种写法），以及安装 skill 的命令。改动记录里用令牌名标明来源。

### 命令行、MCP 和工具接口

服务端实现一组工具（查询树、列表、接下来、详情、搜索、关系图、改动记录、读附件，增删改事项和文件夹，加减依赖和附件，批量应用，撤销），命令行 `nexttodo`、MCP 端点 `/mcp` 和 HTTP 工具接口调用的是同一份实现，参数、行为和输出一致。命令行是 Rust 写的单文件二进制，只负责收发，启动只需几毫秒。默认输出简洁的中文文本，加 `--json` 输出结构化数据。

批量应用的输入是一份计划：新事项用临时的 `ref` 互相引用，已有事项用编号引用，全部成功或全部不生效，可以先预览：

```yaml
folder: /工作/网站改版
tasks:
  - ref: design
    title: 出设计稿
    due: 2026-11-20 18:00
  - ref: api
    title: 写接口
  - title: 联调
    after: [design, api, 42]
```

工具清单、参数、输出格式和各客户端的配置见 [agent 接入](agent.md)。

### Skill

仓库里的 `skills/nexttodo/` 告诉 agent 下面这些。命令行带着同一版本的一份，`nexttodo skill install` 装到 Claude Code、Codex 等 agent 的 skill 目录；只接 MCP 的 agent 在连接时收到它的要点。

- 什么时候用 NextTodo、用命令行还是 MCP；
- 怎么把一个目标拆成有依赖的事项：标题写成动作，描述写清完成标准，只连真正的先后关系；
- 批量改动前先预览给用户看；
- 回答“现在该做什么”时用 `next`。

### 改动记录和撤销

- 每个改动都记录来源：谁改的，在哪台设备上，或用的哪个令牌。
- 每次操作是一个批次，一次批量应用也只算一个批次。自己的令牌做的批次，界面上提示“Claude Code 添加了 12 项”，旁边附撤销按钮；别人的改动见[共享](#共享)。命令行和 MCP 用 `log` 查看、`undo <批次>` 撤销。
- 设置里的“改动记录”列出看得到的全部批次（同 `log`，改动日志保留 90 天），新的在前，按天分组，每条写谁、几点、改了什么，可以撤销；已经撤销了的标“已撤销”，不能再撤销：一个改动和撤销它的、撤销这些撤销的连成一串，每次撤销都把这一串翻过来，和最新的一次方向相反的就是已撤销。比如撤销了一次撤销，原来的改动就不再是已撤销；接着又撤销原来的改动，那次撤销的撤销也成了已撤销。一次撤销好几个批次、或者撤销的同时还改了别的（只有直接调 API 才会这样），不连进这一串：它自己没被撤销时，它撤销的那几个算已撤销。按批次判断，不逐项核对：中间另有改动动过其中一部分东西时，可能把还能撤销的标成已撤销。可以只看删除了事项、文件夹或附件的，用来找回误删的东西，所以不另做回收站。本机模式和手机上都有；连服务器时要联网才看得到。
- 撤销会生成一组反向改动，作为新批次写入，本身也能再撤销。只改回那次改动过的字段，之后别的改动保留；截止时间分成日期、时间和提醒、重复三部分，各自判断。撤销新建的文件夹（包括复制出来的）时，那次建的事项和文件夹照常删掉；之后又放进去的东西保留，装着它们的文件夹也保留。那次把一个文件夹删掉、改名或移走，又在原处建了同名的（或用了它的 ID），之后又往新的里放了东西时，旧的回不来，撤销失败，什么也不改，先把那些东西移走再撤销。
- 撤销改了完成次数的批次（重复的事项完成一次，或撤销这样一次），要求它仍是算数的最后一次：把这之后改过这个事项完成次数的批次按先后过一遍，正好把还算数的最后一次改回去的（撤销），两个都不再算数，其余的算数；过完只剩它，而且事项现在的次数和它改成的一样，才能撤销。所以完成两次以后可以从近到远一次次撤销；之后又完成过的（比如离线的设备撤销时，别的设备已经又完成了一次），或者撤销后同一天又完成、次数和日期都和原来一样的，改回次数会把那些一起抹掉，拒绝并提示“在这之后又完成或撤销过，请先撤销后来的那次”。同一批里排在撤销前面的操作也算。一个批次完成同一事项不止一次的（比如一次补记两天），撤销时从最后一次往前逐次判断，批次里排在后面的那几次也算在“这之后”，所以整批能一起撤销。服务端查这个批次之后的记录，页面查它知道的；两边按 `fixtures/undo-done.json` 校验。

## 账号

- 用户名加密码登录，密码用 Argon2id 存储。
- 第一个管理员在服务器上用命令行创建。其他人注册需要邀请码，邀请码由管理员生成，每个只能用一次。
- 登录后每台设备得到一个会话令牌：网页存在 HttpOnly Cookie 里，App 存在 App 私有的存储里（Android 是 SharedPreferences，小组件也要读；iOS 是 UserDefaults；桌面 App 是 WebView 的 `localStorage`），没有另外加密。设置里可以看到并注销各设备。
- 每个用户只能读写自己的数据和共享给自己的文件夹。所有表都带 `owner_id`，另有一张成员表记录谁是哪个共享的文件夹的成员；服务端在每个查询上按“自己的，加上自己是成员的文件夹里的”过滤。现有数据不用改。

## 同步

### 原则

服务端是唯一的权威数据源。客户端在本地保存一份完整副本，所有操作先在本地生效，再在后台同步。本机模式[借网盘同步](local.md#借网盘同步)时，先后由网盘里编号连续的改动排定，各设备上的服务端按这个顺序写入。

### 改动

- 客户端的每个操作是一个“改动”：带客户端生成的唯一 ID（UUIDv7），内容是操作类型和参数，比如新建事项、修改字段、移动、加依赖。新建的实体也由客户端生成 UUIDv7 作为 ID，离线时就能互相引用。
- 修改只发送改了的字段。服务端按收到的顺序应用，同一字段以后到的为准。离线时改的字段联网后同样以后到的为准，会盖过期间别处对同一字段的修改；盖掉的值留在改动记录里，可以用命令行或 agent 的 `log`、`undo` 找回。在线时的同时修改见[详情](#详情)和 [agent 接入](agent.md#同时修改)。
- 服务端在事务里应用每个改动：校验，写入数据，追加到改动日志，然后确认或拒绝。改动 ID 重复时直接返回原来的结果，所以断线重发不会重复生效。
- 改动日志有全局递增的序号，记录实体在改动前后的值，用于增量同步和撤销。日志保留 90 天。

### 连接

- 客户端和服务端保持一条 WebSocket 连接，改动的提交、确认、拒绝和推送都走这一条连接。
- 建立连接时，客户端报告自己已有的最新序号，服务端补发之后的改动；超出保留期就让客户端重新下载完整数据。
- 服务端应用一个改动后，推送给看得到它的每个用户的所有连接，HTTP API 和 MCP 的改动也一样。
- 改动只发给看得到的人：写入时记下这个改动发给谁、各人看到的是什么样子。事项移出共享的文件夹时，留下的成员看到的是它被删除，移进来时看到的是新建。
- 加入、退出或被移出共享的人，设备重新下载一次完整数据。

### 离线

- 没网时，改动存在本地的待发队列（IndexedDB），界面照常更新。联网后按顺序重发。
- 本地看到的状态 = 服务端最新数据 + 待发队列里的改动。服务端确认后从队列移除。
- 被拒绝的改动（如离线时连出的依赖在服务端成环）会撤回本地效果，并告诉用户哪一项、为什么没有生效。

### 传输

- WebSocket 上只传小的增量，不压缩；完整数据走 HTTP，用 brotli 或 zstd 压缩。数据格式用 JSON。
- App 的前端资源打包在安装包里；网页版通过 PWA 缓存资源。之后打开只同步数据。

## 技术栈

| 部分 | 选型 |
|---|---|
| 核心库 `crates/core` | Rust：数据模型、依赖图算法（判环、拓扑排序、派生状态） |
| 服务端 `crates/server` | Rust：axum、tokio、rusqlite（SQLite，WAL 模式）、rmcp（MCP）、argon2 |
| 命令行 `crates/cli` | Rust：clap、ureq（HTTP）、serde-saphyr（读 YAML 计划）、chrono（本机的日期，完成重复的事项时用） |
| Android 本机模式 `crates/android` | Rust：jni，把服务端编译成 App 里的动态库，见[本机模式](local.md#android) |
| iOS 本机模式 `crates/ios` | Rust：把服务端编译成静态库链接进 App，经 C 接口调用，见 [iOS](ios.md#本机模式) |
| 前端 `apps/web` | React、Vite、TypeScript、Tailwind CSS、Radix、React Flow + elkjs、react-markdown + remark-gfm、vite-plugin-pwa、Lucide（图标）；动效用 CSS 动画 |
| Android `apps/android` | Capacitor，小组件用 Kotlin + Jetpack Glance |
| iOS `apps/ios` | Capacitor，原生部分用 Swift |
| 桌面 `apps/desktop` | Tauri 2（macOS、Windows） |
| 官网 `apps/site` | VitePress，发布到 GitHub Pages，见[官网](deploy.md#官网) |
| 类型共享 | ts-rs 从 Rust 类型生成 TypeScript 类型 |

- 前端离线时需要自己计算派生状态和排序，所以这部分算法在 TypeScript 里也实现一份，和 Rust 版用同一套测试数据校验。
- Rust 部分是一个 Cargo workspace，Tauri 的 `src-tauri` 单独一个（免得 `cargo test` 每次都编译 Tauri）；前端部分是一个 pnpm workspace。

### 哈希用途

只用在这几处：密码用 Argon2id；令牌在数据库里存 SHA-256；前端构建产物的文件名带内容哈希（Vite 默认行为，用于长期缓存）；在设置里升级服务端时，按 SHA-256 摘要校验下载的镜像清单和镜像层（OCI 镜像的标准做法，`docker pull` 也这样校验）；[借网盘同步](local.md#借网盘同步)用 S3 时，请求按 S3 的规定签名（AWS 签名第 4 版，HMAC-SHA256）；[隐私锁](#隐私锁)的 PIN 和恢复码在本机只存 PBKDF2-HMAC-SHA256 的结果（60 万次，每台设备一个随机的盐，用浏览器的 Web Crypto）。

## 部署

- 服务端是一个进程、一个端口：同时提供 API、WebSocket、MCP 和网页静态文件。静态文件在构建时预先压缩好，放在镜像里，见[网页端](web.md#部署)。
- 自己部署：用 GHCR 上的镜像 `ghcr.io/juniexd/nexttodo`（amd64 和 arm64），`docker compose` 启动，数据在挂载的 `data/` 里；前面一般放一个提供 HTTPS 的反向代理，也可以[直接用 HTTP](#直接用-http)。步骤见[部署](deploy.md)。
- 升级由管理员发起，数据库在新版本启动时自动迁移。为了让管理员知道有新版本，管理员登录的网页和 App 在设置“服务器”里显示服务器的版本（服务器上 `/app/desktop.json` 的 `version`），并向 GitHub 查最新的 Release（`api.github.com`，打开时和之后每天最多一次，进设置“服务器”时不论多久前查过都再查一次，请求里没有用户数据）。已是最新时这一行写“已是最新版本，3 分钟前检查”，查过的结果过时了也看得出来；有新版本时写“可升级到 0.1.N”，旁边是“升级”按钮；同一个新版本在打开时用提示条提醒一次（“服务器可升级到 0.1.N”，附“查看”打开设置“服务器”）。查不到时只在这一行写“无法查询最新版本”。普通用户和本机模式不查。
- 点“升级”并确认（“升级到 0.1.N？服务器将下载约 45 MB，更新时各设备断开几秒；新版本无法启动时自动回退。”）后，服务端自己从 GHCR 下载新版本、换上，起不来时连同数据库一起退回，不经过 Docker，见[部署](deploy.md#在设置里升级)。这一行显示进度：正在下载（百分比）、正在重启，换上后写“已升级到 0.1.N”，网页端随后自动刷新，App 立即检查自己的更新；失败时写明原因，附官网上用命令升级的方法，可以重试。不能这样升级的服务端（开发版、加上这个功能以前的版本），这一行没有按钮，照旧附升级方法的链接。也可以照旧在服务器上用 `docker compose` 换镜像。
- 镜像基于 `scratch`，里面只有静态链接的 Linux 服务端和网页文件（含 [App 更新](#app-更新)），容器以 65534 用户运行，只监听容器里的 8080。镜像在 Mac 上用 `cargo-zigbuild` 交叉编译后打包，服务器上不编译。
- 镜像里没有可写的临时目录，在设置里升级时新版本又跑在旧镜像里，所以各端自带的 SQLite 编译时就把临时数据（语句日志、临时表和索引、排序）放在内存里（`.cargo/config.toml` 的 `SQLITE_TEMP_STORE=3`）；数据库、WAL 和备份照常写在数据目录。代价是改写整张表的迁移和恢复，内存峰值接近被改写的数据量。
- 反向代理要开启 WebSocket，并把原来的 `Host` 传过去（或设 `X-Forwarded-Host`），网页的同步连接靠它确认是同源页面。
- 服务端启动时和之后每天用 `VACUUM INTO` 做一次数据库快照，放在 `data/snapshots/snapshot-<Unix 秒>.db`，保留最近 7 份。[附件](#附件)的文件不在快照里，在 `data/files/`，备份时要一起复制。恢复时停掉服务，用服务端的 `restore` 命令换上快照再启动，设备随后重新下载全部数据，见[部署](deploy.md#备份和恢复)。
- 发布：`deploy/build.sh` 构建镜像内容和各端安装包，`deploy/release.sh` 把镜像推到 GHCR、安装包传到 GitHub Releases；`deploy/deploy.sh` 经 ssh 部署到自己的服务器，换版本失败时自动换回上一个。签名密钥从环境变量读取，不进仓库。见[部署](deploy.md#构建发布)。

### 直接用 HTTP

服务端本身只用 HTTP，HTTPS 由反向代理提供。没有证书时（比如只在家里的局域网里用），也可以直接用 HTTP 连它的端口。网页和各个 App 都支持，包括同步、附件和 App 更新，配置见[部署](deploy.md#直接用-http)。

代价是明文传输：途中的人看得到密码、令牌和所有数据，也改得了，包括 Android 热更新的网页部分。APK 和桌面更新包有签名，改不了。所以经公网访问时仍建议用 HTTPS。

- **不写协议的地址**：App 登录页的服务器地址不写协议时，本机和局域网的地址按 `http://`，其余按 `https://`。算本机和局域网的有：
  - 名字：`localhost`、不带点的（如 `nas`），以及 `.local`、`.lan`、`.internal`、`.home.arpa` 结尾的；
  - IPv4：回环 `127/8`、内网 `10/8`、`172.16/12`、`192.168/16`、链路本地 `169.254/16`，以及 Tailscale 这类组网用的 `100.64/10`；
  - IPv6：`::1`、`fc00::/7`、`fe80::/10`。

  不先试 `https://`、失败了再换 `http://`：那样公网上有人挡住 HTTPS 时，App 会悄悄改用明文。写了 `http://` 的照写的连，公网地址也一样。
- **网页**：经 HTTP 打开时不是安全上下文，有几处不同，见[网页端](web.md#经-http-打开)。
- **Android**：
  - 网络安全配置允许明文。
  - 页面来自 `https://localhost`，同步的 `ws://` 和附件的 `http://` 都算混合内容，所以 WebView 允许混合内容（Capacitor 的 `allowMixedContent`）。
- **iOS**：
  - App Transport Security 允许任意地址（`NSAllowsArbitraryLoads`）。
  - 连局域网的地址时，系统会请用户允许访问本地网络（`NSLocalNetworkUsageDescription`）。
- **桌面**：
  - HTTP 插件本来就能发往任意 `http(s)://` 地址。
  - 更新插件允许 `http` 的更新地址（`dangerousInsecureTransportProtocol`），更新包照样校验签名。
  - Windows 的页面本身就是 `http://tauri.localhost`，没有混合内容的问题。
- macOS 和 iOS 的页面（`tauri://localhost`、`capacitor://localhost`）是安全上下文，但 WebKit 不拦它们连局域网的 `ws://` 和 `http://`。2026-11-22 用 macOS 上的 WKWebView 实测过。

## App 更新

各个 App 都从自己登录的服务器拿更新，不经应用商店，所以 App 的版本总是跟着服务端走。更新文件打包在服务端镜像里，放在网页静态文件的 `/app/` 下，服务端不加接口；文件里的下载地址都是相对路径，同一个镜像部署在哪个域名下都能用。

| | 网页部分 | 原生部分 |
|---|---|---|
| Android | 热更新：只下载变了的文件，下次打开 App 生效，新版本打不开就退回 | 下载新 APK，由系统弹出安装确认 |
| 桌面 | 网页打包在 App 里，随整包更新 | Tauri 官方更新插件：后台下载整个新版本、校验签名，重启生效 |
| iOS | 网页打包在 App 里，随整包更新 | App 不能自己安装：提示有新版本，在 SideStore 里更新 |

- 平时的改动几乎都在网页部分，连服务器的 Android 只在原生部分（`apps/android`、Capacitor 配置和插件）改了时才要装新 APK；本机模式的网页部分和服务端都在安装包里，每次发布都要装，见[本机模式](local.md#更新)。桌面 App 每次发布都是整包，几 MB。
- 只从登录的服务器下载（[直接用 HTTP](#直接用-http) 时经 HTTP），和网页端一样信任这台服务器。APK 由系统校验签名，必须和已装的一致；桌面更新包用单独的更新密钥签名，App 里带着公钥校验。
- 每次构建除了服务端，还构建 Android 正式包和桌面更新包，连同版本说明一起放进镜像的 `/app/`。细节见 [Android](android.md#更新) 和[桌面 App](desktop.md#更新)。
- 本机模式没有服务器，从 GitHub Releases 取更新，见[本机模式](local.md#更新)。iOS 总是从 GitHub 取：服务器上没有 iOS 的安装包，见 [iOS](ios.md#更新)。
- **App 比服务器新**：iOS 从 GitHub 更新，各端的安装包也可能是从官网直接下载的，所以 App 可能比登录的服务器新。新版本发出的改动，旧服务器可能不认，保存失败。所以不是管理员的用户，在连服务器的 App 上（网页就是服务器给的，不会比它新；本机模式没有这回事）也读服务器的版本：打开时和之后每天最多一次，进设置“关于”时不论多久前查过都再查一次，但不问 GitHub；网页部分（Android 是热更新后的）比它新时，用提示条说一次“服务器的版本比 App 旧，部分改动可能无法保存，请联系管理员升级服务器”，同一台服务器的同一个版本只说一次；设置“关于”里多一行“服务器版本”，下面写“比 App 旧，请联系管理员升级服务器”。管理员不另说：他们已经会收到“服务器可升级”的提醒。
- 设置页“关于”只显示一个版本号：正在用的这一份的版本，写法和服务器、Release 一样，是 `0.1.<提交数>`。浏览器里叫“网页版本”，App 里叫“App 版本”。Android 的网页部分单独热更新，常常比安装包新，两者不同时“App 版本”下面另写一行“安装包 0.1.<提交数>”；桌面 App、iOS App 和本机模式的网页就在安装包里，版本总是相同，不另列。
- 自动检查失败时不打扰，下次照常再查。设置页“关于”里点按“App 版本”一行，立即检查一次，不受检查间隔限制；这一行下面显示检查的结果：正在检查、已是最新版本（附上次检查的时间）、新版本已下载（Android 的网页部分，下次打开时生效），或者失败的原因：
  - 连不上服务器或 GitHub：“无法连接服务器（或 GitHub），请检查网络后重试”；
  - 服务器上暂时没有可用的更新文件，或下载期间换了版本：“暂时无法获取新版本，请稍后重试”；
  - 新版本下载了却装不上：“新版本无法安装，请从官网下载最新版本”。
  原生部分只报这三类之一（桌面的 `Failure`，Android 插件拒绝时的 `code`），具体的错误记进日志。

### 更新日志

更新以后第一次打开时，弹窗告诉用户这次更新了什么：从这台设备上次用的版本到现在，中间每个发布的版本都列出来。

- 内容写在仓库根目录的 `CHANGELOG.md`：每个发布的版本一节，标题是版本号和日期（`## 0.1.212 · 2026-11-15`），新的在前；下面分新功能、改进、修复（`###`），每条都在其中一组下面，是一句纯文字（不用 Markdown）的短话，写用户看得到的变化，只说变了什么，不展开用法和细节，不写内部的重构，也不写下载和升级服务器的方法。写法简洁、正式、不口语化，用户一眼看得懂：直接说变化，不写套话；新功能写“新增……”“支持……”，修复写“修复……的问题”。发布前写好这一节、提交，再构建：网页端把整个文件打包进去，`deploy/release.sh` 取最上面一节作为 GitHub Release 的说明，它的版本号不是这次要发布的版本时不发布。
- 弹窗做在网页端，网页、Android、iOS、桌面 App 和本机模式都一样。网页部分的版本比这台设备记下的新时，主界面出来后弹一次，列出两者之间（不含记下的，含现在的）每个版本的内容；这之间没有发布过的版本（比如自己部署的两次发布之间的提交）就不弹。用户关掉弹窗时，或者不用弹时，记下现在的版本；记下的只往新里改，退回旧版本（如 Android 的网页部分新版本打不开时）不改。
- 没有记录时，这次打开前在这台设备上登录过的，是从不记版本的 0.1.201 或更早的版本升级上来的，当作记下的是 0.1.201；没登录过的是第一次打开，不弹，只记下。开发版（版本是 `package.json` 的 0.1.0）不弹也不记。从外面打开（小组件的快速添加，点提醒、小组件或菜单栏小窗里的事项）时这次不弹，下次回到 App 时再弹，不等 App 下次启动（Android 上 App 常常一直在后台）；弹窗开着时从外面打开，它让开，同样下次回到 App 时再弹。
- 记录存在设备上，不经服务器：每台设备各弹一次。
- 弹窗标题“已更新到 0.1.212”，下面一行次要文字“自 0.1.201 以来的更新”，跨了几个版本时接着写“· 3 个版本”。各版本的内容合在一起，按新功能、改进、修复分组，组名后面写条数，组内新的版本在前；跨了几个版本时，每条后面用次要文字标出它是哪个版本的。最多列 10 个版本，多于 10 个时第一行写“· 12 个版本，列出最新 10 个”，最后是“还有 2 个更早的版本”，点了在原处接着列出。底部固定一个“知道了”，不随内容滚动。
- 设置“关于”里有“更新日志”一行，弹出全部版本的内容，新的在前，每个版本一节，节标题是版本号和日期，节内同样按新功能、改进、修复分组。
- 这两个弹窗在电脑上比别的弹窗宽，随窗口在 440 到 640 之间变化。

## 性能目标

- 打开 App 到看到数据：不超过 300ms（从本地副本读取）。
- 本地操作到界面更新：一帧之内。
- 服务端常驻内存：不超过 30MB。

## 不做

标签、优先级、看板、甘特图、按小时排的日程、评论、子任务（用依赖和描述里的清单代替）。附件不做视频播放、断点续传、在线编辑和每个用户的空间上限。共享只到文件夹为止：不做 @提醒、只读成员、按人分别设权限、跨服务器共享和公开链接。第一版不做网页提醒、桌面小组件和 Linux 桌面 App（Linux 上用网页端）；iOS 和鸿蒙版见 README 的[未来计划](../README.md#未来计划)。
