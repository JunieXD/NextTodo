# Android

Android App（包括小米澎湃 OS）：Capacitor 外壳加载打包在安装包里的网页端，加上截止提醒和桌面小组件。总体要求见[总体设计](design.md#android包括小米澎湃-os)，网页端见[网页端](web.md)。

## 结构

| 位置 | 内容 |
|---|---|
| `apps/web/capacitor.config.ts` | Capacitor 配置。网页端的代码和依赖只有一份，App 用的插件也装在 `apps/web` |
| `apps/android` | 原生工程（Capacitor 的 `android.path` 指到这里）：外壳、小组件（Kotlin + Jetpack Glance）、给网页调用的小插件 |
| `crates/android` | 本机模式的服务端，编译成动态库打进 APK，见[本机模式](local.md#android) |

网页端用 `Capacitor.isNativePlatform()` 区分自己是在浏览器里还是在 App 里，只有连接服务器的方式和下面几项 App 专有的功能不同，界面完全一样。

## 连接服务器

也可以不连服务器，在本机使用，见[本机模式](local.md)。

App 的页面来自 `https://localhost`，和服务器不同源，所以不用 Cookie：

- 登录页多一个“服务器地址”栏，第一次登录时填写，不写协议时按 `https://`。
- 登录得到的会话令牌和服务器地址存在 Capacitor Preferences（Android 的 SharedPreferences，App 私有）；小组件从同一处读取。App 不参加系统备份（`allowBackup="false"`），令牌不会进云端备份。
- HTTP 请求加 `Authorization: Bearer <令牌>`，经 Capacitor 的原生 HTTP 发出（`CapacitorHttp`），不受跨域限制，服务端不需要 CORS。Capacitor 不给 POST 等写请求转发 `AbortSignal`，所以网页端请求的 20 秒期限在 App 里只对 GET 有效，登录、注销等写请求要等系统的网络超时。
- WebSocket 在 `hello` 里带令牌（见 [API](api.md#同步协议)）。
- 设备名是“NextTodo App · Android”。
- 退出登录时先删令牌，再清小组件、取消所有提醒（包括通知栏里已经弹出的）、删本机数据；服务器地址保留，下次登录不用再填。下次启动发现没有令牌时，先清掉小组件和提醒；有没做完的退出（“正在退出”的记录）就接着删本机数据，否则是登录失效（比如小组件先收到 401 删了令牌），本机数据和待发改动留着，同一账号再登录时补发。退出记录写下后、令牌删掉前被杀掉的，下次启动补完退出时也删令牌、清小组件和提醒。
- 退出时连不上服务器的，令牌照样删掉，服务端的这次登录留着，可以在别的设备的设置里“已登录的设备”注销（网页端会在下次打开时补上注销，App 删了令牌就补不了）。
- 登录失效（服务端不再接受令牌）时，和网页端一样保留本机数据和待发改动，同一账号再登录时补发；令牌、小组件和提醒照样清掉。打开 App 时才发现的（本机没有数据，问服务端得到 401）也一样。
- 登录页改了服务器地址时，内存里之前登录留下的令牌作废，不会发给新的服务器。
- 服务端告诉小组件会话已失效（401）时，如果期间没有重新登录，小组件删掉令牌，显示“打开 NextTodo 登录”；已经重新登录的，旧会话的 401 什么也不改。
- 邀请链接用服务器地址（App 里页面的来源是 `https://localhost`）。
- Capacitor 的桥接日志关掉（`loggingBehavior: "none"`），否则调试版会把登录密码和令牌写进 logcat。
- 返回键（含侧滑返回）一次退一步：先关掉对话框、弹窗、详情，再退出文件夹，最后退到后台；底部栏的页面之间不来回，见[界面](ui.md#返回)。

## 截止提醒

用 `@capacitor/local-notifications` 在本机排定提醒，到点由系统弹出，不依赖推送：

- 会话开始时、本地副本变化后（第一次变化后 2 秒内处理一次，合并这期间的变化）和 App 回到前台时，重新计算未完成事项的提醒时间：截止时间减去 `remind_before`。取将来最近的 50 个，和已排定的比较，增删差异。比较时标题、内容、时间和是否精确都要相同；时间和是否精确放在每个提醒的 `extra` 里比较（插件读回的时间是它自己的格式）。普通闹钟可能到点后才送达：已经过了时间、还没送达的提醒，只要事项仍要这个提醒就保留。
- 通知 ID 用事项编号（服务端分配的整数，每个用户唯一）。还没同步、没有编号的事项，同步后再排。
- 提醒排的是具体时刻。改了手机时区，要等 App 下次回到前台才按新时区重排。
- 通知标题是事项标题，内容是截止时间和文件夹；点开进入 App 并打开这个事项（在设置页的先回到“接下来”；小组件里点事项也一样）。
- 更新提醒或小组件失败时，提示条告诉用户，下次变化时再试。
- 精确到点需要“闹钟和提醒”权限（`SCHEDULE_EXACT_ALARM`）。第一次设置提醒时请求通知权限。没有精确闹钟权限时排普通闹钟（系统可能推迟几分钟），不弹系统设置（插件默认每次排提醒都会打开）；设置里提示并给出打开系统设置的按钮，允许后回到 App 时按精确闹钟重排。

## 小组件

Jetpack Glance 写的“接下来”小组件：

- 每项显示标题、文件夹和截止时间（逾期红色、今天琥珀色，规则同网页）；左边的圆圈点一下完成，点这一行的其他地方打开 App 里的详情；点标题回到 App 的首页；右上角 `+` 打开 App 并聚焦快速添加，刷新按钮立即刷新。
- 圆圈和打开详情的区域在结构上并列，不互相嵌套：打开详情的区域覆盖整行（连同上方的分隔线），在前；圆圈叠在它的左端，可点的范围到标题起点为止（36dp）。澎湃 OS 的桌面和原生的不同：点在一个套着另一个可点元素的元素上，执行的是里面那个元素的动作；点在不属于任何可点元素的空隙上，执行的是这一行里第一个动作。所以两个动作不能嵌套，行里也不能留空隙。
- 事项之间有淡色分隔线，从文字起点开始（小组件画不出 App 里的半像素线，用 1dp、比 outline-variant 更淡的颜色）。
- 点圆圈后这一项立刻显示为完成（实心对勾、标题划线变灰），和 App 里一样在原位停留 0.9 秒（服务端确认得更慢就等到确认），然后从列表移走，再刷新列表；完成失败时恢复原样并提示。Glance 无法做动画，用这个状态代替：正在完成的事项连同它在列表里的位置记在内存里，停留期间来了不含它的新列表，它也留在原位；App 进程被系统结束时，这个状态和正在进行的完成一起消失，不会留下一直显示完成的事项。
- 数据来源：
  - App 每次本地副本变化后，把“接下来”的列表写给小组件（经 `Widget` 插件存入 SharedPreferences 并通知刷新），格式同 `next` 工具数据里的 `tasks`，带事项编号。
  - 小组件自己每 15 分钟（WorkManager 周期任务，联网时）和点刷新按钮时，用令牌调用 `POST /tools/next` 取最新列表（`limit` 用最大的 500，和 App 写的完整列表一致）。
  - 每份列表都带着它对应的服务端改动序号（App 的是本地副本的 `seq`，服务端的是 `next` 回复里的 `seq`），和列表一起存下；比已存的旧的不写，一样新的照写。App 刚启动、或在后台被冻结后恢复时，本地副本可能还没跟上服务端，它的列表会比小组件自己取到的旧，按序号就不会把小组件改回旧内容。退出登录时写入的空列表不带序号，什么都能替换它，它也替换任何列表。
  - 取回来时令牌已经换了（退出或换了账号）的也丢掉。小组件自己对列表的改动依次进行，检查令牌、序号和写入在一起，旧会话取回的列表不会写进新会话。
- 勾选完成时直接调用 `POST /mutations`（`task.update`，`done: true`，带上手机上的当天日期 `today`，改动 ID 由小组件生成；已经在别处完成的照样算成功），成功后按列表里的事项编号、照插件的做法取消这个事项的提醒（App 可能没在运行），存下的列表早于这次完成时，把这一项连同完成的改动序号另外记下、不再显示（列表本身不改，仍是它那个序号时的样子；早于这次完成的列表写进来也照样隐藏它），直到存下的列表不早于这次完成，再刷新；期间重新登录过的不动提醒，因为编号可能已经是另一个账号的。
- [重复](design.md#重复)的事项也这样完成：显示完成、移走，刷新后带着下一次的截止时间回到列表，和 App 里一样标着“今天已完成”。旧的提醒照样取消，下一次的提醒等 App 下次运行时排上（App 在后台连着同步时当场就排）。
- 没登录时显示“打开 NextTodo 登录”。

## 更新

总体见[总体设计](design.md#app-更新)。

**版本**：原生版本是改过原生部分的提交数（`apps/android`、`apps/web/capacitor.config.ts`、`apps/web/package.json`，后者里有 Capacitor 插件的版本），写进 APK（`BuildConfig`）。`versionCode` 仍是全部提交数，只增不减；`versionName` 是 `0.1.<全部提交数>`，和同一次构建的桌面 App 一样。

**网页热更新**：

- 构建网页时生成 `app/web.json`：`{version, native, files}`。`version` 是构建它的提交，`native` 是构建时的原生版本，即这份网页要求的最低原生版本，`files` 是全部文件的路径。它随网页部署到服务器，也打进 APK。
- 打开 App、回到前台时和运行期间（每小时最多一次）请求服务器的 `/app/web.json`。版本号必须是提交号（它也是目录名），和当前不同、原生版本够用时，在 App 私有目录 `files/web/<version>/` 准备新版本：`assets/` 下的文件名由 Vite 按内容生成，当前版本里已有的直接复制，其余从服务器下载。全部下载成功、并且再取一次 `web.json` 版本没变（下载期间服务器没换版本）才算准备好，否则下次再试。换了服务器登录时，检查重新开始。
- 下次打开 App 时生效：打开前把 Capacitor 的 `serverBasePath` 指向新目录。网页显示出第一个页面（登录页或主界面）后报告就绪（`webReady`），这时新版本才算可用，删掉更早的目录。新版本打开后 30 秒内没报告就绪的，当场退回它要替换的版本（或 APK 里的）并重新加载，不再尝试这个版本；不等下次启动，因为再点图标往往只是回到同一个界面。期间又下载好的版本等下次启动再试。
- 装了新 APK 后，Capacitor 自动改用 APK 里的网页（`isNewBinary`），之前下载的版本作废、删掉。

**原生更新**：服务器上的 `/app/android.json` 是 `{native, versionName, url}`，和网页热更新各查各的，一个失败不影响另一个。它的原生版本比已装的新时，设置页“关于”里显示“有新版本”，并在打开 App 时用提示条提醒一次；点“下载安装”把 APK 下载到缓存目录（每次一个新文件，整个 App 同时只下载一个；安装器可能还没读，本次运行下载的都留着，之前运行留下的在下次下载时删掉），交给系统安装器。第一次需要在系统设置里允许本 App“安装未知应用”（`REQUEST_INSTALL_PACKAGES`）。

设置页“关于”显示网页版本和 App 版本，点按 App 版本立即检查更新，见[总体设计](design.md#app-更新)。

## 澎湃 OS

系统会清理后台，小组件的定时刷新和提醒需要 App 被允许“自启动”、省电策略设为“无限制”。App 第一次启动时显示一张说明卡片，按钮打开本 App 的系统设置页；在设置里也能再次查看。

## 构建和签名

- 需要 Android SDK（`ANDROID_HOME`）和 JDK 21（Capacitor 8 的 Gradle 版本还不支持更新的 JDK）。
- 本机模式的动态库由 Gradle 在构建前编译（任务 `rust`，调用 `cargo ndk`），还需要 SDK 里的 NDK、`rustup target add aarch64-linux-android` 和 `cargo install cargo-ndk`。
- `pnpm android:build`（在 `apps/web` 下）：构建网页端、`cap sync android`，再用 Gradle 打 release APK。
- 正式版用自签名的密钥签名，直接安装。密钥库和密码不进仓库：路径和密码从环境变量 `NEXTTODO_KEYSTORE`、`NEXTTODO_KEYSTORE_PASSWORD` 读取。
- 版本号见[更新](#更新)。发布用的 APK 由 `deploy/build.sh` 构建，放进服务端镜像，也上传到 GitHub Releases，见[部署](deploy.md#构建发布)。

## 测试

- 网页端的逻辑（提醒时间计算、小组件列表）用 Vitest 测。
- 原生部分在模拟器上实际操作验证：登录、同步、离线修改、提醒到点弹出、小组件显示和勾选。
- 小组件的点击还要在澎湃 OS 真机上验证：桌面处理列表点击的方式和原生不同，模拟器上测不出来。真机上装测试版（调试版的包名临时加后缀，和正式版并存），用 `adb reverse` 连本机的开发服务器，不碰正式数据。
