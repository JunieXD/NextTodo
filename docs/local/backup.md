# 备份和搬迁

## 备份和恢复

备份和恢复由原生部分直接调用服务端库，不走 HTTP 接口：桌面是 Rust 命令，Android 经 JNI，iOS 经 C 接口。桌面的保存和打开对话框用 Tauri 官方的 `tauri-plugin-dialog`，由 Rust 命令打开，路径不经过页面；Android 用系统的存储访问框架，iOS 用系统的文件选择器，都经临时文件交给 Rust。

### 备份

1. 等待待发队列清空，包括正在保存的改动。被拒绝的照现有方式提示。本机服务端一直在，通常立即完成；几秒内没清空就提示稍后重试。
2. 服务端用 `VACUUM INTO` 在数据目录里生成一份数据库的副本 `backup.part`，和每日快照一样，运行中也能得到一致的副本；再和副本的 `files` 表里列出的、还没清理的附件文件（在用的，和删除后还能撤销的）一起打成一个 tar，打完删掉副本。借网盘同步时，其中本机还没有的先从网盘下载，下载不了就提示稍后重试；文件清单就取自这份副本，所以备份过程中读入的改动不会让两者对不上。tar 的第一项是 `backup.json`（`{"format": 1}`，见[格式版本](../local.md#格式版本)），然后是 `files/<附件 ID>`，最后是 `nexttodo.db`，这样在两项之间截断的备份没有数据库，恢复时认得出。附件的文件写入后不再变，不用停下服务端；这期间被每天的清理删掉的跳过，它们在副本里也早已没人用；还在用的文件不见了，备份失败。
3. 保存到用户选的位置，默认文件名 `NextTodo-备份-<日期>.tar`：先写成旁边的 `<文件名>.partial`，再改名换上，不会留下写了一半的备份。选在数据目录 `local/` 里就提示，不保存：那样可能换掉正在用的数据库。

备份里有：

- 全部数据，包括改动记录，撤销还能用。
- 附件的文件。
- API 令牌，只存哈希，恢复后重新生效。

备份里没有 AI 整理的配置：它存在页面里，所以备份里也没有 API 密钥。恢复成别的本机用户（备份来自另一台设备）后，要重新填写。

### 恢复

不需要服务端在运行，所以启动失败时也能恢复。

**准备**：选一个备份文件，放到数据目录里的临时目录 `restore.part/`（同名的旧目录先删掉）：tar 的解开：第一项必须是 `backup.json`，格式不比 App 新（新了就提示“请先更新 App”），之后只能有 `nexttodo.db` 和 `files/<附件 ID>` 这些普通文件，各一份，附件的文件不超过 20 MB，有别的就不认；以前版本的备份是单独的数据库文件，原样复制。在这份副本上检查和准备，任何一步不通过，就删掉 `restore.part/`、提示原因，什么都不改：

1. 是 SQLite 数据库，`integrity_check` 和 `foreign_key_check` 通过。
2. 迁移版本合法，不比 App 新；表结构和同一版本的空数据库完全一致。这一条认出它是 NextTodo 的数据库，以前各版本的备份和服务器数据库也认得出。所以发布过的迁移建出的表结构不能变，写在建表语句里面的注释也存在数据库里，同样不能改；`db.rs` 的测试拿 `crates/server/migrations/schema.txt` 检查这一点。
3. 正好一个用户。
4. tar 里的附件文件和数据库的 `files` 表对得上：每个都在表里，大小和记录的一样；还在用的一个不缺，没人用的可以缺（备份时正好被清理掉）。
5. 跑迁移，规范为本机用户，换一个新的数据代号。恢复的即使是这台设备自己的备份，也和现在的数据不是同一份历史。

单用户的服务器数据库也能这样恢复，相当于把自己部署的数据搬到本机；多用户的不行。这样恢复的没有附件的文件，附件打开时提示“文件不存在”。准备完关闭数据库，不留 `-wal`，把文件写入磁盘（`fsync`）。

**提交**：用户确认“会用备份替换这台设备上的全部数据”，然后：

1. 把 `restore.part/` 改名为 `restore/`，从这一刻起恢复算是提交了。改名失败就提示原因，会话照常。之后同步 `local/` 目录失败只记日志：恢复已经提交，断电最多让它作废。
2. 页面结束会话，不再发送改动。
3. App 重启，第 2 步出错也照样重启。

确认框写明两件会丢的事：

- 还没发出的改动会丢弃，找不回来；队列里有改动时写出有几项。从设置里恢复时，准备之前已等待队列清空，通常没有；启动失败时恢复，就可能有。
- 现在的数据会留在 `local/` 下的旧数据目录里；从确认到 App 重启之间，小组件、AI 整理和桌面上的 agent 写入的改动，也只在那里，不会出现在恢复后的数据中。

**完成**：新进程拿到数据目录锁之后、打开数据库之前，按目录的状态续做。每一步都是 `local/` 里的目录改名：

| 状态 | 做法 |
|---|---|
| 有 `restore.part/` | 没提交的准备，删掉 |
| 有 `restore/`，也有 `db/` | 把 `db/` 改名为 `before-restore-<Unix 秒>/`（已存在就加序号，不覆盖），连同 `-wal`、`-shm` 原样保留，不自动删除；再做下一行 |
| 有 `restore/`，没有 `db/` | 把 `restore/` 改名为 `db/` |
| 没有 `restore/` | 没有要做的 |

- 保证的是进程在任何一步被结束后都能续做。断电只尽力：macOS 和 Android 上每次改名后同步 `local/` 目录；Windows 上同步目录要用不安全的系统调用（项目禁止 `unsafe`），只靠 NTFS 自己的日志。断电后回到哪一步，按上表照样续做。
- 任何一步失败（比如文件被占用、磁盘出错）就停下：不打开数据库，也不删任何东西，按启动失败显示原因，下次启动再从当时的状态续做。

**之后**：

- 页面和 Android 原生部分看到新的[数据代号](../local.md#数据代号)，丢掉旧的本地副本、待发改动、小组件列表和提醒，从头下载。
- 恢复时还没发出的改动不会作用到恢复后的数据上：用户要的是换成备份里的数据。从设置里恢复时，准备之前会先等待队列清空，所以通常没有这样的改动。

## 搬到服务器和搬回本机

两个方向都用[备份](#备份)的文件，格式只有一种：

| 方向 | 做法 | 结果 |
|---|---|---|
| 本机 → 服务器 | 本机模式里“备份”；登录服务器后，设置的“账号”里“导入备份” | 加进这个账号，账号里原有的数据不动 |
| 服务器 → 本机 | “账号”里“导出备份”；进入本机模式后“恢复” | 换掉本机的数据，同现有的[恢复](#恢复) |

- 导出和导入是服务器账号的功能，网页、App 都有，在设置的“账号”里；App 上导出的文件用保存附件的同一套方式存。命令行是 `nexttodo export`、`nexttodo import`，见 [agent 接入](../agent.md#命令行)。MCP 没有：MCP 的客户端经网络连服务器，交不了本机的文件，agent 用命令行。
- 本机模式没有导出和导入（接口返回 404），用上面的备份和恢复。
- 也能在两个服务器、两个账号之间搬：导出的文件同样能导入。

### 导出

`GET /export`：服务端在附件目录里新建一个临时的数据库（跑完迁移的空库），写进这个用户自己的数据，再和附件的文件一起打成和[备份](#备份)一样的 tar，也是临时文件，打完再发出去。下载的文件名是 `NextTodo-<用户名>-<日期>.tar`，日期是设备上的（请求带 `today`，不带用 UTC 的）。临时文件发完或下载中断就删，服务端中途停了由附件的每日清理删掉。

- 带上：[跟着账号的设置](../ui/settings.md#跟着账号的设置)（固定的快速添加文件夹是别人共享的、没带上的，恢复后显示“已不在”）、自己的文件夹（包括共享出去的，不带成员）、其中和根目录的事项、完成记录、两端都在其中的依赖、这些文件夹里和根目录的自己的整理请求、这些事项和请求的附件和文件、这些文件夹和全局的 AI 说明。别人共享的文件夹里自己的整理请求和 AI 说明不带。
- 不带：别人共享给自己的文件夹（是共享人的数据）、负责人、令牌和会话、邀请码、同步到服务器的 AI 配置（用服务器的密钥加密，本机解不开，恢复时本来也会删掉）、改动记录（恢复后从头记，之前的撤销不了）。
- 库里只有这一个用户：共享的文件夹里成员加的、改的事项，添加人和最后修改人都写成这个用户。
- 本机的“恢复”照现有的检查和规范读它（单用户，改成本机用户），不用另写读入。

### 导入

1. 页面（或命令行）先把整个 tar 照[恢复](#恢复)的规则检查一遍，不合格的什么都不上传：第一项 `backup.json` 的格式不比自己新，后面只有普通文件 `files/<附件 ID>`（不重复）和一个 `nexttodo.db`，每项的头完整、校验和对得上、内容没有截断。再把每个 `files/<附件 ID>` 按 tar 里的先后（备份按附件 ID 排列）生成新 ID，用 `PUT /files/{新 ID}` 上传（类型 `application/octet-stream`，导入时按数据库里记的改过来），再把 `nexttodo.db` 也这样上传（类型 `application/vnd.sqlite3`）。只有数据库、没有 tar 的旧版备份同样能导入。单个文件最多 20 MB：附件本来就有这个上限；数据库带着全部改动记录，一万多条改动以内都不到 20 MB（演示数据一年 235 条改动，0.9 MB），超过时提示“备份里的数据库超过 20 MB，暂时导入不了”。
2. `POST /import`，`{id, database, files}`：`id` 是这次改动的 ID，和别的改动一样按它去重；`database` 是上传的数据库的文件 ID，`files` 是备份里的附件 ID 到上传的文件 ID 的对照。服务端在一份副本上做[恢复](#恢复)的前三项检查（是 NextTodo 的数据库、版本不比服务端新、正好一个用户），跑迁移，读出没删除的数据，在一个事务里写进这个账号，作为一个改动：
   - 全部换新 ID：按原来的先后生成 UUIDv7，先后不变；引用一起改，包括上级文件夹、所在文件夹、依赖、完成记录、附件的归属和描述里的 `attachment:` 链接。所以同一份备份导入两次就是两份；从这个账号导出、在本机用了一阵再导回来的，也不会和账号里原来的撞上，而是另加一份（原来的可以先删掉）。
   - 编号接着这个账号现有的往后排，按备份里原来编号的先后。
   - 文件夹放进根目录；同一层已有同名的，按[复制文件夹](../design.md#文件夹)的规则叫“工作 副本”。
   - 创建、完成、修改的时间原样保留；添加人和最后修改人是导入的用户。
   - 整理请求导入为失败，原因“导入的请求，重试后整理”：不自动发给这个账号配置的模型。
   - AI 说明跟着文件夹搬；全局说明只在这个账号还没有时导入，已有的不覆盖。说明不在改动里，撤销导入时留着，和删除文件夹时一样。
   - 用到的附件文件少了（没上传成功），或大小和备份里记的不一样，就整个失败，写明是哪些附件；备份里没人用的文件不导入。
   - 读入的数据照 API 收到的数据一样检查（标题、描述、日期这些值），文件夹不能互相包含，依赖不能成环，不合格就整个失败。读的时候不看共享的成员，所以这些检查之前不会顺着文件夹往下找。
   - 一次导入是一个改动，可以超过 1000 个操作；在一个事务里写完，依赖的环在进事务之前一次查完（实测 1 万个事项、1 万条依赖约 0.3 秒）。
3. 返回 `{tasks, folders, batch}`：加了几个事项、几个文件夹，和这个批次的序号。改动记录里照常写“新建 8 个文件夹；添加 120 项 …”；页面的提示条写“已导入 120 个事项、8 个文件夹”，附“撤销”，命令行输出批次号，用 `nexttodo undo` 撤销。撤销就删掉导入的全部，和撤销复制文件夹一样。
4. 上传的数据库和没导入的文件不用删：它们没加为附件，按[附件文件的清理规则](../data-model.md#files)和别的没用上的上传一样清理。导入失败时，上传的文件同样。

选好文件、检查过 tar 以后，确认框写明“备份里的文件夹和事项会加进这个账号，放在根目录，账号里原有的不动；导入后可以撤销”。导入期间“导入备份”一行显示进度（已上传几个文件），失败时提示原因。上传途中退出了登录（或换了账号）就停下，后面的文件不再上传。最后一步没收到回复时，提示条附“重试”，用同一个改动 ID 重发，不会导入两份。
