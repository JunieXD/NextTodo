# 网页端

`apps/web`：React 单页应用，也是 Android 和 macOS App 的前端。产品和界面的规格见[总体设计](design.md)和[界面](ui.md)，同步协议见 [API](api.md#同步协议)。

## 结构

| 位置 | 内容 |
|---|---|
| `src/api/` | HTTP 请求（`http.ts`）；`types/` 是从 Rust 生成的类型，不手改 |
| `src/domain/` | 派生状态和排序（`board.ts`，与 `crates/core/src/board.rs` 一致）、本地应用操作（`apply.ts`）、关系图和轨道画哪些事项和依赖（`graph.ts`）、日期显示（`dates.ts`）、文本校验（`text.ts`，与服务端规则一致） |
| `src/sync/` | 本地副本和待发队列（`store.ts`）、WebSocket 连接（`socket.ts`）、IndexedDB 持久化（`persist.ts`） |
| `src/session.tsx` | 登录状态：启动时先用本机数据，再向服务端确认；本地副本和连接的创建 |
| `src/ui/` | 通用组件：图标、勾选圈、分段控件、底部面板、弹窗和对话框、提示条、Markdown 描述 |
| `src/views/` | 页面：登录、手机和电脑两种布局、接下来、文件夹、关系图（`Graph.tsx`，布局在 `graph-layout.ts`）、搜索、详情、设置、各种选择面板 |
| `src/index.css` | 样式：原型的样式原样放在 `components` 层，Tailwind 提供基础样式和颜色工具类 |

技术选型见[总体设计](design.md#技术栈)；路由用 wouter，IndexedDB 用 idb，顺序键用 fractional-indexing，ID 用 uuid（v7）。

选中的事项写在地址的 `?t=<id>` 里：打开详情会加一条历史记录，返回键（包括 Android 的）关掉详情。

## 数据

客户端保存一份完整的本地副本，界面只读本地数据，从不等网络：

- **基线**：服务端确认过的数据（`/snapshot` 加上之后收到的所有变化）和对应的序号 `seq`。
- **待发队列**：本地提交、服务端还没确认的改动，按提交顺序排列。
- **视图** = 基线 + 依次应用待发队列里的改动。基线或队列变了就重新计算，界面始终显示视图。

本地应用操作的规则和服务端一致（`domain/apply.ts`），也产生同样格式的变化，所以本地也能立即撤销。服务端才知道的东西本地不猜：新事项的编号在同步后才有，界面先不显示编号。本地应用失败的改动（比如要改的事项已经被别的设备删了）在视图里跳过，等服务端拒绝后从队列移除并提示。

新建的文件夹和事项总是由客户端给出顺序键（排在最后时用 `generateKeyBetween(最后一个, null)`），这样本地和服务端的顺序一致。

## 同步

1. **启动**：先从 IndexedDB 读出基线和待发队列，马上显示；本地没有数据时请求 `/snapshot`。
2. **连接**：打开 WebSocket `/api/v1/sync`，发 `hello`（带基线的 `seq` 和副本所属的用户 ID）。服务端补发之后的变化，然后持续推送新的变化。
3. **收到变化**：按顺序应用到基线，更新 `seq`；变化对应的改动如果在待发队列里，就从队列移除（它的效果已经在基线里了）。
4. **提交**：本地改动加入待发队列，写进 IndexedDB 后，已连接就发 `mutate`。每次连上（含重连）后，把队列里已经写进本机的改动按顺序全部重发一遍；服务端按改动 ID 去重，重发不会重复生效。
5. **拒绝**：从队列移除，视图随之撤回本地效果，提示条说明哪一项、为什么没有生效。服务端只告诉发出它的标签页，这个标签页再广播给其他标签页：它们打开时从本机读进了同一份队列，也要去掉这一项。
6. **重新下载**：收到 `resync` 时重新请求 `/snapshot` 作为基线，待发队列保留。
7. **确认**：收到 `ack` 时，如果它的序号不超过基线的 `seq`，说明基线里已经有这项改动、它不会再作为变化到达（比如新下载的快照里已经包含了它），直接从队列移除。
8. **断线**：指数退避重连（1 秒起，最长 30 秒）；页面回到前台或网络恢复时立即重连。

本地数据每次变化后写入 IndexedDB，按用户 ID 分开存，分两张表：

- `copies`：基线、`seq` 和撤销用的最近改动，每个标签页的会话存自己的一份，互不覆盖。
- `outbox`：待发队列，所有标签页共用一份，每项改动一条记录。改动提交时加进去，写进去以后才发出；任何一个标签页收到它的变化、`ack` 或 `reject` 时删掉，和这个标签页的副本在同一个事务里写入（各标签页收到的每一项变化都要删，不管是不是自己提交的）。改动先进队列再发出，别的标签页收到它时队列里已经有它，删得掉，所以不会因为提交它的标签页没等到确认就关掉而在下次打开时重放。万一两边都有（比如写入失败过），重发时服务端按 ID 去重，`ack` 的序号不超过基线时移除（第 7 条）。

写入一次只进行一个，等着的那次带上最新的副本和这期间的所有队列变化。写入失败时提示条告诉用户，改动照常发给服务端，没写进去的内容随下一次写入补上；会话关闭时再补写一次。

打开应用时取 `seq` 最新的副本作为当前会话的副本（删掉其他的），再读出整个待发队列（按改动 ID，也就是提交先后排列）。还开着的标签页下次改动时会再存它自己的一份；它和当前标签页都会重发队列里的改动，服务端按 ID 去重，只生效一次。

每次登录有一个 ID，和登录的用户一起存在 `localStorage`，同一浏览器的标签页共用。登录 ID 取自本机的一个递增计数（也存在 `localStorage`，在锁内取号），删掉一个用户全部数据的退出也取一个号。登录和退出的广播都带着号，标签页只理会号比自己那次登录大的：退出的号比之前所有登录都大，这个用户已有的标签页都会退出；之后才建立的登录号更大，晚到的广播结束不了它。登录时删掉本机上其他用户的数据，并广播登录的用户，其他用户的标签页随即退出到登录页，同样删掉数据；同一用户还开着的标签页照常使用（Cookie 换成了新登录的，用户相同）。

- **退出登录**：先记下“正在退出”（这次登录的 ID 和用户），再请服务端注销；同一浏览器已经在另一个标签页重新登录过的不注销也不记（Cookie 已经是那次登录的了）。然后停掉连接和保存、等写入完成，删掉这个用户在本机的所有数据，登录信息还属于这个用户就删掉（放在最后），并广播“这个用户退出了”，让这个用户所有开着的标签页都退出，不管属于哪一次登录、是否还持有登录信息（比如断线中的，或者正因登录失效而退出的，这时数据照样删掉）。注销成功、数据删完才清掉“正在退出”的记录；注销没成功（断网、服务端出错或超时）或者中途标签页被关掉，下次打开应用或登录时，按记录删掉那个用户的数据和登录信息、广播，再补上注销，不会凭留下的 Cookie 或数据自动登录。期间如果已经用同一账号重新登录了（登录 ID 变了，用户相同），数据归新的登录，只删自己这个会话的副本。
- **登录失效**（服务端不再接受这次登录，比如在别的设备上退出了它）：立即回到登录页（等着收尾时改动既存不下也发不出），停掉连接和保存；登录信息还是这次登录的就删掉，已经有了新的登录则不动它。本机数据，包括还没发出的改动，都留着，同一账号再登录时接着用，改动补发；换别的账号登录时删掉，收尾时已经有别人登录的也删掉。之后这个用户在本机退出了，照样删掉。
- **换了账号**：另一个标签页换了账号时，这个标签页收到广播就退出；广播漏掉的，启动时的 `/me` 检查或下次连接的 `hello` 也会发现。

几件事用 Web Locks 加锁，各标签页依次执行：登录（连同登录请求和补完没做完的退出）；打开时读登录信息和本机数据，没有就问服务端谁登录着（`/me`）并据此登录；退出时看登录信息、决定要不要注销；结束会话时决定删哪些数据；会话对象也在锁里建立，从它读到的状态之后的每次登录和退出广播它都收得到。这样不会一边刚读到数据、另一边就把它删了，问到的登录状态在用上时也还成立；改变 Cookie 的请求也都在锁内，退出不会注销掉另一个标签页刚建立的登录，也不会在它设好 Cookie 以后再清掉。本机没有数据时，快照在锁外下载，下载完再进锁核对：期间已经退出或换了账号的，不打开。请求（包括读响应）20 秒没完成就按连不上处理，不会无限期占着锁；锁内的请求慢时，别的标签页的登录、打开和退出要等它返回，登录失效的标签页不等，立即回登录页。剩下一个很窄的空隙：结束会话的标签页在拿到锁之前还会写完最后几次保存，如果这时另一个标签页已经用同一账号登录、读走了数据，这几次保存里新加的待发改动不在它的内存里，留在队列里等下次打开时重发。

## 手动排序

文件夹列表按依赖排好后，没有先后约束的事项之间按顺序键排。拖动一行时，可移动的范围是它直接或经由未完成事项间接等待的最后一项之后、等待它的第一项之前。放下后，只要列表里顺序键沿新顺序递增，按依赖排序的结果就正好是新顺序：保留顺序键已经递增的最长子序列，只给移动的事项和其余少数事项生成新的顺序键，作为一次改动提交。

## 关系图

文件夹页面可以在列表和关系图之间切换，选择记在本机。关系图第一次打开时才加载 React Flow 和 ELK，不拖慢首屏。

- **布局**：ELK Layered 在 Web Worker 里计算，只在事项或依赖增减、节点尺寸变化时重新计算，改标题、完成状态和手动顺序不会让图跳动（给 ELK 的事项和依赖按 ID 排序，和列表顺序无关）。新布局算好之前，画面保持上一份布局的位置、尺寸和连线。参数是用几份真实计划（毕业论文、搬家、求职，以及 40 个事项的随机计划）对比后选的：
  - 分层 `LONGEST_PATH_SOURCE`，连通分量不分开排：可做的事项都在第一层，包括和其他事项无关的。
  - 节点放置 `NETWORK_SIMPLEX`：比默认的 `BRANDES_KOEPF` 更紧凑，链条更直。
  - 连线 `SPLINES` 的 `CONSERVATIVE` 模式：曲线绕开节点；`SLOPPY` 模式会斜穿空白，交叉更多。
- **平移和缩放**：React Flow 负责；单指或鼠标拖动平移，捏合或 Ctrl + 滚轮缩放，触控板双指滑动平移。第一屏按原大小显示，缩小到 0.8 倍能放下就缩小，放得下就居中，放不下从第一层开始。
- **画法**：节点和连线由应用自己画，连线直接用 ELK 算出的路径；React Flow 的连接点只是摆设，藏起来。
- React Flow 的署名链接保留在画布右上角：隐藏它需要订阅 React Flow Pro。

## 登录

网页用 HttpOnly Cookie，脚本拿不到令牌。登录和注册页面提交后服务端设置 Cookie；请求 `/me` 返回 401 时回到登录页。设备名取自浏览器和系统，如“Chrome · macOS”。

## 部署

`pnpm build` 输出到 `apps/web/dist`，并为每个文本文件生成 `.br` 和 `.gz` 预压缩版本。服务端用 `--web <目录>` 提供这些文件：

- 页面地址（最后一段没有扩展名，如 `/folders/<id>`）返回 `index.html`，由前端路由处理。
- 其他路径按文件提供，不存在就是 404；`/assets/` 下带内容哈希的资源成功返回时长期缓存，其余（含 `index.html` 和 Service Worker）每次重新检查。
- `/api`、`/mcp` 下的未知路径返回 JSON 格式的 404，不回退到网页。

开发时 `pnpm dev` 启动 Vite（5173），把 `/api` 和 `/mcp` 转发到本地服务端（8080）。

## 测试

用 Vitest：

- `board.ts` 用 `fixtures/board.json` 校验，和 Rust 版结果一致。
- `apply.ts` 和 `store.ts`：本地应用、撤销、待发队列和基线的合并、拒绝、重连重发。
- `reorder.ts`：随机生成的依赖和顺序键下，任意允许的拖动之后，排序结果正好是拖成的顺序。

界面在浏览器里实际操作验证，不写冻结样式的测试。
