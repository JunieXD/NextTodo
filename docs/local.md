# 本机模式

不部署服务器也能用：macOS、Windows 和 Android App 可以选“在本机使用”，服务端随 App 运行在这台设备上，不用注册登录，数据只存在本机，不和其他设备同步。网页端（浏览器）没有本机模式。总体设计见[总体设计](design.md)，两个 App 各自的部分见 [Android](android.md) 和[桌面 App](desktop.md)。

## 做法

服务端本来就是一个 Rust 库（`crates/server`）。本机模式下，App 在自己的进程里启动它，只监听 `127.0.0.1`；页面和连服务器时一样走 HTTP 和 WebSocket（App 连服务器的那一套），只是地址是本机，令牌由 App 的原生部分交给页面。依赖规则、编号、改动记录和撤销、AI 整理都用同一份代码，前端不另写一套。

Android 也走 HTTP，不另做进程内调用：页面和小组件都已经用 HTTP，换传输方式两边都要另写一套。

| | 连接服务器 | 在本机使用 |
|---|---|---|
| 数据在 | 自己部署的服务器，各设备有副本 | 这台设备 |
| 账号 | 用户名和密码，邀请码注册 | 没有，自动建一个本机用户 |
| 多端同步 | 有 | 没有 |
| agent 接入 | 命令行、MCP、HTTP | 桌面上用命令行和 MCP（经命令行转接），App 运行时可用；Android 上没有 |
| AI 整理 | 配置可以仅本机或同步到服务器 | 只能仅本机 |
| 更新来源 | 登录的服务器 | GitHub Releases |
| 网页部分热更新 | Android 有 | 没有，随安装包更新 |

## 选择和切换

App 的登录页在表单下方多一个“在本机使用”按钮，附一行说明“数据只存在这台设备上，不同步”。

模式由一条记录决定，写下或删掉它就是切换的那一刻。其余的事都在之后的启动时按[数据代号](#数据代号)做，重做也没关系，所以中途被打断不会停在一半：

| | Android | 桌面 |
|---|---|---|
| 记录 | Preferences 的 `mode` 为 `local` | 文件 `local/enabled`，由原生部分读写 |
| 进入 | 在当前进程里启动服务端，得知本机用户；写下记录，重启 App | 调用 `start_local`，写下记录，不用重启 |
| 离开 | 一次提交里删掉记录、`server`、`token` 和原生部分记着的代号，重启 App | 删掉记录，重启 App |

- 桌面的记录不放在页面的 `localStorage` 里：WebKit 过一会儿才把它写进磁盘，离开本机模式后 App 紧接着重启，删掉的记录会回来。
- 在本机模式的登录页（启动失败后点“改用服务器”，或者收到 401）登录服务器，也是离开：登录成功后先删记录，再存服务器的会话。Android 删记录时连同 `server`、`token` 一起删，顺序反过来就会删掉刚存的会话。
- **进入**时，页面打开本机用户的数据，和登录另一个账号一样：设备上其他账号留在页面里的数据会删除。其中有没发出的改动（登录失效时会保留）时，先提示“这些改动会丢失”，确认后才进入。已经在本机模式时再点“在本机使用”（比如收到 401 之后），同样是重启，重新签发会话。
- **离开**和登录失效一样：没有令牌，回到登录页，小组件和提醒按现有规则清空。页面里本机用户的数据保留，包括本地副本、待发改动、草稿和设备上的 AI 整理配置：以后再点“在本机使用”就接着用，登录服务器账号时按现有规则删除。本机数据库原样保留。
- 两种模式的数据互不相通。把本机数据搬到服务器第一版不做，见[以后](#以后)。

**重启**：

- 桌面用 Tauri 的 `request_restart`（更新后的“重启”也是它）：先走完退出事件、释放单实例插件的占用，再启动新进程、退出旧的。
- Android 要结束进程、由系统重新创建，不只是重建界面，这样 `Application.onCreate` 和服务端会重新来一遍。做法和 ProcessPhoenix 一样：打开一个在单独进程里的透明界面，由它结束主进程、再打开 App。它自己是可见的界面，不受后台启动界面的限制；用 `AlarmManager` 定时打开会被拦下。澎湃 OS 真机还要验证（见[实验](#实现前先验证)），不行的话，结束进程前提示“请重新打开 NextTodo”。切换和恢复都在下次启动时续做，所以手动打开也一样完成。
- 两边新旧进程都可能短暂并存，靠[数据目录锁](#启动)保证新进程等旧进程退出后才动数据。

## 本机的服务端

### 启动

服务端库提供一个启动入口，命令行的 `serve` 也改用它，两边只有一份启动代码。本机模式下按顺序：

1. 取得数据目录锁：对 `local/lock` 加系统的独占文件锁（进程退出时系统自动释放），一直持有到进程结束。最多等 10 秒，拿不到就报“NextTodo 的另一个进程还在运行”。旧进程还没完全退出时，新进程就在这里等它。
2. 完成[待完成的恢复](#恢复)。
3. 只读地查看数据库的迁移版本。数据库不存在就新建；版本不合法（负数）或比 App 知道的新（装回了旧版本 App），就不打开、什么都不改，报“数据来自更高版本的 NextTodo，请先更新”或“数据库损坏”。
4. 打开数据库，跑迁移。
5. [规范本机用户](#本机用户)。
6. 把上次中断的 AI 整理记为失败。要在开始接受请求之前做完，否则会和刚连上的页面新开始的整理抢在一起。
7. 监听 `127.0.0.1`，端口由系统分配（绑定端口 0），给页面用。桌面上再监听一个给 agent 用的 HTTPS 端口：每次运行新生成一个 CA 和由它签发的证书，CA 的私钥签完就丢，证书的私钥只在内存里；把这个端口的地址和 CA 证书写进 `local/address`（JSON：`{"url": "https://127.0.0.1:<端口>", "ca": "<PEM>"}`），先写临时文件再改名，覆盖上次的（见[agent 接入](#agent-接入)）。这一步失败就返回错误，这时还没启动任何后台任务。
8. 启动每日快照、改动日志清理和 AI 整理队列，开始处理请求，返回地址、本机用户的 ID 和[数据代号](#数据代号)。

服务器上的 `serve` 没有恢复、规范用户和地址文件这几步，监听的是给定地址；数据目录锁是共享的，只是不让[恢复快照](deploy.md#备份和恢复)在它运行时换掉数据库。其余相同。

数据目录是 App 私有目录下的 `local/`。数据库放在其中的 `db/` 子目录里，好让[恢复](#恢复)整个换掉：

```
local/
  enabled              在本机模式时有这个文件（桌面）
  lock                 数据目录锁
  address              给 agent 的地址和这次运行的 CA 证书（桌面）
  db/nexttodo.db       连同 -wal、-shm
  snapshots/           每日快照
  before-restore-<秒>/ 恢复前的旧数据
```

| 平台 | `local/` 在 |
|---|---|
| macOS | `~/Library/Application Support/cn.juniexd.nexttodo/local` |
| Windows | `%APPDATA%\cn.juniexd.nexttodo\local` |
| Android | App 内部存储的 `files/local` |

- 启动失败时不签发会话。页面显示原因，附“恢复备份”和“改用服务器”（拿不到数据目录锁时还有“重试”）；Android 的小组件显示“打开 NextTodo”。
- 服务端在进程里一直运行到进程结束，中途不停止；需要换数据库（恢复备份）或离开本机模式时，App 重启。

### 数据代号

- 每个数据库有一个随机的代号，存在迁移新增的单行表里，建库时生成；[恢复](#恢复)时给换上的数据库换一个新的。
- 序号只在同一份历史里有意义，换了数据库，旧的序号就对不上了：可能恰好相等，也可能更小。所以靠代号，而不是靠比较序号，来判断设备上记着的东西还算不算数。
- 原生部分把代号连同地址、令牌、用户 ID 一起交给页面。页面和 Android 原生部分各自记着上次用的代号：
  - **页面**：打开本机用户的数据之前，代号变了就删掉这个用户在页面里的本地副本和待发改动，草稿和 AI 整理配置保留，然后从头下载。用户 ID 和上次的不同（恢复了另一台设备的备份）时，按登录另一个账号处理。先删，再记下新代号，中途被打断下次重删。
  - **Android 原生部分**：在 `onCreate` 里，代号变了就清空小组件的列表和全部提醒，然后记下新代号。小组件记着的序号、提醒用的事项编号都属于换掉的数据。页面打开会话后，会照常重写小组件、重排提醒。
- 离开本机模式时，Android 原生部分记着的代号随模式记录一起删掉：之后服务器账号会写入自己的列表和提醒，再进入本机模式时就会清掉它们，哪怕本机数据库没换过。页面记着的代号保留，它对应的本地副本也保留着，回来接着用。

### 本机用户

每次启动时规范数据库，第一次启动和恢复备份后也一样：

- 正好一个用户，用户名 `local`，显示名“本机”。没有就建一个；多于一个的数据库不打开，恢复前已经挡住（见[恢复](#恢复)）。
- 不是管理员；密码存空串，任何密码都验证不过（`verify_password` 解析不了空串，登录照常回答“用户名或密码错误”）；删除全部邀请码。所以登录、注册、邀请这些不需要令牌的接口，在本机模式下做不成任何事，不必单独关掉。
- 删除同步到服务器的 AI 配置。本机没有解密用的密钥，从服务器数据库恢复来的配置用不了。
- API 令牌保留，桌面上 agent 用的就是它们。

### 令牌和端口

- 原生部分在服务端启动成功后签发设备会话（设备名“本机”）。签发和作废之前的设备会话在同一个事务里。然后把地址、令牌、用户 ID 和代号交给页面：
  - Android 在 `Application.onCreate` 里签发，写进 Preferences 的 `server`、`token`。
  - 桌面每次调用 `start_local` 都签发一个，调用排队依次执行。服务端只在第一次调用时启动；启动失败的，下次调用再试。只有一个窗口，再次调用只会是页面重新加载，之前那次的页面已经不在了。
- 页面拿到之前不发任何请求。桌面上的页面不保存它们，每次加载都重新取。
- Android 上，一个进程里 `server` 和 `token` 只会被删掉（离开本机模式、登录失效），不会换成别的值；换值只在重启后的 `onCreate` 里。所以小组件分两次读这两个值，读到的要么是同一次启动的，要么缺一个，缺了就照常显示“打开 NextTodo”。
- 本机模式下正常不会收到 401。万一收到，按现有的“登录失效”处理：回到登录页，待发改动保留，再点“在本机使用”会签发新的会话。

端口在两个平台上都由系统每次分配，不用固定端口：固定端口可能被别的程序先占住，App 就启动不了，agent 还会把令牌发给它。桌面上的 agent 经命令行找到这次的地址，见[agent 接入](#agent-接入)。

**安全的依据是令牌。** 能连到这个端口的，有这台设备上的任何程序、浏览器里的网页（包括借 DNS 重绑定访问 `127.0.0.1` 的网页）、Android 上的其他 App。它们没有令牌，做不了任何事：

- 会话令牌只在 App 的进程和私有存储里，API 令牌只在用户自己配置的 agent 那里。agent 只在核对过证书的 HTTPS 连接上发令牌。
- 本机模式下没有人用密码登录，这个地址下不会有会话 Cookie，浏览器替网页带不上任何凭据。

**不在防护范围内的**：以同一用户身份运行的不可信程序。它们本来就能读 App 的数据文件和私有存储。桌面本机模式假定这台电脑上没有这种程序；Android 上每个 App 互相隔离，不存在这个问题。

### 可靠性

- SQLite 是 WAL 模式（`synchronous=NORMAL`）。进程被杀不丢已确认的改动；断电或系统崩溃时，可能丢失最后一刻的改动。
- 快照和改动日志的保留和服务器一样：启动时和之后每天快照一次，保留 7 份；改动日志保留 90 天。快照和数据在同一台设备上，只防数据库损坏，不防设备丢失，所以另有[备份](#备份和恢复)。恢复前的旧数据（`before-restore-*`）不算快照，不自动删除。
- 日志不写用户内容，级别和服务器一样默认是 info。桌面写标准错误，连同插件的日志，`RUST_LOG` 可以调；从终端启动 App 才看得到。Android 经 `android_logger` 写 logcat，标签是 `NextTodo`。

## 桌面

- Tauri 外壳（`src-tauri`）直接依赖 `nexttodo-server`，在 Tauri 自带的 tokio 运行时上启动服务端。
- 页面加载时读到本机模式的记录，先调用 `start_local`，拿到地址、令牌、用户 ID 和代号后，再打开会话。开机自启（`--hidden`）时页面同样加载，所以 App 只在菜单栏或托盘里时服务端也在运行。
- HTTP 插件已经允许任意 `http(s)://` 地址，不用改。

### 页面直连

页面连本机的服务端用的是普通 HTTP，经过代理就会把会话令牌和数据交给代理；代理在别的机器上时还根本连不上。所以本机模式下页面的请求一律直连：

- HTTP：桌面的 HTTP 插件默认用系统代理和代理环境变量，而且不会自动绕开 `127.0.0.1`。本机模式下每个请求带上一个显式的代理设置 `{all: {url: <随便一个地址>, noProxy: "127.0.0.1"}}`，并且不跟随重定向（`maxRedirections: 0`）。
  - reqwest 只要给了显式的代理，就不再用系统代理和环境变量；`noProxy` 又让到 `127.0.0.1` 的请求直连。
  - `noProxy` 要写 IP 本身：`*` 只匹配域名，对 IP 地址不起作用。
  - macOS 和 Windows 上已实测。
- WebSocket 走 WebView 自己的网络。macOS 的 WebKit 和 Windows 的 WebView2 上实测，连 `127.0.0.1` 都不走代理，给 WebView 单独设了代理也一样。
- Android：系统设了代理（Wi-Fi 代理或全局代理）时，`HttpURLConnection` 默认连 `127.0.0.1` 也走代理。CapacitorHttp 和小组件都用它发请求，而 CapacitorHttp 不能按请求关掉代理。所以本机模式下：
  - 页面的 HTTP 改用 WebView 自己的 `fetch`。Capacitor 给 `fetch` 打补丁之前，把原来的存在了 `window.CapacitorWebFetch`。WebView 连 `127.0.0.1` 不走代理，也不算混合内容。
  - 本机的服务端在 Android 上允许来源 `https://localhost` 跨域，请求头 `Authorization` 和 `Content-Type`。
  - 顺带，写请求也能按时取消了：CapacitorHttp 不转发 `AbortSignal`。
  - 小组件的请求用 `Proxy.NO_PROXY`。
  - Android 16、17 的模拟器上已实测。

### agent 接入

端口每次启动都变，agent 的配置里写不了地址，改由命令行去找这次运行的 App。设置里照常生成 API 令牌，鉴权和连服务器时完全一样。

- **给 agent 的端口用 HTTPS**：桌面上服务端另外监听一个端口，只给 agent 用。每次运行新生成一个 CA 和由它签发的证书（包含 IP `127.0.0.1`），私钥都不落盘；地址和 CA 证书写在 `local/address`（见[启动](#启动)）。
  - 命令行只信任这张 CA 证书，不用系统的信任库，握手成功才发出令牌和请求内容。rustls 不支持把终端证书本身当作信任的根，所以要多一个 CA。
  - 地址文件可能已经过时（App 崩溃后留下的，或者 App 刚好退出），旧端口也可能已经被别的程序占了。对方拿不出这次证书的私钥，握手就失败，什么都不会发出去，也没有回复可以伪造。
  - 只保护令牌是不够的：发错了端口，请求里的标题、描述、搜索词也会被别人收到，回复也可能是伪造的。先确认对方是这次运行的 App，这些才都挡得住。
  - 证书不是秘密，地址文件只要求别人改不了：数据目录、地址文件和它的临时文件从创建起就只有本用户能写，Windows 上要核对继承来的权限。命令行按平台知道 `local/` 在哪。
  - 页面照旧用普通 HTTP，连另一个端口。它的地址是原生部分在监听后当场交给它的，不会过时；请求不经代理，见[页面直连](#页面直连)。
  - Android 上没有 agent 接入，不监听这个端口。
  - 握手在各个连接上并发进行，10 秒超时，一个慢的连接挡不住别的。
  - 新依赖：生成证书的 `rcgen`，在 axum 上跑 TLS 的 `tokio-rustls`。加密后端统一用 ring，和桌面现有的 rustls 一致：`tokio-rustls` 默认带的 aws-lc-rs 要关掉，两个后端同时启用时 rustls 选不出默认的，会 panic。这些放在服务端库里一个只有桌面启用的 feature 下，Android 的动态库不带。
- **命令行**：`NEXTTODO_URL` 是 `local` 时，连这台电脑上本机模式的 App。
  - 令牌只从 `NEXTTODO_TOKEN` 读，不用配置文件里连服务器的那个。
  - 地址文件里的地址必须正好是 `https://127.0.0.1:<端口>`（端口不为 0，没有用户名、路径和查询），否则报错。不经代理（不管 `HTTPS_PROXY` 等环境变量），不跟随重定向，收到 3xx 当作错误。
  - 每个地址文件用一套新的连接配置，已经和上一张证书握过手的连接不再复用。
  - 每条命令只读一次地址文件。网络出错后的自动重试（幂等键不变）只发给同一次运行：App 中途重启过的，重试会因为证书对不上而失败，就报错，不会把同一个写操作再发给恢复后的另一个数据库。证书对不上时不重试，同一次运行里重试也不会成功。
  - 没有地址文件或连不上时，报“连不上本机模式的 NextTodo：App 没有在运行，或者正在启动”。握手失败时报“本机 NextTodo 的证书对不上，App 可能刚重启过”。地址文件格式不对或读取出错时，如实报告。
- **MCP**：新增 `nexttodo mcp`，一个 stdio 的 MCP 服务器。
  - 它从标准输入逐行读消息，每条都重新读一次地址文件，按上面的方式连到这次运行的 App，POST 到 `<地址>/mcp`，再把回复写到标准输出。App 重启、换了端口和证书也照常。标准输出只写协议消息，诊断信息写标准错误。
  - 请求头：`Accept: application/json, text/event-stream`、`Content-Type: application/json`，初始化之后带上协商好的 `MCP-Protocol-Version`。
  - 服务端是无状态的，直接回 JSON（`crates/server/src/mcp.rs`）。通知得到 202，什么也不输出；回复不是 JSON 的当作错误，现在的工具不会这样回。
  - 连不上或 HTTP 出错时：带 `id` 的请求回一个同样 `id` 的 JSON-RPC 错误，写明原因；通知只把错误写到标准错误。
  - 不自动重试：MCP 的写操作没有幂等键，重发可能做两遍。
- **令牌页给出的写法**（本机模式下）：
  - 命令行用的环境变量：`NEXTTODO_URL=local` 和 `NEXTTODO_TOKEN`，写法和现在一样，macOS 写进 shell 配置，Windows 用 `setx`。
  - Claude Code：`claude mcp add nexttodo --env NEXTTODO_URL=local --env NEXTTODO_TOKEN=<令牌> -- nexttodo mcp`。
  - Codex：`codex mcp add nexttodo --env NEXTTODO_URL=local --env NEXTTODO_TOKEN=<令牌> -- nexttodo mcp`。
  - 都要先装命令行，见 [agent 接入](agent.md#命令行)；不在 `PATH` 里的，写完整路径。
- 不支持直接调 HTTP 工具接口：地址和证书每次都变。
- 没用 Unix 套接字和 Windows 命名管道：命名管道在 App 没运行时同样能被别的用户抢先创建，要另做校验；HTTPS 加证书在两个平台上是同一种做法，也不用另做一套传输。
- 命令行不随 App 打包：Windows 上 agent 开着的 `nexttodo mcp` 会占住这个文件，App 更新时换不掉它。

## Android

- 服务端编译成 `arm64-v8a` 的动态库（`cargo-ndk`），打进 APK 的 `jniLibs`。真机和 Apple 芯片 Mac 上的模拟器都是 arm64，只出这一种。
  - 用单独的 profile `android`：`lto = "fat"`、`codegen-units = 1`、`opt-level = "s"`、`strip = true`，动态库 7.3 MB；不开这些是 11.3 MB。按 16 KB 页对齐，Android 15 起的 16 KB 页设备也能加载。
  - Gradle 在构建前编译它（任务 `rust`），所以打 APK 还是一条命令。
  - APK 里按默认不压缩存放，装好后不用解压，安装包大约大 7 MB（现在 6.5 MB）。压缩存放能小一半，但装好后要解压出来，多占一份空间。
- JNI 的胶水代码放在单独的小 crate `crates/android` 里，对应 Kotlin 的 `LocalServer`，只有几个入口：启动、签发会话、备份、准备恢复、提交恢复。出错时抛出带着给用户看的原因的异常。
  - JNI 按函数名找入口，入口要不改名地导出（`#[unsafe(no_mangle)]`），Rust 把它算作不安全代码。所以这个 crate 不用工作区禁止 `unsafe` 的设置，改为默认禁止、在每个入口上单独放行；除此之外没有 `unsafe`。
  - 启动、签发会话和备份在 crate 自己的 tokio 运行时上同步执行，服务端的后台任务也在这个运行时上，一直到进程结束。
- 新增自定义的 `Application`（`NextTodoApp`）。`Restart` 所在的单独进程什么也不做，否则它会等主进程手里的锁。主进程的 `onCreate` 里读到本机模式时，按顺序：
  1. 清掉 Preferences 里旧的 `server` 和 `token`。
  2. 同步启动服务端（[启动](#启动)的全部步骤）。模拟器上实测：已有数据库时约 1 毫秒；新建并迁移时 12～19 毫秒；偶尔有一次 60 毫秒。
  3. 按[数据代号](#数据代号)决定是否清空小组件和提醒。
  4. 签发会话，写入新的 `server` 和 `token`。

  启动失败时只记日志：页面打开时向原生部分要地址、令牌、用户 ID 和代号（插件的 `openLocal`），这时在同一进程里再试一次，仍然失败就显示原因；拿不到锁时点“重试”也是这样。
- App、小组件、提醒、定时刷新，不管哪个让进程启动，都会先经过 `onCreate`。所以小组件读到的时候，服务端一定已经在了。小组件照旧从 Preferences 读地址和令牌，经 HTTP 取列表、勾选完成，进行中的操作照旧按令牌判断是否作废。
- 每次启动按当前模式重新登记小组件的定时刷新：本机模式下不要求联网。用更新已有任务的方式登记，已装的 App 原来那个要求联网的任务也会改过来。
- 网页版本：本机模式只用 APK 自带的网页，网页和服务端打在同一个 APK 里，版本始终一致。
  - 本机模式下启动时，删掉从服务器热更新下来的版本，把 `serverBasePath` 换回 APK 自带的。
  - 本机模式下不查 `web.json`。
- 明文 HTTP：网络安全配置只放行到 `127.0.0.1` 的明文请求，其他地址照旧只能用 HTTPS。
- 进程在后台会被冻结或结束，服务端只在进程存在时运行，不保证 AI 整理在后台做完：
  - 冻结期间整理暂停，回到前台后接着做，或者按超时失败。
  - 进程被结束的，下次启动时记为失败（“整理中断”），可以重试。
- 设置里不显示令牌一组：服务端只监听本机，手机上又没有命令行，agent 接不进来。

## 界面

本机模式下设置页的不同（其余见[界面](ui.md)）：

- 最上面的账号卡片换成“本机模式”卡片：说明数据只存在这台设备上，下面是“备份”“恢复”“改用服务器”。
- 不显示：修改密码、显示名、邀请码、已登录的设备、退出登录。
- 令牌：桌面照常显示，Android 不显示。
- AI 整理的保存位置只有“仅本机”：本机服务端没有加密用的密钥（`NEXTTODO_SECRET_KEY`），现有界面已经这样处理。

## 备份和恢复

备份和恢复由原生部分直接调用服务端库，不走 HTTP 接口：桌面是 Rust 命令，Android 经 JNI。桌面的保存和打开对话框用 Tauri 官方的 `tauri-plugin-dialog`，由 Rust 命令打开，路径不经过页面；Android 用系统的存储访问框架，经缓存目录里的临时文件交给 Rust。

### 备份

1. 等待待发队列清空，包括正在保存的改动。被拒绝的照现有方式提示。本机服务端一直在，通常立即完成；几秒内没清空就提示稍后再试。
2. 服务端用 `VACUUM INTO` 生成一份副本，和每日快照一样，运行中也能得到一致的副本。
3. 保存到用户选的位置，默认文件名 `NextTodo-备份-<日期>.db`：先写成旁边的 `<文件名>.partial`，再改名换上，不会留下写了一半的备份。选在数据目录 `local/` 里就提示，不保存：那样可能换掉正在用的数据库。

备份里有：

- 全部数据，包括改动记录，撤销还能用。
- API 令牌，只存哈希，恢复后重新生效。

备份里没有 AI 整理的配置：它存在页面里，所以备份里也没有 API 密钥。恢复成别的本机用户（备份来自另一台设备）后，要重新填写。

### 恢复

不需要服务端在运行，所以启动失败时也能恢复。

**准备**：选一个备份文件，复制到数据目录里的临时目录 `restore.part/`（同名的旧目录先删掉）。在这份副本上检查和准备，任何一步不通过，就删掉 `restore.part/`、提示原因，什么都不改：

1. 是 SQLite 数据库，`integrity_check` 和 `foreign_key_check` 通过。
2. 迁移版本合法，不比 App 新；表结构和同一版本的空数据库完全一致。这一条认出它是 NextTodo 的数据库，以前各版本的备份和服务器数据库也认得出。
3. 正好一个用户。
4. 跑迁移，规范为本机用户，换一个新的数据代号。恢复的即使是这台设备自己的备份，也和现在的数据不是同一份历史。

单用户的服务器数据库也能这样恢复，相当于把自己部署的数据搬到本机；多用户的不行。准备完关闭数据库，不留 `-wal`，把文件写入磁盘（`fsync`）。

**提交**：用户确认“会用备份替换这台设备上的全部数据”，然后：

1. 把 `restore.part/` 改名为 `restore/`，从这一刻起恢复算是提交了。改名失败就提示原因，会话照常。之后同步 `local/` 目录失败只记日志：恢复已经提交，断电最多让它作废。
2. 页面结束会话，不再发送改动。
3. App 重启，第 2 步出错也照样重启。

确认框写明两件会丢的事：

- 还没发出的改动会丢弃，找不回来；队列里有改动时写出有几项。从设置里恢复时，准备之前已等待队列清空，通常没有；启动失败时恢复，就可能有。
- 现在的数据会留在 `local/` 下的旧数据目录里；从确认到 App 重启之间，小组件、AI 整理和桌面上的 agent 写入的改动，也只在那里，不会出现在恢复后的数据中。

**完成**：新进程拿到数据目录锁之后、打开数据库之前，按目录的状态续做。每一步都是 `local/` 里的目录改名：

| 状态 | 做法 |
|---|---|
| 有 `restore.part/` | 没提交的准备，删掉 |
| 有 `restore/`，也有 `db/` | 把 `db/` 改名为 `before-restore-<Unix 秒>/`（已存在就加序号，不覆盖），连同 `-wal`、`-shm` 原样保留，不自动删除；再做下一行 |
| 有 `restore/`，没有 `db/` | 把 `restore/` 改名为 `db/` |
| 没有 `restore/` | 没有要做的 |

- 保证的是进程在任何一步被结束后都能续做。断电只尽力：macOS 和 Android 上每次改名后同步 `local/` 目录；Windows 上同步目录要用不安全的系统调用（项目禁止 `unsafe`），只靠 NTFS 自己的日志。断电后回到哪一步，按上表照样续做。
- 任何一步失败（比如文件被占用、磁盘出错）就停下：不打开数据库，也不删任何东西，按启动失败显示原因，下次启动再从当时的状态续做。

**之后**：

- 页面和 Android 原生部分看到新的[数据代号](#数据代号)，丢掉旧的本地副本、待发改动、小组件列表和提醒，从头下载。
- 恢复时还没发出的改动不会作用到恢复后的数据上：用户要的是换成备份里的数据。从设置里恢复时，准备之前会先等待队列清空，所以通常没有这样的改动。

## 更新

- 本机模式没有服务器可以取更新，改从 GitHub Releases 取：用固定地址 `https://github.com/JunieXD/NextTodo/releases/latest/download/<清单>` 取 `android.json`、`desktop.json`。GitHub 会转到最新 Release 里的同名文件，不调 GitHub API。
- `deploy/build.sh` 构建时，Release 的文件里加上更新要用的全部文件：两份清单，以及 macOS 的更新包 `NextTodo.app.tar.gz`（APK 和 Windows 安装程序本来就在）。清单里的下载地址写成这个 Release 的完整地址（`…/releases/download/v<版本>/<文件>`），不依赖跳转后的相对路径，所以清单和安装包不会对错版本。
- 只有发布 Release 才有新版本，平时部署到自己服务器的不算。
- 比较版本的规则和连服务器时一样：Android 看原生版本，桌面看版本号。
- 校验照旧：APK 由系统校验签名，桌面更新包用更新密钥校验。信任的是 GitHub 的 HTTPS 和这两种签名。
- 检查失败（比如连不上 GitHub）时不打扰，下次照常再查；设置页“关于”里显示上次检查的时间和结果。
- Android 的网页部分不热更新，随 APK 更新（见[网页版本](#android)）。

## 实现前先验证

还没做的，要在澎湃 OS 真机上做：

- 自动重新打开 App（ProcessPhoenix 的做法）：澎湃 OS 对后台启动和自启动管得比原生 Android 严。不行的话，改成提示手动重新打开。
- 页面直连、`Application.onCreate` 的耗时，在真机上再看一眼。

恢复时被打断后续做，由 Rust 测试在三个平台上覆盖；断电时能保证到哪一步无法实测，按[恢复](#恢复)里写的尽力而为。

已验证的（2026-11-06，macOS、Windows 11、Android 16 和 17 模拟器，用单独的实验程序）：

- 桌面重启：用 `request_restart` 时，单实例插件不会把新进程当成第二个实例；新进程等旧进程退出后拿到锁（Windows 上等了 83 毫秒）。
- 端口：监听期间别的用户抢不走。macOS 上连同一用户都绑不上同一个地址和端口；Windows 上另一个用户绑同一地址被拒（tokio 不设 `SO_REUSEADDR`），不用设 `SO_EXCLUSIVEADDRUSE`。两边绑 `0.0.0.0`（macOS 上还有 `[::]`）的，都收不到发往 `127.0.0.1` 的连接。
- 页面直连：HTTP 插件默认会把到 `127.0.0.1` 的请求发给代理环境变量里的代理；带上[页面直连](#页面直连)的设置后直连，也不跟随重定向。WebKit 和 WebView2 的 WebSocket 和 fetch 连 `127.0.0.1` 都不走代理，WebView 单独设了代理也一样。页面（`tauri://localhost`、`http://tauri.localhost`）连 `ws://127.0.0.1` 不算混合内容。
- 命令行连 HTTPS 端口（ureq，只信任这次的 CA，不经代理，不跟随重定向）：连对的运行正常；连另一次运行的端口，握手失败，对方收不到请求；连只收字节的程序，对方只收到握手的开头，没有令牌和路径；有代理环境变量也直连；一个连接不握手，不影响别的连接。生成证书在 macOS 上约 1 毫秒，Windows（ARM 上模拟 x64）上第一次 65 毫秒。
- 加密后端：桌面现有的依赖加上 `tokio-rustls`（只开 ring）和 `rcgen`，仍然只有 ring，rustls 不会 panic。
- Windows 上的改名：进程刚退出就改名它用过的目录，200 次都成功；一边读地址文件一边改名替换它，2000 次没有失败，也没读到写了一半的内容。
- Android 的页面：`https://localhost` 的页面连 `ws://127.0.0.1`、`fetch` `http://127.0.0.1`，都不算混合内容，WebView 的混合内容设置是默认最严的那档也一样。WebView 的请求在系统设了代理时也直连。带 `Authorization` 头的跨域请求（有预检）正常。
- Android 的明文配置：只放行 `127.0.0.1` 的网络安全配置生效，`HttpURLConnection` 连 `127.0.0.1` 正常，明文连别的地址被拒。
- Android 的代理：系统设了代理时，`HttpURLConnection` 默认连 `127.0.0.1` 也走代理，`Proxy.NO_PROXY` 时直连。由此改了[页面直连](#页面直连)的做法。
- Android 的启动：`Application.onCreate` 里同步启动服务端，加载动态库约 0.5 毫秒，启动见 [Android](#android)。冷启动到页面显示 570～710 毫秒，大部分是 WebView 初始化。
- Android 的重启：ProcessPhoenix 的做法在 16 和 17 上都能用，新进程约 0.1 秒后启动，拿锁不用等；`AlarmManager` 定时打开被后台启动限制拦下（即使创建 PendingIntent 时声明了允许）。
- Android 动态库的大小：见 [Android](#android)。

## 测试

- Rust：
  - 启动顺序：拿不到锁时等待和报错；拒绝版本不合法和版本更新的数据库，并且没写过它；先处理中断的整理，再接受请求；监听失败时没有启动后台任务；地址文件在监听后才写，每次运行换一张证书。
  - 命令行和 `nexttodo mcp`：地址文件过时或缺失时报错，不发出任何内容；设了代理环境变量也直连；App 重启后自动重试失败、不发给新的一次运行；`nexttodo mcp` 的请求、通知、出错时回的 JSON-RPC 错误，以及 App 重启后连上新端口。
  - 规范本机用户：没有密码、不是管理员、没有邀请码和服务器上的 AI 配置。签发会话时作废旧的。
  - 备份：拒绝存进数据目录。
  - 恢复的准备：拒绝多用户、版本更新、表结构不符、损坏的文件；接受以前版本的备份和单用户的服务器数据库；换了数据代号。
  - 恢复的完成：在每次改名前后打断，再启动都能接着做完；改名失败时停下、什么都不删。
- 网页（Vitest）：代号变了时删掉副本和待发改动、保留草稿和 AI 配置；换了用户时按登录另一个账号处理；不在本机模式时登录服务器不碰模式记录；恢复没提交时会话照常，提交了就重启。
- 实际操作：
  - 两个 App 上：选本机模式、增删改、重启后数据还在、改用服务器再切回来、备份恢复（包括恢复这台设备更早的备份、另一台设备的备份，以及启动失败时恢复）、更新检查。
  - 桌面上的命令行和 MCP（Claude Code、Codex）：App 在运行、没在运行、正在启动、中途重启这几种情况。
  - Android 的小组件和提醒：进程被结束后从小组件拉起、完全离线时刷新、从旧版本升级后定时刷新不再要求联网，以及恢复和切换模式后不留旧列表和旧提醒。
