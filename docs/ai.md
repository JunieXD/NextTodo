# AI 整理

把随手写下的一大段话整理成待办：添加框切到“AI 整理”，写完提交，不用等；服务端在后台调用用户自己配置的大模型，整理成一条或几条事项（标题、描述、截止时间、依赖），完成后同步到各端。原文的信息一点不丢。

## 添加

- 添加框有两种模式：“直接添加”（现在的行为）和“AI 整理”，用框里的 ✦ 按钮切换，和字数无关。设备记住上次用的模式，Android 上 App 和小组件的[添加弹窗](android.md#添加弹窗)共用。还没配置模型时，点 ✦ 打开设置里的“AI 整理”。
- AI 整理模式下回车换行，用发送按钮提交，电脑上也可以按 Ctrl + Enter（macOS 上 ⌘ + Enter）。输入框随内容增高，最多 5 行，再多就在框内滚动；超过 3 行时可以展开成单独的编辑页，见[界面](ui.md#其他)。
- 原文最多 10000 字，不受标题 200 字的限制；没提交的内容和直接添加共用一份草稿。
- 提交后输入框清空，列表里马上出现一行“整理中”的请求。

## 整理请求

提交的内容是一个整理请求，不是事项：不进“接下来”，不算在可做的数量里，小组件和提醒也不管它。

| 状态 | 显示 | 能做的事 |
|---|---|---|
| 等待 | “等待整理”，原文第一行 | 删除 |
| 整理中 | 转圈，“正在整理” | 删除（结果丢弃） |
| 失败 | “整理失败：<原因>” | 重试；改原文后重试；按原文添加；删除 |

- 显示在所在文件夹的事项列表顶部；“接下来”顶部也列出全部未完成的请求，提交后不论在哪一页都看得到。
- 成功时，请求消失、整理出的事项出现，二者在同一个改动里，作者记为“AI 整理”。提示条写“AI 整理完成，添加了 3 项”，附“撤销”。
- 撤销整理结果：事项删除，请求恢复为失败，原因“已撤销”，原文还在，可以重试、改了再试或按原文添加。
- 撤销删除（包括撤销删除所在的文件夹）时，请求照原样回来；原来是整理中的，回来时记为失败，原因“已撤销”，因为那次整理的结果已经丢弃。请求状态的变化（开始整理、失败、重试）本身不能撤销。
- 按原文添加：标题取第一行的前 200 字，原文较长时全文放进描述，同时删除请求。

| 边界 | 处理 |
|---|---|
| 离线时提交 | 请求和其他改动一样先存在本机，联网同步后才开始整理 |
| 整理中改原文 | 不允许，提示“正在整理，稍后再改” |
| 整理中删除请求或它所在的文件夹 | 请求随之删除（可撤销）；整理结果丢弃，不留下事项 |
| 结果引用的事项已被删除，或依赖成环 | 失败，原因写清是哪一项 |
| 模型返回的不是合法 JSON，或不符合格式 | 失败，可重试 |
| 结果的依赖指向这个文件夹以外的事项 | 失败：只能接在发给模型的那些事项后面 |
| 接口报错：密钥错误、余额不足、限流、超时 | 失败，原因先说明状态码的含义，括号里附上接口返回的信息 |
| 服务器重启 | 整理中的记为失败（“服务器重启，整理中断”），等待的照常整理 |

## 模型配置

设置里的“AI 整理”页：服务商、接口地址、API 密钥、模型、思考程度、保存位置，以及“测试”按钮（用当前配置发一个最小的请求，显示成功或接口返回的错误）。模型可以从接口的 `GET /models` 列表里选，也可以手填。

只支持 OpenAI 兼容接口（`POST <接口地址>/chat/completions`）。预设的服务商：

| 服务商 | 接口地址 | 默认模型 | 思考参数 | JSON 模式 |
|---|---|---|---|---|
| DeepSeek | `https://api.deepseek.com` | `deepseek-flash` | `thinking` + `reasoning_effort` | 支持 |
| 通义千问 | `https://dashscope.aliyuncs.com/compatible-mode/v1` | `qwen-plus` | `enable_thinking` | 不开思考时支持 |
| OpenAI | `https://api.openai.com/v1` | `gpt-5-mini` | `reasoning_effort` | 支持 |
| 自定义 | 用户填写 | 用户填写 | 不发思考参数 | 不发 |

思考程度有“关闭”“低”“高”三档，按服务商换成各自的参数：

| 思考参数 | 关闭 | 低 | 高 |
|---|---|---|---|
| `thinking` + `reasoning_effort` | `thinking: {type: "disabled"}` | `thinking: {type: "enabled"}`，`reasoning_effort: "low"` | 同左，`"high"` |
| `enable_thinking` | `enable_thinking: false` | `enable_thinking: true` | 同左 |
| `reasoning_effort` | `"minimal"` | `"low"` | `"high"` |

- DeepSeek 默认开着思考，所以“关闭”也要明确发出。
- JSON：提示词里写明只输出 JSON、给出格式（DeepSeek 和千问要求提示词里出现“json”）；支持 JSON 模式的同时发 `response_format: {type: "json_object"}`。解析前去掉代码块围栏和 `<think>` 段落，再按下面的格式严格校验。
- 预设的地址、模型和参数写在服务端一处，客户端从 `GET /ai/providers` 读取。
- 服务端替用户访问的只能是公网上的 HTTPS 接口，借它读不到服务器内网里的东西：接口地址必须是 `https://`；域名解析出的地址里，回环、内网、链路本地等不是公网的一律不连，只剩这些时报“接口地址不是公网地址”；不走代理，不跟随重定向。模型的回复最多取 1 MB。
- 本机模式不查公网地址：用这台设备的只有它的主人，不存在借服务端访问别人内网的问题；而开着 fake-ip 模式代理的电脑上，域名都解析到 `198.18.0.0/15` 这类假地址，查了就连不上。
- 报错时先写状态码的含义，再在括号里附上接口回复里的错误信息，如“API 密钥无效（接口返回 401：invalid key）”：401 密钥无效，402 余额不足，403 密钥没有权限，404 接口地址或模型名称有误，429 请求过于频繁或额度已用完，5xx 服务商暂时不可用，3xx 接口地址有误；其他状态只写接口返回的信息。去掉其中出现的 API 密钥，最多 300 字：它会作为失败原因保存在请求上。
- 连不上接口时，原因写成用户能懂的话：超时、找不到域名、证书无效，其余的写“无法连接接口，请检查接口地址和网络”，网络的原始错误只记日志。

## 保存位置和安全

| | 仅本机 | 同步到服务器 |
|---|---|---|
| 配置和密钥存在 | 这台设备，按用户分开，退出登录时删除 | 服务端，按用户存放；密钥加密 |
| 谁来启动整理 | 这台设备联网时，把请求连同配置交给服务端（`POST /ai/jobs/{id}/run`）；服务端只在内存里用这把密钥，整理完就丢，不写数据库、不写日志 | 服务端自己在后台整理，提交后设备可以立即离线 |
| 设备不在线时 | 请求一直“等待整理”，直到某台存有配置的设备上线 | 照常整理 |

- 加密用 XChaCha20-Poly1305，服务端的密钥来自环境变量 `NEXTTODO_SECRET_KEY`（32 字节，base64）。没设置时只能选“仅本机”，[本机模式](local.md)也是这样。数据库文件和快照单独泄露时，密钥仍然安全。
- 读取配置时，密钥只返回末 4 位；改配置时不填密钥表示沿用原来的。
- 配置和请求和其他数据一样，每个查询都按用户过滤。只读令牌不能提交请求。
- 配置、测试、列模型和交出配置开始整理（`/ai/settings`、`/ai/test`、`/ai/models`、`/ai/jobs/{id}/run`）只能用登录的设备，API 令牌返回 403：agent 用不到，也就碰不到密钥。
- 发给模型的内容：原文、提交时的本地时间、文件夹路径，以及这个文件夹里未完成事项的编号、标题、截止时间和依赖（最多 50 项）。事项描述不发。

## 提示词和结果

结果是 `apply` [计划](agent.md#计划)里的事项列表：`{"tasks": [{ref, title, description, due, remind, after, before}]}`，不能写 `folder`，事项都放进请求所在的文件夹。由服务端用 `apply` 的同一套代码校验并执行，规则和 agent 提交的计划完全一样。

提示词要求（措辞经[评测](#评测)比较选定）：

- 原文的每个要求、细节、理由、背景、疑问和不确定之处都要留在标题或描述里，不编造。
- 标题简短，以动作开头，写清这件事本身；原文提到的每个对象都在标题里（拆开时各在各的标题里），没说动作的不猜、不删词。原文很短、本身就像标题时（如“官网迁移与新版本文档”），模型容易为了以动作开头只留下一半。
- 描述只写标题装不下的信息，用简洁的书面语自己重新组织，不照搬原话：去掉语气词、口头填充、重复和改口，不写“我觉得”“我发现”这类第一人称的口头叙述，原文拿不准的照样写明，几点时写成列表，不重复标题。标题已经说全了就不写描述，原文很短时通常如此。
- 代码、命令、链接、文件路径、数字和数据，以及引号里要照着用的原话，原样放进描述，一个字不改：改一个字就可能出错。写给 AI 或 agent 的提示词也常是语音输入的口语，和别的内容一样改成书面语，每一条要求都留下。
- 能分成独立步骤的拆成几条，有先后的加依赖。拆不开的就是一条。
- 逐条对照文件夹里已有的事项：要用到它的成果、或要等它做完才能开始的，写进新事项的前置（如“写官网文档”要等“建好官网”）；已有事项要等新事项的，写进后续（如“开存款证明”做完才能“提交签证材料”）。只是主题相近的不连。
- 只在原文明确给出时间时写截止时间；“明天下午三点”这类按提交时的本地时间换算。原文说了某天以后才能做（“1 号开始领”“下周一起”）的，写开始日期，同样换算。
- 每个事项都写 `ref`，依次是 `a`、`b`、`c`。只写“选填、供引用”时，模型常在 `after` 里写 `a` 却没给那一项写上 `ref`，计划因此被拒，整理失败。
- 末尾三个例子：一段口语、一个短原文、两件有先后的事各整理成什么样。只改规则时照抄原话少了近一半，多写描述仍常见；加上例子后多写描述也很少了。例子写明只示范写法，评测里没见到模型套用其中的内容。

上下文就是上面的文件夹信息，先不做单独的“记忆文件”；以后确有需要，再给文件夹加一段说明一起发送。

## 整理文件夹

用自己的话告诉 AI 要对一个文件夹里的事项做什么：人在这里能做的，AI 都能做。AI 只提出建议，用户逐条确认后才执行。

- 入口：文件夹的“…”菜单和右键菜单（根目录在左栏右键）里的“AI 整理事项”。先在多行的输入框里写要求，下面注明“新建、修改、完成、删除、移动事项，调整先后和顺序都可以，执行前由你逐条确认”。默认是“把标题改清楚，描述改成简洁的书面语，补上漏掉的先后关系。”，可以改。回车换行，电脑上按 Ctrl + Enter（macOS 上 ⌘ + Enter）也能提交。文件夹里没有事项时提示“这里没有事项”，还没配置模型时打开设置里的“AI 整理”。
- 提交后和整理请求一样排队、在后台整理，列表顶部显示“整理已有事项”这一行，不用等。整理完不直接改动，而是变成“N 条建议，待确认”。

AI 能做的：

| 操作 | 说明 |
|---|---|
| 新建事项 | 放在这个文件夹里，可以带描述、截止时间、提醒、重复和先后 |
| 改标题、描述 | |
| 截止时间、提醒、重复 | 设置、修改或清除；只改截止时间时，规则同 agent 的 `edit`：带具体时间的保留原来的提醒，重复保留 |
| 完成、重新打开 | 重复的事项完成时顺延到下一次；同时去掉重复的，就是结束重复并完成 |
| 删除 | |
| 移动 | 移到这个文件夹下已有的子文件夹（含更深的层级） |
| 先后 | 加上或去掉前置，只在这个文件夹的事项（含新建的）之间 |
| 顺序 | 重排这个文件夹的手动顺序，依赖仍然优先，见[排序](design.md#排序) |

- 没有具体要求时，只改写标题和描述、补上漏掉的先后，以及标题或描述里写明了的截止时间。其余操作（新建、改已有的截止时间、完成、重新打开、删除、移动、去掉前置、调整顺序）只在要求里说了时才做。
- 点开是“整理建议”：按事项分组，新建的事项各一组，标“新建”；调整顺序单独一组。每组先写 AI 的理由，下面每处修改各一个勾选框，默认全选。新标题和新描述同时给出时算一处，一起采纳：标题里的细节可能挪进了新描述；截止时间、提醒和重复算一处，写成“原来 → 新的”。删除的事项只有“删除”一处。没勾选的新建事项，和它相连的先后也不做。
- 去掉前置和加上前置分开勾选：要求“先做 B 再做 A”，而 A 现在是 B 的前置时，建议去掉 A → B、加上 B → A。只勾了加上、没勾去掉而成环的，应用时提示成环。
- 建议里记着 AI 整理时事项的标题、描述和截止时间（含提醒和重复）。之后改过的（比如在另一台设备上），那处修改默认不勾选，并注明“整理后已改为：……”，由用户决定是否仍用建议覆盖；删除也一样，事项之后改过就默认不勾选。之后移出了这个文件夹的事项，移动那处同样默认不勾选。预览开着时才改的也一样，确认覆盖后又被改了，就再问一次。之后被删除的事项、已经是建议的样子的修改（已经完成、已经在那个文件夹、已经连上或去掉的前置）不再列出。
- “应用 N 处”：所选修改和删除这条请求在同一个改动里，提示条附“撤销”；撤销后修改还原，请求带着原来的建议回来。“放弃”删除请求（可撤销）；“重新整理”丢掉这批建议，按现在的事项再整理一次。
- 没有建议时显示“无需修改”。失败时和整理请求一样可以改要求后重试，没有“按原文添加”。

发给模型的内容：要求、提交时的本地时间、文件夹路径、这个文件夹下所有子文件夹的路径（供移动，最多 200 个），以及这个文件夹里（不含子文件夹）的事项：未完成的最多 50 项，带编号、标题、描述、截止时间、提醒、重复和依赖；最近完成的最多 20 项，只带编号和标题（供重新打开）。描述按顺序累计最多 30000 字，超出的事项和已完成的事项不发描述，AI 也不能改它们的标题和描述：没看到描述就改标题，可能丢掉标题里的信息。

结果是 `{"suggestions": [...]}`，每条是下面三种之一，`reason` 是一句话的理由（模型漏写时留空）：

| 种类 | 字段 |
|---|---|
| 改已有事项 | `number`；只写要改的：`title`、`description`、`due`、`remind`、`repeat`、`repeat_from`（写法同 agent 的 `edit`）、`clear`（要清除的，`due`、`remind`、`repeat` 的列表：模型常给不改的字段写 `null`，所以不用 `null` 表示清除）、`done`（`true` 完成，`false` 重新打开）、`folder`（发过去的子文件夹路径之一）、`requires`（要加的前置，编号或新事项的 `ref`）、`drop_requires`（要去掉的前置的编号）；或者只写 `delete: true` |
| 新建事项 | `ref`（`a`、`b`、`c`……）、`title`；选填 `description`、`due`、`remind`、`repeat`、`repeat_from`、`requires`、`required_by`，先后写编号或 `ref` |
| 调整顺序 | `order`：这个文件夹里未完成事项的编号，按新的顺序 |

先后用 `requires`（前置，要先做完的）和 `required_by`（新事项是谁的前置），不用整理成事项和 agent 计划里的 `after`、`before`：评测里模型常把 `after` 读成“排在它后面的”，先后方向反了。发给模型的事项也用 `requires` 列出已有的前置。

服务端用 agent 工具的同一套代码把结果换成改动操作，按应用时的规则完整校验一遍再存为建议：编号必须是发过去的事项，字段合法，已完成的事项要先重新打开才能改别的，全部应用后依赖不成环，连同删除请求不超过一个改动最多 1000 个操作；和现在一样的修改、已有的依赖、本来就没有的依赖去掉，删除的事项只留下删除，别处给它加或去掉的先后也去掉（删除时它的先后本来就一起去掉）。模型不时把同一事项的几处修改拆成几条，合成一条，两条不同的以后一条为准。新建事项的 ID 在这时生成，应用时照用。

提示词要求和整理请求一致：信息一点不丢（改标题时原标题的每个对象都要留下，输出前逐条对照；合并重复的事项时，删掉的那项的信息并进留下的那项），口语（包括写给 AI 的提示词）改成简洁的书面语，代码、命令、链接和数据原样保留，有先后才连前置；另外，已经清楚的事项不列出，不为改而改。

## 评测

改提示词前后，用同一批样例让真实模型各整理几遍，比较结果。

```sh
export NEXTTODO_EVAL_PROVIDER=deepseek NEXTTODO_EVAL_URL=https://api.deepseek.com NEXTTODO_EVAL_MODEL=deepseek-flash
read -rs NEXTTODO_EVAL_KEY && export NEXTTODO_EVAL_KEY  # 粘贴 API 密钥后回车，不显示，也不进命令历史
cargo run -p nexttodo-server --example ai_eval -- fixtures/ai/organize.json --repeat 3
```

服务商取 `llm.rs` 里预设的 `id`，自定义的接口用 `custom`；思考程度用 `NEXTTODO_EVAL_THINKING`（`off`、`low`、`high`，默认 `off`）。要试别的提示词，加上 `--system <文件>`；只跑部分样例，加上 `--only <id 里的一段>`。

- 整理成事项的样例在 `fixtures/ai/organize.json`，都是虚构的：短得像标题的、语音口语的、几件事有先后或互不相干的、带提示词命令链接的、和文件夹里已有事项有先后的、英文的。每条是服务端发给模型的输入（`local_time`、`folder`、`open_tasks`、`text`）和对结果的要求，没写的不检查：`tasks` 条数范围；`facts` 每项要出现在某个标题或描述里，列出几种可以接受的说法；`verbatim` 要原样出现；`absent` 不能出现（如改口前的说法）；`description: false` 不该写描述；`due`、`remind`；`after`、`before` 是要连上的已有事项；`linked` 新事项之间是否连先后；`order` 按先后列出几个新事项标题里的词，检查它们确实按这个顺序相连；`written: true` 表示原文已经是书面语，描述用原词不算照抄。
- 用户自己的原文不进仓库，可以另放一个同样格式的文件，跟在后面一起传入。
- [整理文件夹](#整理文件夹)的样例在 `fixtures/ai/tidy.json`，也是虚构的，覆盖每种修改和容易出错的情况：改、推迟、清除截止时间，加上时间和提醒，去掉提醒，停止或改变重复，跨年和相对日期，按周几重复（每个工作日、每周一三五）和只改时间时保留它；按给出的顺序串起来、反转、改正、去掉、插入先后，默认要求下补出明显的先后；笼统地说完成了一类事、重复的事项完成、从原因推断删哪些、几项合并、合并后保住先后；移进多层子文件夹、要移去的文件夹不存在；拆成几步、新建带提醒和重复的事项；按编号指事项、按截止时间排序、排序和先后冲突、一条要求里有几件事、大文件夹里只改几项、口语和改口、命令和链接、英文、没有要改的。输入里有 `request`，和服务端发给模型的完全一致（读入时用服务端的代码重新生成一遍核对）；要求有：`allowed` 允许做的种类（`title`、`description`、`due`、`done`、`reopen`、`folder`、`after`、`unlink`、`delete`、`create`、`order`），`deleted`、`deletes`、`done`、`reopened`、`moved`，`due` 改了截止时间的事项和改成的样子，连同提醒和重复一起比（如 `2026-12-01 09:00 !1440 ~1m`，`!` 后是提前几分钟提醒，`~` 后是重复，写法同模型的（按周几的如 `1w:1,3,5`），从完成那天算的加 `/done`，清除写空），`new_due` 新事项标题里的词和它的截止时间，`linked`、`not_linked` 全部应用后要有、不能有的先后（可以经过别的事项；事项写编号，或那时标题里独有的词），`unlinked` 要去掉的前置，`created` 新建条数范围，`untouched` 不该动的事项，`order`，以及和上面一样的 `facts`、`verbatim`、`absent`。
- 检查：先用服务端的同一套代码解析结果、生成要做的改动，再按服务端的规则查操作数（加上删除请求的一个）和先后关系是否成环，服务端会拒绝的算出错；再查条数、信息有没有丢、该不该有描述、描述里的口语词（按字面判断，语气助词只算句尾的，“网吧。”这类也会算进去）、照抄（描述里与原文相同的、6 个汉字以上的片段占描述汉字的一半以上）、描述重复标题、截止时间、提醒和先后。信息用关键词判断，换了说法可能误判，看不准的去 `target/ai-eval/` 里读回答原文。
- 同一提示词每次结果不同，两遍 6 次之间“通过”数能差 6 条左右；比较时每条至少跑 3 次，差别小于这个数就当作一样。
- 接口限流（429）或服务商暂时出错（5xx）时，隔 20、40、60 秒各再问一次；还是常被限流的，改用 `--jobs 1` 重跑，一次问一个。
- 像本机模式那样调用接口，不查公网地址：开着 fake-ip 模式代理的电脑上，域名都解析到 `198.18.0.0/15`。

## 服务端

- 后台一个整理队列：每个用户同时只整理一个请求（有的接口限制并发），全部用户最多同时 4 个；单个请求超时 5 分钟。
- 状态变化都是服务端发起的改动（作者“AI 整理”），走同一套同步：各端实时看到“整理中”“失败”。
- 日志只记请求 ID、状态、耗时、接口的 HTTP 状态和连不上接口时的网络错误，不记原文、结果和密钥。
- 新依赖只有 `chacha20poly1305`。调用接口用命令行已经在用的 `ureq`（rustls，根证书用 webpki-roots，镜像里没有系统证书也能用），在阻塞线程上跑。

## 接口

| 改动操作 | 字段 | 说明 |
|---|---|---|
| `ai_job.create` | `id`、`text`、`local_time`，可选 `folder_id`、`kind` | `local_time` 是提交时的本地时间，如 `2026-11-04 16:30 星期三`；`kind` 是 `organize`（整理请求，默认）或 `tidy`（整理文件夹，`text` 是要求） |
| `ai_job.retry` | `id`，可选 `text`、`folder_id` | 只能对失败的请求和有建议的整理文件夹：带上改过的原文或文件夹（`null` 是根目录）重试，回到等待，原来的建议丢掉 |
| `ai_job.delete` | `id` | 整理中也可以删，结果丢弃 |

开始整理、失败和整理完成是服务端自己做的改动，`actor` 是“AI 整理”。完成的那个改动删除请求、添加事项和依赖，撤销它就是撤销整理结果；整理文件夹完成时只把请求改成 `ready` 并带上建议，应用建议是用户自己的改动。

| 端点 | 说明 |
|---|---|
| `GET /ai/providers` | 预设的服务商 |
| `GET` / `PUT` / `DELETE /ai/settings` | 同步到服务器的配置 |
| `POST /ai/test`、`POST /ai/models` | 用给出的配置（或已同步的配置）测试、列出模型 |
| `POST /ai/jobs/{id}/run` | 仅本机：交出配置，开始整理这个等待中的请求；请求不在等待，或这个用户正有一条在整理时返回 409 |

`/snapshot` 增加 `ai_jobs`，变化增加 `ai_job` 一类。数据表见[数据模型](data-model.md#ai_jobs)。agent 用读工具 `jobs` 查看请求和状态，见 [agent 接入](agent.md#工具)。
