# NextTodo 总体设计

## 定位

个人待办应用，核心是事项之间的先后关系：事项和依赖组成一张有向无环图，首页随时列出“现在能做的事”。文件夹可以无限嵌套，用来分开不同的项目。手机优先，网页、Android、macOS 实时同步，离线也能用。agent 通过 API、命令行和 MCP 管理整个待办。支持多个账号，朋友凭邀请码注册，各用各的。

## 概念和规则

### 文件夹

- 可以无限嵌套，也可以没有文件夹，事项直接放在根目录。默认不建任何文件夹。
- 同一层的文件夹不能重名，名字里不能有 `/`，所以每个文件夹都能用路径（如 `/工作/网站改版`）唯一指明。
- 同一层的文件夹按手动顺序排列。
- 删除文件夹会连同里面的子文件夹和事项一起删除：界面上先确认，删除后能撤销。

### 事项

| 字段 | 说明 |
|---|---|
| 编号 | 每个用户从 1 开始递增的短编号（如 `#42`），由服务端在收到时分配，方便命令行和 agent 引用。离线新建的事项同步后才有编号 |
| 标题 | 必填，单行 |
| 描述 | 可选，Markdown（GFM，支持 `- [ ]` 清单） |
| 文件夹 | 可选，不填就放在根目录 |
| 完成时间 | 为空表示待办，有值表示已完成。状态只由这一个字段决定 |
| 截止时间 | 可选：一个日期，可以再加具体时间（精确到分钟） |
| 提醒 | 可选，只有设了具体的截止时间才能设：截止时，或提前若干分钟 |
| 顺序 | 手动顺序，作为依赖顺序之外的次级排序 |

### 依赖

- `A → B` 表示 A 完成后才能做 B，A 是 B 的**前置**，B 是 A 的**后续**。
- 可以跨文件夹连；事项移到别的文件夹时依赖不变。
- 不能成环：服务端在每次加依赖时检查，成环就拒绝，并返回环上的事项。
- 删除事项时，连着它的依赖一起删除。

### 派生状态

| 状态 | 条件 |
|---|---|
| 可做 | 待办，且所有前置都已完成 |
| 等待中 | 待办，且还有前置没完成 |
| 已完成 | 有完成时间 |

前置没完成也能直接把事项标为完成（现实里经常有跳步），界面上会先确认一次。重新打开一个已完成的事项，它的后续可能因此变回“等待中”。

### 排序

- 文件夹内：待办事项按依赖拓扑排序，没有先后约束的事项之间按手动顺序排。先后约束也算经过文件夹外未完成事项的间接依赖（A → 外面的 X → B，A 仍排在 B 前面）；中间的事项已经完成时，这条路径不再约束。已完成的折叠在底部，最近完成的在前。
- 手动拖动排序只能在不违反依赖的范围内移动，越界时弹回并提示原因。
- “接下来”：只列“可做”的事项。有截止时间的按时间从早到晚排在前面（只有日期的算当天最晚），其余按所在文件夹的顺序和手动顺序排。文件夹的顺序是从根目录开始把文件夹树从上往下展开，父文件夹在子文件夹前面。

## 界面

### 布局

| | 手机 | 电脑（宽屏） |
|---|---|---|
| 导航 | 底部栏：接下来、文件夹、设置 | 左栏：接下来、文件夹树、搜索，设置在左下角。左栏和详情栏都能收起 |
| 内容 | 文件夹逐层点进去，标题栏可切换列表和关系图 | 中栏显示列表或关系图 |
| 详情 | 底部面板，可以上拉展开、下拉关闭 | 右栏 |

### 接下来

首页。列出所有“可做”的事项，每项显示所在文件夹路径和截止时间，已逾期的标红。Android 小组件显示的也是这份列表。

### 文件夹

- 先列子文件夹，再列事项。左侧用“轨道”画出事项之间的先后关系。等待中的事项显示为灰色，并标注“等 N 项”。
- 右滑完成，左滑删除或进入更多操作，长按拖动排序。
- 底部有快速添加栏。连续添加时可以打开“依次排队”，每一项会自动接在上一项后面，手动排一串有先后的事项时很快。

### 关系图

- 显示当前文件夹（可选包含子文件夹）里的事项和依赖。连到文件夹外的依赖显示为半透明节点，标注所在文件夹。
- 布局全自动，用 ELK 分层布局：手机上从上到下，电脑上从左到右。连线不穿过节点，交叉尽量少，链条尽量直，可做的事项排在第一层。不保存节点位置。
- 可以平移和缩放：手机上单指拖动、双指捏合，电脑上用触控板或鼠标。
- 冗余连线默认不画：已有 A→B→C 时就不画 A→C，但数据里保留。
- 已完成的事项默认隐藏，可以切换显示。
- 选中一个节点时，高亮它的全部前置链和后续链。
- 编辑：
  - 点“连线”，再依次点前置和后续两个节点，建立依赖；点连线弹出删除确认；点节点打开详情。电脑和手机相同。

### 详情

标题、完成勾选、所在文件夹、截止时间和提醒、描述（编辑和预览切换）、前置和后续列表（可以搜索添加、单独移除），底部显示创建和最后修改的来源（本人，或哪个令牌）。

### 搜索

按标题和描述搜索全部事项，结果显示文件夹路径。

### 设置

账号和密码、令牌管理、邀请码（仅管理员）、外观（跟随系统、浅色、深色）。

### 视觉和交互

Material 3 的配色和组件，加上 iOS 的结构和手势，支持深色模式。具体规格见[界面](ui.md)。

## agent 接入

所有入口都走同一条改动管线（见[同步](#同步)），agent 做的改动会实时出现在所有设备上。

### 令牌

在设置里生成，自己起名（如“Claude Code”），分只读和读写两种。令牌只在生成时显示一次。改动记录里用令牌名标明来源。

### 命令行、MCP 和工具接口

服务端实现一组工具（查询树、列表、接下来、详情、搜索、关系图、改动记录，增删改事项和文件夹，加减依赖，批量应用，撤销），命令行 `nexttodo`、MCP 端点 `/mcp` 和 HTTP 工具接口调用的是同一份实现，参数、行为和输出一致。命令行是 Rust 写的单文件二进制，只负责收发，启动只需几毫秒。默认输出简洁的中文文本，加 `--json` 输出结构化数据。

批量应用的输入是一份计划：新事项用临时的 `ref` 互相引用，已有事项用编号引用，全部成功或全部不生效，可以先预览：

```yaml
folder: /工作/网站改版
tasks:
  - ref: design
    title: 出设计稿
    due: 2026-11-20 18:00
  - ref: api
    title: 写接口
  - title: 联调
    after: [design, api, 42]
```

工具清单、参数、输出格式和各客户端的配置见 [agent 接入](agent.md)。

### Skill

仓库里的 `skills/nexttodo/` 告诉 agent：

- 什么时候用 NextTodo、用命令行还是 MCP；
- 怎么把一个目标拆成有依赖的事项：标题写成动作，描述写清完成标准，只连真正的先后关系；
- 批量改动前先预览给用户看；
- 回答“现在该做什么”时用 `next`。

### 改动记录和撤销

- 每个改动都记录来源（本人在哪台设备上改的，或哪个令牌）。
- 每次操作是一个批次，一次批量应用也只算一个批次。界面上提示“Claude Code 添加了 12 项”，旁边附撤销按钮；命令行和 MCP 用 `log` 查看、`undo <批次>` 撤销。
- 撤销会生成一组反向改动，作为新批次写入，本身也能再撤销。

## 账号

- 用户名加密码登录，密码用 Argon2id 存储。
- 第一个管理员在服务器上用命令行创建。其他人注册需要邀请码，邀请码由管理员生成，每个只能用一次。
- 登录后每台设备得到一个会话令牌：网页存在 HttpOnly Cookie 里，App 存在 App 私有的存储里（Android 是 SharedPreferences，小组件也要读；macOS 是 WebView 的 `localStorage`），没有另外加密。设置里可以看到并注销各设备。
- 每个用户的数据完全隔离。所有表都带 `owner_id`，服务端在每个查询上按用户过滤。
- 第一版不做共享。以后要做文件夹共享时，加成员表并扩展同步的可见范围即可，现有数据不用改。

## 同步

### 原则

服务端是唯一的权威数据源。客户端在本地保存一份完整副本，所有操作先在本地生效，再在后台同步。

### 改动

- 客户端的每个操作是一个“改动”：带客户端生成的唯一 ID（UUIDv7），内容是操作类型和参数，比如新建事项、修改字段、移动、加依赖。新建的实体也由客户端生成 UUIDv7 作为 ID，离线时就能互相引用。
- 修改只发送改了的字段。服务端按收到的顺序应用，同一字段以后到的为准。
- 服务端在事务里应用每个改动：校验，写入数据，追加到改动日志，然后确认或拒绝。改动 ID 重复时直接返回原来的结果，所以断线重发不会重复生效。
- 改动日志有全局递增的序号，记录实体在改动前后的值，用于增量同步和撤销。日志保留 90 天。

### 连接

- 客户端和服务端保持一条 WebSocket 连接，改动的提交、确认、拒绝和推送都走这一条连接。
- 建立连接时，客户端报告自己已有的最新序号，服务端补发之后的改动；超出保留期就让客户端重新下载完整数据。
- 服务端应用一个改动后，推送给这个用户的其他所有连接，HTTP API 和 MCP 的改动也一样。

### 离线

- 没网时，改动存在本地的待发队列（IndexedDB），界面照常更新。联网后按顺序重发。
- 本地看到的状态 = 服务端最新数据 + 待发队列里的改动。服务端确认后从队列移除。
- 被拒绝的改动（如离线时连出的依赖在服务端成环）会撤回本地效果，并告诉用户哪一项、为什么没有生效。

### 传输

- WebSocket 上只传小的增量，不压缩；完整数据走 HTTP，用 brotli 或 zstd 压缩。数据格式用 JSON。
- App 的前端资源打包在安装包里；网页版通过 PWA 缓存资源。之后打开只同步数据。

## 各端

### 网页

React 单页应用，可以安装成 PWA。第一版网页不做截止提醒。

### Android（包括小米澎湃 OS）

- Capacitor 外壳加载打包在安装包里的前端。
- 截止提醒：每次同步后，在本机排好接下来的提醒，到点由系统弹出本地通知。不依赖谷歌推送。需要授予“精确闹钟”权限。
- 小组件（Kotlin + Jetpack Glance）：
  - 显示“接下来”，每项带标题、文件夹和截止时间；可以直接勾选完成，点 `+` 快速添加，点事项打开 App 里的详情。
  - App 每次同步后把列表写给小组件。小组件自己每 15 分钟刷新一次，也可以点按钮手动刷新；勾选完成时直接调 API，然后刷新。
  - 澎湃 OS 需要给 NextTodo 开“自启动”，后台刷新才不会被系统清掉；App 首次启动时引导设置。
- 用自签名的密钥打正式版 APK，直接安装。密钥不进仓库。

### macOS

- Tauri 2 外壳加载打包在安装包里的前端。
- 菜单栏图标：点开就能快速添加，也可以用全局快捷键呼出。
- App 运行时弹出截止提醒通知；可以设置开机自启。
- 不做苹果签名。首次打开需要右键选“打开”。

## 技术栈

| 部分 | 选型 |
|---|---|
| 核心库 `crates/core` | Rust：数据模型、依赖图算法（判环、拓扑排序、派生状态） |
| 服务端 `crates/server` | Rust：axum、tokio、rusqlite（SQLite，WAL 模式）、rmcp（MCP）、argon2 |
| 命令行 `crates/cli` | Rust：clap、ureq（HTTP）、serde-saphyr（读 YAML 计划） |
| 前端 `apps/web` | React、Vite、TypeScript、Tailwind CSS、Radix、React Flow + elkjs、react-markdown + remark-gfm、vite-plugin-pwa、Lucide（图标）；动效用 CSS 动画 |
| Android `apps/android` | Capacitor，小组件用 Kotlin + Jetpack Glance |
| macOS `apps/desktop` | Tauri 2 |
| 类型共享 | ts-rs 从 Rust 类型生成 TypeScript 类型 |

- 前端离线时需要自己计算派生状态和排序，所以这部分算法在 TypeScript 里也实现一份，和 Rust 版用同一套测试数据校验。
- Rust 部分是一个 Cargo workspace，Tauri 的 `src-tauri` 单独一个（免得 `cargo test` 每次都编译 Tauri）；前端部分是一个 pnpm workspace。

### 哈希用途

只用在这几处：密码用 Argon2id；令牌在数据库里存 SHA-256；前端构建产物的文件名带内容哈希（Vite 默认行为，用于长期缓存）。

## 部署

- 服务端是一个进程、一个端口：同时提供 API、WebSocket、MCP 和网页静态文件。静态文件在构建时预先压缩好，放在镜像里，见[网页端](web.md#部署)。
- 在本机用 `cargo-zigbuild` 交叉编译 x86_64 Linux 静态二进制，打成基于 `scratch` 的镜像，通过 `docker save | ssh rcvps docker load` 传到服务器。服务器上不编译。
- 服务器目录 `/opt/1panel/www/sites/NextTodo/`：`compose.yaml` 和 `data/`（SQLite 数据库和快照）。只监听 `127.0.0.1`。
- 域名 `todo.juniexd.cn`：由 1Panel 反向代理，开启 WebSocket，使用 `*.juniexd.cn` 证书。反向代理要把原来的 `Host` 传过去（或设 `X-Forwarded-Host`），网页的同步连接靠它确认是同源页面。
- 服务端启动时和之后每天用 `VACUUM INTO` 做一次数据库快照，放在 `data/snapshots/snapshot-<Unix 秒>.db`，保留最近 7 份。恢复时停掉服务，用快照替换 `data/nexttodo.db`（并删掉旁边的 `-wal`、`-shm` 文件）再启动。
- 部署用一条命令完成：`deploy/deploy.sh`（`--build` 只在本机构建镜像）。镜像里只有服务端和网页文件，容器以 65534 用户运行，每次部署把 `data/` 整个交给这个用户；服务端端口默认映射到 `127.0.0.1:8790`，第一次部署前确认服务器上没被占用。
- 服务器上由 `deploy/switch.sh` 换版本：先检查新配置，保留旧的 `compose.yaml` 和 `.env`，启动后 30 秒内首页没有响应就换回上一个版本。
- 替换 Vikunja：NextTodo 上线后，把 `/opt/1panel/www/sites/vikunja` 备份到外接盘 `Backups/`，停掉并删除 Vikunja，再把 `todo.juniexd.cn` 的反向代理指向 NextTodo。

## 性能目标

- 打开 App 到看到数据：不超过 300ms（从本地副本读取）。
- 本地操作到界面更新：一帧之内。
- 服务端常驻内存：不超过 30MB。

## 开发顺序

| 阶段 | 内容 |
|---|---|
| 0 | 视觉稿和交互原型（已确认，见[界面](ui.md)） |
| 1 | 核心库和服务端：数据模型、依赖规则、改动管线、REST API、登录和邀请码、测试 |
| 2 | agent 接入：命令行、`apply`、MCP、skill、改动记录和撤销 |
| 3 | 网页：列表、文件夹、详情、Markdown、实时同步、离线 |
| 4 | 关系图：电脑端和手机端两套交互 |

| 6 | Android App、小组件、截止提醒 |
| 7 | macOS App |

## 不做

标签、优先级、看板、甘特图、日历视图、评论、附件、重复任务、子任务（用依赖和描述里的清单代替）、团队协作。第一版不做共享、网页提醒、macOS 小组件和 iOS App。
