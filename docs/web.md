# 网页端

`apps/web`：React 单页应用，也是 Android、iOS 和桌面 App 的前端。产品和界面的规格见[总体设计](design.md)和[界面](ui.md)，同步协议见 [API](api.md#同步协议)。

## 结构

| 位置 | 内容 |
|---|---|
| `src/api/` | HTTP 请求（`http.ts`）；`types/` 是从 Rust 生成的类型，不手改 |
| `src/domain/` | 派生状态和排序（`board.ts`，与 `crates/core/src/board.rs` 一致）、本地应用操作（`apply.ts`）、关系图和轨道画哪些事项和依赖（`graph.ts`）、日期显示（`dates.ts`）、文本校验（`text.ts`，与服务端规则一致） |
| `src/sync/` | 本地副本和待发队列（`store.ts`）、WebSocket 连接（`socket.ts`）、IndexedDB 持久化（`persist.ts`）、附件的文件和上传（`files.ts`）、快速添加的草稿（`drafts.ts`） |
| `src/attach.ts` | 添加附件：起名字、压缩图片、引用的写法 |
| `src/session.tsx` | 登录状态：启动时先用本机数据，再向服务端确认；本地副本和连接的创建 |
| `src/local.ts` | 两个 App 的[本机模式](local.md)：打开 App 里的服务端，进入和离开，备份和恢复 |
| `src/ui/` | 通用组件：图标、勾选圈、分段控件、底部面板、弹窗和对话框、提示条、Markdown 描述 |
| `src/views/` | 页面：登录、手机和电脑两种布局、接下来、文件夹、关系图（`Graph.tsx`，布局在 `graph-layout.ts`）、搜索、详情、设置、各种选择面板 |
| `src/index.css` | 样式：原型的样式原样放在 `components` 层，Tailwind 提供基础样式和颜色工具类 |

技术选型见[总体设计](design.md#技术栈)；路由用 wouter，IndexedDB 用 idb，顺序键用 fractional-indexing，ID 用 uuid（v7）。

选中的事项写在地址的 `?t=<id>` 里：打开详情会加一条历史记录，浏览器的返回关掉详情。Android 的返回键不走历史记录：打开的对话框、弹窗、菜单、详情和文件夹页各自登记一步（`ui/back.ts` 的 `useBack`），分三层：对话框和菜单在最上，详情和关系图的连线状态居中，页面在最下；返回键退最上层里最后登记的一步，没有了就退到后台，见[界面](ui.md#返回)。

## 数据

客户端保存一份完整的本地副本，界面只读本地数据，从不等网络：

- **基线**：服务端确认过的数据（`/snapshot` 加上之后收到的所有变化）和对应的序号 `seq`。
- **待发队列**：本地提交、服务端还没确认的改动，按提交顺序排列。
- **视图** = 基线 + 依次应用待发队列里的改动。基线或队列变了就重新计算，界面始终显示视图。

本地应用操作的规则和服务端一致（`domain/apply.ts`），也产生同样格式的变化，所以本地也能立即撤销。服务端才知道的东西本地不猜：新事项的编号在同步后才有，界面先不显示编号。本地应用失败的改动（比如要改的事项已经被别的设备删了）在视图里跳过，等服务端拒绝后从队列移除并提示。

新建的文件夹和事项总是由客户端给出顺序键（排在最后时用 `generateKeyBetween(最后一个, null)`），这样本地和服务端的顺序一致。

## 同步

1. **启动**：先从 IndexedDB 读出基线和待发队列，马上显示；本地没有数据时请求 `/snapshot`。
2. **连接**：打开 WebSocket `/api/v1/sync`，发 `hello`（带基线的 `seq` 和副本所属的用户 ID）。服务端补发之后的变化，然后持续推送新的变化。
3. **收到变化**：按顺序应用到基线，更新 `seq`；变化对应的改动如果在待发队列里，就从队列移除（它的效果已经在基线里了）。
4. **提交**：本地改动加入待发队列，写进 IndexedDB 后，已连接就发 `mutate`。每次连上（含重连）后，把队列里已经写进本机的改动按顺序全部重发一遍；服务端按改动 ID 去重，重发不会重复生效。添加、移除[共享](design.md#共享)的成员和退出共享不走队列，直接 `POST /mutations`，要联网：用户名对应谁只有服务端知道，退出后这份副本也要整个重新下载。它们的变化照常从推送到达。
5. **拒绝**：从队列移除，视图随之撤回本地效果，提示条说明哪一项、为什么没有生效。服务端只告诉发出它的标签页，这个标签页再广播给其他标签页：它们打开时从本机读进了同一份队列，也要去掉这一项。
6. **重新下载**：收到 `resync` 时重新请求 `/snapshot` 作为基线，待发队列保留。
7. **确认**：收到 `ack` 时，如果它的序号不超过基线的 `seq`，说明基线里已经有这项改动、它不会再作为变化到达（比如新下载的快照里已经包含了它），直接从队列移除。
8. **断线**：指数退避重连（1 秒起，最长 30 秒）；页面回到前台或网络恢复时立即重连。

本地数据每次变化后写入 IndexedDB，按用户 ID 分开存，分两张表（附件的文件另有两张，见[附件](#附件)）：

- `copies`：基线、`seq` 和撤销用的最近改动，每个标签页的会话存自己的一份，互不覆盖。
- `outbox`：待发队列，所有标签页共用一份，每项改动一条记录。改动提交时加进去，写进去以后才发出；任何一个标签页收到它的变化、`ack` 或 `reject` 时删掉，和这个标签页的副本在同一个事务里写入（各标签页收到的每一项变化都要删，不管是不是自己提交的）。改动先进队列再发出，别的标签页收到它时队列里已经有它，删得掉，所以不会因为提交它的标签页没等到确认就关掉而在下次打开时重放。万一两边都有（比如写入失败过），重发时服务端按 ID 去重，`ack` 的序号不超过基线时移除（第 7 条）。

快速添加栏里还没提交的文字和待添加的附件（见[界面](ui.md#其他)）按用户存在 `localStorage`（`sync/drafts.ts`），附件的文件存在 `files` 表，和 IndexedDB 里的数据一起删除。

数据库升级版本时，开着的旧版页面要先关掉连接：本版页面听到新版要升级，关掉连接并刷新成新版；更早的版本不会让路，新版页面这时提示“其他开着的 NextTodo 页面还是旧版本，请关闭它们后刷新这一页”。

写入一次只进行一个，等着的那次带上最新的副本和这期间的所有队列变化。写入失败时提示条告诉用户，改动照常发给服务端，没写进去的内容随下一次写入补上；会话关闭时再补写一次。

打开应用时取 `seq` 最新的副本作为当前会话的副本（删掉其他的），再读出整个待发队列（按改动 ID，也就是提交先后排列：改动 ID 是 UUIDv7，开头是时间，新改动的时间总在队列里上一个之后，时钟往回调了也一样）。还开着的标签页下次改动时会再存它自己的一份；它和当前标签页都会重发队列里的改动，服务端按 ID 去重，只生效一次。

每次登录有一个 ID，和登录的用户一起存在 `localStorage`，同一浏览器的标签页共用。登录 ID 取自本机的一个递增计数（也存在 `localStorage`，在锁内取号；不小于当前的毫秒时间，清掉站点数据以后，新取的号也比还开着的标签页的大），删掉一个用户全部数据的退出也取一个号。登录和退出的广播都带着号，标签页只理会号比自己那次登录大的：退出的号比之前所有登录都大，这个用户已有的标签页都会退出；之后才建立的登录号更大，晚到的广播结束不了它。登录时删掉本机上其他用户的数据，并广播登录的用户，其他用户的标签页随即退出到登录页，同样删掉数据；同一用户还开着的标签页照常使用（Cookie 换成了新登录的，用户相同）。

- **退出登录**：先记下“正在退出”（这次登录的 ID 和用户），再请服务端注销；同一浏览器已经在另一个标签页重新登录过的不注销也不记（Cookie 已经是那次登录的了）。然后停掉连接和保存、等写入完成，删掉这个用户在本机的所有数据，登录信息还属于这个用户就删掉（放在最后），并广播“这个用户退出了”，让这个用户所有开着的标签页都退出，不管属于哪一次登录、是否还持有登录信息（比如断线中的，或者正因登录失效而退出的，这时数据照样删掉）。注销成功、数据删完才清掉“正在退出”的记录；注销没成功（断网、服务端出错或超时）或者中途标签页被关掉，下次打开应用或登录时，按记录删掉那个用户的数据和登录信息、广播，再补上注销，不会凭留下的 Cookie 或数据自动登录。在 App 里退出后进了本机模式的不补：服务器账号的令牌进本机模式时已经删了，这时的会话、小组件和提醒都是本机服务端的，只清掉记录，那个账号的数据在打开本机数据时和其他人的一起删掉。期间如果已经用同一账号重新登录了（登录 ID 变了，用户相同），数据归新的登录，只删自己这个会话的副本。
- **登录失效**（服务端不再接受这次登录，比如在别的设备上退出了它）：立即回到登录页（等着收尾时改动既存不下也发不出），停掉连接和保存；登录信息还是这次登录的就删掉，已经有了新的登录则不动它。本机数据，包括还没发出的改动，都留着，同一账号再登录时接着用，改动补发；换别的账号登录时删掉，收尾时已经有别人登录的也删掉。之后这个用户在本机退出了，照样删掉。
- **换了账号**：另一个标签页换了账号时，这个标签页收到广播就退出；广播漏掉的，启动时的 `/me` 检查或下次连接的 `hello` 也会发现。

几件事用 Web Locks 加锁，各标签页依次执行：登录（连同登录请求和补完没做完的退出）；打开时读登录信息和本机数据，没有就问服务端谁登录着（`/me`）并据此登录；退出时看登录信息、决定要不要注销；结束会话时决定删哪些数据；会话对象也在锁里建立，从它读到的状态之后的每次登录和退出广播它都收得到。这样不会一边刚读到数据、另一边就把它删了，问到的登录状态在用上时也还成立；改变 Cookie 的请求也都在锁内，退出不会注销掉另一个标签页刚建立的登录，也不会在它设好 Cookie 以后再清掉。本机没有数据时，快照在锁外下载，下载完再进锁核对：期间已经退出或换了账号的，不打开。请求（包括读响应）20 秒没完成就按连不上处理，不会无限期占着锁；锁内的请求慢时，别的标签页的登录、打开和退出要等它返回，登录失效的标签页不等，立即回登录页。剩下一个很窄的空隙：结束会话的标签页在拿到锁之前还会写完最后几次保存，如果这时另一个标签页已经用同一账号登录、读走了数据，这几次保存里新加的待发改动不在它的内存里，留在队列里等下次打开时重发。

## 附件

[附件](design.md#附件)的信息和别的数据一样在本地副本里；文件另存在 IndexedDB（`sync/files.ts`），都按 `[用户 ID, 附件 ID]`：`files` 表存文件本身（Blob），加入或下载时写一次，之后不再重写；`fileInfo` 表存大小、是否已上传和最近一次显示的时刻，随时更新。分开是因为 WebKit（Safari、Mac 和 iOS 的 App）里把读出来的 Blob 原样写回记录后，这个文件就读不出来了。

- **添加**（`attach.ts`）：起名字，按服务器的设置压缩（JPEG 用 `<img>` 解码，它按 EXIF 的方向摆正，画到 canvas 上再用 `toBlob` 编码），存进 `files` 表，再提交改动。名字和 ID 当场定下，所以在描述编辑框里粘贴时，引用立即插在光标处；压缩和存进 `files` 表在这之后。存不进去的（压缩后仍超过 20 MB、设备空间不够）提示条写明原因，不加为附件，还在编辑时插入的引用也去掉。会话结束后不再存：正在压缩的文件在退出登录以后不写进本机。每个文件一个只含 `attachment.add` 的改动，排在快速添加的 `task.create` 后面，一个文件传不上去不连累事项和别的文件。AI 整理请求例外：`ai_job.create` 和它的附件在同一个改动里，附件到齐以前请求不会开始整理。服务器的设置在打开会话时取一次（`GET /settings`），存在 `localStorage`，离线时用上次的，没取到过时按默认的压缩。
- **上传**：待发队列照旧按顺序发出，但带 `attachment.add` 的改动要等它的文件都上传完才发，发出后还要等服务端确认，后面的改动才接着发：它可能因为文件不在服务器上要重来（见下），后面对这个附件的改名、删除不能先到。服务端收到的顺序因此还是做的顺序。每个标签页重连后补发队列时都照这个规则，只发到第一个还没确认的带附件的改动为止。
  - 同时只有一个标签页在传：有文件要传的标签页请求 Web Locks 的锁 `upload:<用户 ID>`，拿到锁的从 IndexedDB 的待发队列里按顺序找出还没上传的文件，传一个（`PUT /files/{id}`），在 `fileInfo` 表里记下、广播给其他标签页，各标签页随即发出能发的改动；再重新读一遍队列找下一个，没有了就放开锁。找的时候，`fileInfo` 表里已上传、这个标签页却没听说的（上传的标签页没来得及广播就关了）也当作已上传，刚因为 `file_missing` 清掉记号、还没写进表的除外。别的标签页新加了文件也会请求这把锁，所以持锁的标签页会接着传它们。
  - 连不上服务器、超时（408）、太频繁（429）或服务端出错（5xx）时，像 WebSocket 一样指数退避重试，页面回到前台或联网时立即重试。登录失效（401）按[登录失效](#同步)处理，队列和文件都留着。
  - 服务器明确拒绝（400、403、409、413，反向代理拒绝的 413 也算）时，这个改动按被服务端拒绝处理（[同步](#同步)第 5 条）：从队列去掉，广播给其他标签页，提示条写““图片 1.png”上传失败：{原因}”。改动不改写，只整个去掉，各标签页的队列始终一致。要传的文件已经不在本机的（比如另一个标签页恰好把它从快速添加栏去掉了）也这样处理，原因写“文件已不在这台设备上”，后面的改动照常发出。去掉的不是 AI 整理请求时，它的文件也从本机删掉；是 AI 整理请求时，原文和它的附件都放回那个文件夹快速添加栏的草稿（原文接在已有的文字后面），传不上去的那个记下原因。这些由处理这次失败的标签页做，中途关掉也不丢、不重复：先在草稿里记下这个改动的 ID（AI 整理请求连同原文和附件，`localStorage` 的一次写入），再从待发队列删掉改动。记下的 ID 就是“这个改动已经撤回”：打开应用时，补发和上传之前先从队列里删掉这些改动。持锁的标签页每次找下一个要传的文件前，把记下的改动都从队列里删掉、通知其他标签页也去掉（不管队列里还有没有），通知过才去掉记下的 ID：撤回到一半关掉的标签页不会让别的标签页一直等着，改动也不会因为下次上传成功了而又发出去。
  - 加附件的改动因为文件不在服务器上被拒绝时（`file_missing`：没加为附件的文件 90 天后清理，或者服务器恢复过快照），不去掉这个改动，它后面的改动继续等着：立即清掉它的文件的“已上传”记号（先清内存里的，改动在重传完以前不会再发），重新上传后再发。文件在改动确认前一直留在本机，同一个人重传同一个 ID 也没事。
- **复制**：[复制文件夹](design.md#文件夹)时，副本里的附件不经过这台设备：只在 `fileInfo` 表里记下它复制自哪个附件（大小记 0，`files` 表里没有），上传时换成 `PUT /files/{id}?from=<原附件 ID>`，由服务端复制。复制文件夹是一个改动，同样等这些文件都复制完才发。原附件可能是待发队列里的改动刚加上或撤销删除恢复的，服务端还没有：复制时记下让它出现的最后一个改动，副本的文件等这个改动确认了才复制，没确认时先跳过它、接着传后面的文件，没有别的可传了再按上面的退避过一会儿再看，有改动确认时立即再看；原附件服务端已经有的立即复制，不等队列里别的改动。已经关掉的标签页留下的改动要到下次打开应用才发出，等它的副本不能挡住别的文件。原附件已经删掉、复制不成的，整个改动按上面的拒绝处理。还没复制完时显示原附件的文件。
- **显示**：缩略图、查看器和打开文件先读 `files` 表，没有再下载（`GET /files/{id}`）并存进去，用 Blob 的对象 URL 显示；同一个文件同时只下载一次。打开应用、每次下载以后和加附件的改动确认以后，看一眼本机文件的总大小，超过 500 MB 就删掉最久没显示的，直到 400 MB 以下；加它的改动还在队列里的（确认以前服务器可能还要它重传）、草稿里待添加的不删。缩略图和查看器只用于 PNG、JPEG、GIF、WebP、AVIF，SVG 当作文件。退出登录时和本地副本一起删除。
- **请求**：浏览器里是同源的 `fetch`，桌面 App 用 HTTP 插件（本机模式照样直连），Android 用 WebView 自己的 `fetch`（`window.CapacitorWebFetch`）：CapacitorHttp 经原生和网页之间的桥传整个文件，文件大了会出问题，见 [Android](android.md#附件)；iOS 同样用 WKWebView 自己的 `fetch`，见 [iOS](ios.md#附件)。
- **打开和保存**：浏览器里，上面那几种图片和 PDF 用对象 URL 在新标签页打开，`text/` 开头的换成 `text/plain; charset=utf-8` 再打开，其他（包括 HTML 和 SVG）都下载：对象 URL 属于这个页面的源，服务端给文件加的 `Content-Security-Policy: sandbox` 管不到它，HTML 或 SVG 在里面打开就能以这个页面的身份运行脚本。App 里交给原生部分，见 [Android](android.md#附件)、[iOS](ios.md#附件) 和[桌面 App](desktop.md#附件)。
- **引用**：react-markdown 默认只放行 `http`、`https`、`mailto` 这类链接，`attachment:` 另外放行，渲染成小标签；别的协议照旧去掉。插入引用时，名称里的 `[`、`]`、`\` 前面加 `\`。

## 手动排序

文件夹列表按依赖排好后，没有先后约束的事项之间按顺序键排。拖动一行时，可移动的范围是它直接或经由未完成事项间接等待的最后一项之后、等待它的第一项之前。放下后，只要列表里顺序键沿新顺序递增，按依赖排序的结果就正好是新顺序：保留顺序键已经递增的最长子序列，只给移动的事项和其余少数事项生成新的顺序键，作为一次改动提交。

## 关系图

文件夹页面可以在列表和关系图之间切换，选择记在本机。关系图第一次打开时才加载 React Flow 和 ELK，不拖慢首屏。渲染 Markdown 的 react-markdown 和 remark-gfm 也一样，只有事项描述用到：启动 2 秒后或第一次显示时才加载，启动要解析的脚本因此少了约五分之一。

- **布局**：ELK Layered 在 Web Worker 里计算，只在事项或依赖增减、节点尺寸变化时重新计算，改标题、完成状态和手动顺序不会让图跳动（给 ELK 的事项和依赖按 ID 排序，和列表顺序无关）。新布局算好之前，画面保持上一份布局的位置、尺寸和连线。参数是用几份真实计划（毕业论文、搬家、求职，以及 40 个事项的随机计划）对比后选的：
  - 分层 `LONGEST_PATH_SOURCE`，连通分量不分开排：可做的事项都在第一层，包括和其他事项无关的。
  - 节点放置 `NETWORK_SIMPLEX`：比默认的 `BRANDES_KOEPF` 更紧凑，链条更直。
  - 连线 `SPLINES` 的 `CONSERVATIVE` 模式：曲线绕开节点；`SLOPPY` 模式会斜穿空白，交叉更多。
- **平移和缩放**：React Flow 负责；单指或鼠标拖动平移，捏合或 Ctrl + 滚轮缩放，触控板双指滑动平移。第一屏按原大小显示，缩小到 0.8 倍能放下就缩小，放得下就居中，放不下从第一层开始。
- **画法**：节点和连线由应用自己画，连线直接用 ELK 算出的路径；React Flow 的连接点只是摆设，藏起来。
- 关系图不显示 React Flow 的署名链接（`proOptions.hideAttribution`）：React Flow 是 MIT 许可，个人项目隐藏署名不受限制。

## 登录

网页用 HttpOnly Cookie，脚本拿不到令牌。登录和注册页面提交后服务端设置 Cookie；请求 `/me` 返回 401 时回到登录页。设备名取自浏览器和系统，如“Chrome · macOS”。

## 浏览器

最低支持 Chromium 99，其余按 Vite 默认的 Baseline Widely Available（Safari 16.4、Firefox 114）。Chromium 放低到 99 是为了没有谷歌服务的华为手机：App 的页面跑在系统的 WebView 里，这些手机用华为自己的 WebView，不随 Google Play 更新，华为 WebView 14 报的内核版本是 Chrome 99。

- 语法和 CSS 由构建按这些目标转换（`vite.config.ts` 的 `build.target`），比如媒体查询的范围写法。
- 浏览器自带的方法转换不了，用了 Chromium 99 没有的就会出错。TypeScript 的 `lib` 是 ES2023，更新的方法通不过类型检查；ES2023 给数组加的 `toSorted` 等方法和常见的较新 DOM 方法，由 ESLint 的 `no-restricted-properties` 拦下，清单在 `eslint.config.js`。其他较新的接口，用之前查 MDN 的兼容表，没有的先判断再用。
- 跟着视口变的高度不直接写 `dvh`，写成 `calc(100 * var(--dvh))`：`--dvh` 是 `1dvh`，没有 `dvh` 的内核里是 `1vh`。同一属性先写 `vh` 再写 `dvh` 的回退不管用：构建压缩 CSS 时 Tailwind 按 Chrome 111 优化，会删掉前一条；含 `var()` 的值在旧内核里也不会退回前一条，而是整条失效。
- 占位文字的颜色由应用的样式给出：Tailwind 默认的要混色，Chromium 99 上会和输入的文字一样深。
- 在 Chromium 99 上不生效、影响不大的：`color-mix()`（按下行时的底色、几处光晕动画，构建时生成的后备颜色不混合）、`:has()`、`field-sizing`（详情里的标题编辑框不随内容变高）、`inert`。
- 试的时候用 Chromium 的官方快照，比如 macOS ARM 的 99.0.4844.0：`https://commondatastorage.googleapis.com/chromium-browser-snapshots/Mac_Arm/961656/chrome-mac.zip`，打开开发版服务端提供的构建（`vite build` 的输出）。

## 部署

`pnpm build` 输出到 `apps/web/dist`，并为每个文本文件生成 `.br` 和 `.gz` 预压缩版本。构建时还写出 `app/web.json`，供 Android App 热更新（见 [Android](android.md#更新)），热更新按构建所在的提交区分版本。设置页“关于”里显示的版本号（`import.meta.env.WEB_VERSION`）和服务端一样，是 `deploy/build.sh` 给的 `NEXTTODO_VERSION`，没有它时（开发版）是 `package.json` 的版本 0.1.0。服务端用 `--web <目录>` 提供这些文件：

- 页面地址（最后一段没有扩展名，如 `/folders/<id>`）返回 `index.html`，由前端路由处理。
- 其他路径按文件提供，不存在就是 404；`/assets/` 下带内容哈希的资源成功返回时长期缓存，其余（含 `index.html` 和 Service Worker）每次重新检查。
- `/api`、`/mcp` 下的未知路径返回 JSON 格式的 404，不回退到网页。

开发时 `pnpm dev` 启动 Vite（5173），把 `/api` 和 `/mcp` 转发到本地服务端（8080）。

## 测试

用 Vitest：

- `board.ts` 用 `fixtures/board.json` 校验，和 Rust 版结果一致。
- `apply.ts` 和 `store.ts`：本地应用、撤销、待发队列和基线的合并、拒绝、重连重发。
- `reorder.ts`：随机生成的依赖和顺序键下，任意允许的拖动之后，排序结果正好是拖成的顺序。

界面在浏览器里实际操作验证，不写冻结样式的测试。改了样式或用了较新的接口，在 Chromium 99 里也试一遍，见[浏览器](#浏览器)。
