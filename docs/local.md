# 本机模式

不部署服务器也能用：macOS、Windows、Android 和 iOS App 可以选“在本机使用”，服务端随 App 运行在这台设备上，不用注册登录，数据存在本机；可以[借网盘同步](#借网盘同步)，不开就不和其他设备同步。网页端（浏览器）没有本机模式。总体设计见[总体设计](design.md)，各 App 自己的部分见 [Android](android.md)、[iOS](ios.md#本机模式) 和[桌面 App](desktop.md)。

## 做法

服务端本来就是一个 Rust 库（`crates/server`）。本机模式下，App 在自己的进程里启动它，只监听 `127.0.0.1`；页面和连服务器时一样走 HTTP 和 WebSocket（App 连服务器的那一套），只是地址是本机，令牌由 App 的原生部分交给页面。依赖规则、编号、改动记录和撤销、AI 整理都用同一份代码，前端不另写一套。

手机上也走 HTTP，不另做进程内调用：页面和 Android 的小组件都已经用 HTTP，换传输方式两边都要另写一套。

| | 连接服务器 | 在本机使用 |
|---|---|---|
| 数据在 | 自己部署的服务器，各设备有副本 | 这台设备；借网盘同步时网盘里也有一份 |
| 账号 | 用户名和密码，邀请码注册 | 没有，自动建一个本机用户 |
| 多端同步 | 实时 | 可以借网盘同步，几十秒内到 |
| agent 接入 | 命令行、MCP、HTTP | 桌面上用命令行和 MCP（经命令行转接），App 运行时可用；手机上没有 |
| AI 整理 | 配置可以仅本机或同步到服务器 | 只能仅本机 |
| 更新来源 | 登录的服务器 | GitHub Releases |
| 网页部分热更新 | Android 有 | 没有，随安装包更新 |

## 选择和切换

App 没有记住的服务器地址时（比如第一次打开），登录页先请用户选用法：“在本机使用”（数据只存在这台设备上，无须服务器和账号）和“连接服务器”（在多台设备之间同步，须先部署服务端），下面是官网上“了解两种用法”的链接。选“连接服务器”才显示登录表单，表单下方仍有“在本机使用”，附一行说明“数据只存在这台设备上，不同步”。记住了服务器地址、登录失效或从邀请链接打开时，直接显示登录表单。

模式由一条记录决定，写下或删掉它就是切换的那一刻。其余的事都在之后的启动时按[数据代号](#数据代号)做，重做也没关系，所以中途被打断不会停在一半：

| | Android | 桌面 |
|---|---|---|
| 记录 | Preferences 的 `mode` 为 `local` | 文件 `local/enabled`，由原生部分读写 |
| 进入 | 在当前进程里启动服务端，得知本机用户；写下记录，重启 App | 调用 `start_local`，写下记录，不用重启 |
| 离开 | 一次提交里删掉记录、`server`、`token` 和原生部分记着的代号，重启 App | 删掉记录，重启 App |

iOS 同 Android，只是重启 App 换成在进程里停下服务端、重新加载页面，见下面的重启。

- 桌面的记录不放在页面的 `localStorage` 里：WebKit 过一会儿才把它写进磁盘，离开本机模式后 App 紧接着重启，删掉的记录会回来。
- 在本机模式的登录页（收到 401 之后）登录服务器，也是离开：登录成功后先删记录，再存服务器的会话。Android 删记录时连同 `server`、`token` 一起删，顺序反过来就会删掉刚存的会话。
- **进入**时，页面打开本机用户的数据，和登录另一个账号一样：设备上其他账号留在页面里的数据会删除。其中有没发出的改动（登录失效时会保留）时，先提示“这些改动会丢失”，确认后才进入。已经在本机模式时再点“在本机使用”（比如收到 401 之后），同样是重启，重新签发会话。
- **离开**和登录失效一样：没有令牌，回到登录页，小组件和提醒按现有规则清空。页面里本机用户的数据保留，包括本地副本、待发改动、草稿和设备上的 AI 整理配置：以后再点“在本机使用”就接着用，登录服务器账号时按现有规则删除。本机数据库原样保留。
- 两种模式的数据互不相通。把本机数据搬到服务器第一版不做，见[以后](#以后)。

**重启**：

- 桌面用 Tauri 的 `request_restart`（更新后的“重启”也是它）：先走完退出事件、释放单实例插件的占用，再启动新进程、退出旧的。
- Android 要结束进程、由系统重新创建，不只是重建界面，这样 `Application.onCreate` 和服务端会重新来一遍。做法和 ProcessPhoenix 一样：打开一个在单独进程里的透明界面，由它结束主进程、再打开 App。它自己是可见的界面，不受后台启动界面的限制；用 `AlarmManager` 定时打开会被拦下。澎湃 OS 真机还要验证（见[实验](#实现前先验证)），不行的话，结束进程前提示“请重新打开 NextTodo”。切换和恢复都在下次启动时续做，所以手动打开也一样完成。
- iOS 的 App 不能自己重新打开：在进程里停下服务端，再重新加载页面，页面加载时服务端随之重新启动，见 [iOS](ios.md#本机模式)。
- 两边新旧进程都可能短暂并存，靠[数据目录锁](#启动)保证新进程等旧进程退出后才动数据。

## 本机的服务端

### 启动

服务端库提供一个启动入口，命令行的 `serve` 也改用它，两边只有一份启动代码。本机模式下按顺序：

1. 取得数据目录锁：对 `local/lock` 加系统的独占文件锁（进程退出时系统自动释放），一直持有到进程结束。最多等 10 秒，拿不到就报“NextTodo 的另一个进程还在运行”。旧进程还没完全退出时，新进程就在这里等它。
2. 完成[待完成的恢复](#恢复)。
3. 只读地查看数据库的迁移版本。数据库不存在就新建；版本不合法（负数）或比 App 知道的新（装回了旧版本 App），就不打开、什么都不改，报“数据来自更新版本的 NextTodo，请先更新 App”或“数据库损坏”。
4. 打开数据库，跑迁移。
5. [规范本机用户](#本机用户)。
6. 把上次中断的 AI 整理记为失败。要在开始接受请求之前做完，否则会和刚连上的页面新开始的整理抢在一起。[借网盘同步](#借网盘同步)时不等网盘，只把它们排在同步任务的最前面，见[运行](#运行)。
7. 监听 `127.0.0.1`，端口由系统分配（绑定端口 0），给页面用。桌面上再监听一个给 agent 用的 HTTPS 端口：每次运行新生成一个 CA 和由它签发的证书，CA 的私钥签完就丢，证书的私钥只在内存里；把这个端口的地址和 CA 证书写进 `local/address`（JSON：`{"url": "https://127.0.0.1:<端口>", "ca": "<PEM>"}`），先写临时文件再改名，覆盖上次的（见[agent 接入](#agent-接入)）。这一步失败就返回错误，这时还没启动任何后台任务。
8. 启动每日快照、改动日志清理和 AI 整理队列，开始处理请求，返回地址、本机用户的 ID 和[数据代号](#数据代号)。

服务器上的 `serve` 没有恢复、规范用户和地址文件这几步，监听的是给定地址；数据目录锁是共享的，只是不让[恢复快照](deploy.md#备份和恢复)在它运行时换掉数据库。其余相同。

数据目录是 App 私有目录下的 `local/`。数据库和附件的文件放在其中的 `db/` 子目录里，好让[恢复](#恢复)整个换掉：

```
local/
  enabled              在本机模式时有这个文件（桌面）
  lock                 数据目录锁
  address              给 agent 的地址和这次运行的 CA 证书（桌面）
  db/nexttodo.db       连同 -wal、-shm
  db/files/            附件的文件
  snapshots/           每日快照
  before-restore-<秒>/ 恢复前的旧数据
```

| 平台 | `local/` 在 |
|---|---|
| macOS | `~/Library/Application Support/cn.juniexd.nexttodo/local` |
| Windows | `%APPDATA%\cn.juniexd.nexttodo\local` |
| Android | App 内部存储的 `files/local` |
| iOS | App 沙盒里的 `Library/Application Support/local` |

- 启动失败时不签发会话。页面显示原因，附“恢复备份”和“改用服务器”（拿不到数据目录锁时还有“重试”），最下面是“到 QQ 群反馈问题”的链接（README 里的加群链接）；Android 的小组件显示“打开 NextTodo”。
- 打开 App 时服务端启动了、页面却打不开本机用户的数据（比如页面连不上服务端），也显示这一页，原因写成“打开本机数据失败：{原因}”，并且总有“重试”。不回登录页：那里的服务器地址和账号密码在本机模式下都用不上，只会让人以为要登录。
- Android 上系统可能禁止 App 联网（[澎湃 OS 的“应用联网”](android.md#澎湃-os)），连本机的连接也一起拒绝。原生部分每次把地址交给页面之前先连一下服务端的端口，被系统拒绝（`EACCES`、`EPERM`）就不交，报“系统禁止了 NextTodo 联网……”；这一页除了“重试”，还有“前往设置”，打开本 App 的系统设置页，“应用联网”就在那里。
- 这一页的“改用服务器”就是[离开](#选择和切换)本机模式：删掉记录，重启 App，回到登录页。服务端这时可能已经在运行，要重启才停得下来。
- 本机模式下请求没有回应时，提示“无法连接 App 内置的服务端，请重试”，不说“请检查网络”：服务端就在这台设备上，和网络无关。
- 服务端在进程里一直运行到进程结束，中途不停止；需要换数据库（恢复备份）或离开本机模式时，App 重启。

### 数据代号

- 每个数据库有一个随机的代号，存在迁移新增的单行表里，建库时生成；[恢复](#恢复)时给换上的数据库换一个新的。
- 序号只在同一份历史里有意义，换了数据库，旧的序号就对不上了：可能恰好相等，也可能更小。所以靠代号，而不是靠比较序号，来判断设备上记着的东西还算不算数。
- 原生部分把代号连同地址、令牌、用户 ID 一起交给页面。页面和 Android 原生部分各自记着上次用的代号：
  - **页面**：打开本机用户的数据之前，代号变了就删掉这个用户在页面里的本地副本和待发改动，草稿和 AI 整理配置保留，然后从头下载。用户 ID 和上次的不同（恢复了另一台设备的备份）时，按登录另一个账号处理。先删，再记下新代号，中途被打断下次重删。
  - **Android 原生部分**：在 `onCreate` 里，代号变了就清空小组件的列表、全部提醒（连同稍后提醒）和[原生没发出的改动](android.md#原生发出的改动)，然后记下新代号。小组件记着的序号、提醒用的事项编号和改动都属于换掉的数据。页面打开会话后，会照常重写小组件、重排提醒。
- 离开本机模式时，Android 原生部分记着的代号随模式记录一起删掉：之后服务器账号会写入自己的列表和提醒，再进入本机模式时就会清掉它们，哪怕本机数据库没换过。页面记着的代号保留，它对应的本地副本也保留着，回来接着用。

### 本机用户

每次启动时规范数据库，第一次启动和恢复备份后也一样：

- 正好一个用户，用户名 `local`，显示名“本机”。没有就建一个；多于一个的数据库不打开，恢复前已经挡住（见[恢复](#恢复)）。
- 不是管理员；密码存空串，任何密码都验证不过（`verify_password` 解析不了空串，登录照常回答“用户名或密码错误”）；删除全部邀请码。所以登录、注册、邀请这些不需要令牌的接口，在本机模式下做不成任何事，不必单独关掉。
- 删除同步到服务器的 AI 配置。本机没有解密用的密钥，从服务器数据库恢复来的配置用不了。
- API 令牌保留，桌面上 agent 用的就是它们。

### 令牌和端口

- 原生部分在服务端启动成功后签发设备会话（设备名“本机”）。签发和作废之前的设备会话在同一个事务里。然后把地址、令牌、用户 ID 和代号交给页面：
  - Android 在 `Application.onCreate` 里签发，写进 Preferences 的 `server`、`token`。
  - 桌面在 App 运行期间第一次调用 `start_local` 时签发，之后的调用拿到同一个，主窗口和[菜单栏小窗](desktop.md#菜单栏小窗)共用；在登录页点“在本机使用”或在启动失败页点“重试”时重新签发（`renew`），之前的那个可能正是打不开的原因。调用排队依次执行。服务端只在第一次调用时启动；启动失败的，下次调用再试。
- 页面拿到之前不发任何请求。桌面上的页面不保存它们，每次加载都重新取。
- Android 上，一个进程里 `server` 和 `token` 只会被删掉（离开本机模式、登录失效），不会换成别的值；换值只在重启后的 `onCreate` 里。所以小组件分两次读这两个值，读到的要么是同一次启动的，要么缺一个，缺了就照常显示“打开 NextTodo”。
- 本机模式下正常不会收到 401。万一收到，按现有的“登录失效”处理：回到登录页，待发改动保留，再点“在本机使用”会签发新的会话。

端口在两个平台上都由系统每次分配，不用固定端口：固定端口可能被别的程序先占住，App 就启动不了，agent 还会把令牌发给它。桌面上的 agent 经命令行找到这次的地址，见[agent 接入](#agent-接入)。

**安全的依据是令牌。** 能连到这个端口的，有这台设备上的任何程序、浏览器里的网页（包括借 DNS 重绑定访问 `127.0.0.1` 的网页）、Android 上的其他 App。它们没有令牌，做不了任何事：

- 会话令牌只在 App 的进程和私有存储里，API 令牌只在用户自己配置的 agent 那里。agent 只在核对过证书的 HTTPS 连接上发令牌。
- 本机模式下没有人用密码登录，这个地址下不会有会话 Cookie，浏览器替网页带不上任何凭据。

**不在防护范围内的**：以同一用户身份运行的不可信程序。它们本来就能读 App 的数据文件和私有存储。桌面本机模式假定这台电脑上没有这种程序；Android 上每个 App 互相隔离，不存在这个问题。

### 可靠性

- SQLite 是 WAL 模式（`synchronous=NORMAL`）。进程被杀不丢已确认的改动；断电或系统崩溃时，可能丢失最后一刻的改动。
- 快照和改动日志的保留和服务器一样：启动时和之后每天快照一次，保留 7 份；改动日志保留 90 天。快照和数据在同一台设备上，只防数据库损坏，不防设备丢失，所以另有[备份](#备份和恢复)。恢复前的旧数据（`before-restore-*`）不算快照，不自动删除。
- 日志不写用户内容，级别和服务器一样默认是 info。桌面写标准错误，连同插件的日志和检查更新失败的原因，`RUST_LOG` 可以调；从终端启动 App 才看得到。Android 经 `android_logger` 写 logcat，标签是 `NextTodo`。iOS 写系统日志（子系统 `cn.juniexd.nexttodo`）。

## 桌面

- Tauri 外壳（`src-tauri`）直接依赖 `nexttodo-server`，在 Tauri 自带的 tokio 运行时上启动服务端。
- 页面加载时读到本机模式的记录，先调用 `start_local`，拿到地址、令牌、用户 ID 和代号后，再打开会话。开机自启（`--hidden`）时页面同样加载，所以 App 只在菜单栏或托盘里时服务端也在运行。
- HTTP 插件已经允许任意 `http(s)://` 地址，不用改。

### 页面直连

页面连本机的服务端用的是普通 HTTP，经过代理就会把会话令牌和数据交给代理；代理在别的机器上时还根本连不上。所以本机模式下页面的请求一律直连：

- HTTP：桌面的 HTTP 插件默认用系统代理和代理环境变量，而且不会自动绕开 `127.0.0.1`。本机模式下每个请求带上一个显式的代理设置 `{all: {url: <随便一个地址>, noProxy: "127.0.0.1"}}`，并且不跟随重定向（`maxRedirections: 0`）。
  - reqwest 只要给了显式的代理，就不再用系统代理和环境变量；`noProxy` 又让到 `127.0.0.1` 的请求直连。
  - `noProxy` 要写 IP 本身：`*` 只匹配域名，对 IP 地址不起作用。
  - macOS 和 Windows 上已实测。
- WebSocket 走 WebView 自己的网络。macOS 的 WebKit 和 Windows 的 WebView2 上实测，连 `127.0.0.1` 都不走代理，给 WebView 单独设了代理也一样。
- Android：系统设了代理（Wi-Fi 代理或全局代理）时，`HttpURLConnection` 默认连 `127.0.0.1` 也走代理。CapacitorHttp 和小组件都用它发请求，而 CapacitorHttp 不能按请求关掉代理。所以本机模式下：
  - 页面的 HTTP 改用 WebView 自己的 `fetch`。Capacitor 给 `fetch` 打补丁之前，把原来的存在了 `window.CapacitorWebFetch`。WebView 连 `127.0.0.1` 不走代理，也不算混合内容。
  - 本机的服务端在手机上允许来源跨域（Android 的 `https://localhost`，iOS 的 `capacitor://localhost`），请求头 `Authorization` 和 `Content-Type`。
  - 顺带，写请求也能按时取消了：CapacitorHttp 不转发 `AbortSignal`。
  - 小组件的请求用 `Proxy.NO_PROXY`。
  - Android 16、17 的模拟器上已实测。

### agent 接入

端口每次启动都变，agent 的配置里写不了地址，改由命令行去找这次运行的 App。设置里照常生成 API 令牌，鉴权和连服务器时完全一样。

- **给 agent 的端口用 HTTPS**：桌面上服务端另外监听一个端口，只给 agent 用。每次运行新生成一个 CA 和由它签发的证书（包含 IP `127.0.0.1`），私钥都不落盘；地址和 CA 证书写在 `local/address`（见[启动](#启动)）。
  - 命令行只信任这张 CA 证书，不用系统的信任库，握手成功才发出令牌和请求内容。rustls 不支持把终端证书本身当作信任的根，所以要多一个 CA。
  - 地址文件可能已经过时（App 崩溃后留下的，或者 App 刚好退出），旧端口也可能已经被别的程序占了。对方拿不出这次证书的私钥，握手就失败，什么都不会发出去，也没有回复可以伪造。
  - 只保护令牌是不够的：发错了端口，请求里的标题、描述、搜索词也会被别人收到，回复也可能是伪造的。先确认对方是这次运行的 App，这些才都挡得住。
  - 证书不是秘密，地址文件只要求别人改不了：数据目录、地址文件和它的临时文件从创建起就只有本用户能写，Windows 上要核对继承来的权限。命令行按平台知道 `local/` 在哪。
  - 页面照旧用普通 HTTP，连另一个端口。它的地址是原生部分在监听后当场交给它的，不会过时；请求不经代理，见[页面直连](#页面直连)。
  - 手机上没有 agent 接入，不监听这个端口。
  - 握手在各个连接上并发进行，10 秒超时，一个慢的连接挡不住别的。
  - 新依赖：生成证书的 `rcgen`，在 axum 上跑 TLS 的 `tokio-rustls`。加密后端统一用 ring，和桌面现有的 rustls 一致：`tokio-rustls` 默认带的 aws-lc-rs 要关掉，两个后端同时启用时 rustls 选不出默认的，会 panic。这些放在服务端库里一个只有桌面启用的 feature 下，Android 的动态库不带。
- **命令行**：`NEXTTODO_URL` 是 `local` 时，连这台电脑上本机模式的 App。
  - 令牌只从 `NEXTTODO_TOKEN` 读，不用配置文件里连服务器的那个。
  - 地址文件里的地址必须正好是 `https://127.0.0.1:<端口>`（端口不为 0，没有用户名、路径和查询），否则报错。不经代理（不管 `HTTPS_PROXY` 等环境变量），不跟随重定向，收到 3xx 当作错误。
  - 每个地址文件用一套新的连接配置，已经和上一张证书握过手的连接不再复用。
  - 每条命令只读一次地址文件。网络出错后的自动重试（幂等键不变）只发给同一次运行：App 中途重启过的，重试会因为证书对不上而失败，就报错，不会把同一个写操作再发给恢复后的另一个数据库。证书对不上时不重试，同一次运行里重试也不会成功。
  - 没有地址文件或连不上时，报“无法连接本机模式的 NextTodo：App 未运行或正在启动”。握手失败时报“本机 NextTodo 的证书不匹配，App 可能刚重启过”。地址文件格式错误或读取出错时，如实报告。
- **MCP**：新增 `nexttodo mcp`，一个 stdio 的 MCP 服务器。
  - 它从标准输入逐行读消息，每条都重新读一次地址文件，按上面的方式连到这次运行的 App，POST 到 `<地址>/mcp`，再把回复写到标准输出。App 重启、换了端口和证书也照常。标准输出只写协议消息，诊断信息写标准错误。
  - 请求头：`Accept: application/json, text/event-stream`、`Content-Type: application/json`，初始化之后带上协商好的 `MCP-Protocol-Version`。
  - 服务端是无状态的，直接回 JSON（`crates/server/src/mcp.rs`）。通知得到 202，什么也不输出；回复不是 JSON 的当作错误，现在的工具不会这样回。
  - 连不上或 HTTP 出错时：带 `id` 的请求回一个同样 `id` 的 JSON-RPC 错误，写明原因；通知只把错误写到标准错误。
  - 不自动重试：MCP 的写操作没有幂等键，重发可能做两遍。
- **令牌页给出的写法**（本机模式下）：
  - 命令行用的环境变量：`NEXTTODO_URL=local` 和 `NEXTTODO_TOKEN`，写法和现在一样，macOS 写进 shell 配置，Windows 用 `setx`。
  - Claude Code：`claude mcp add nexttodo --env NEXTTODO_URL=local --env NEXTTODO_TOKEN=<令牌> -- nexttodo mcp`。
  - Codex：`codex mcp add nexttodo --env NEXTTODO_URL=local --env NEXTTODO_TOKEN=<令牌> -- nexttodo mcp`。
  - 都要先装命令行，见 [agent 接入](agent.md#命令行)；不在 `PATH` 里的，写完整路径。
- 不支持直接调 HTTP 工具接口：地址和证书每次都变。
- 没用 Unix 套接字和 Windows 命名管道：命名管道在 App 没运行时同样能被别的用户抢先创建，要另做校验；HTTPS 加证书在两个平台上是同一种做法，也不用另做一套传输。
- 命令行随桌面 App 安装，Windows 上运行中的 `nexttodo mcp` 不妨碍 App 更新，见[桌面 App](desktop.md#命令行)。

## Android

- 服务端编译成 `arm64-v8a` 的动态库（`cargo-ndk`），打进 APK 的 `jniLibs`。真机和 Apple 芯片 Mac 上的模拟器都是 arm64，只出这一种。
  - 用单独的 profile `android`：`lto = "fat"`、`codegen-units = 1`、`opt-level = "s"`、`strip = true`，动态库 7.3 MB；不开这些是 11.3 MB。按 16 KB 页对齐，Android 15 起的 16 KB 页设备也能加载。
  - Gradle 在构建前编译它（任务 `rust`），所以打 APK 还是一条命令。
  - APK 里按默认不压缩存放，装好后不用解压，安装包大约大 7 MB（现在 6.5 MB）。压缩存放能小一半，但装好后要解压出来，多占一份空间。
- JNI 的胶水代码放在单独的小 crate `crates/android` 里，对应 Kotlin 的 `LocalServer`，只有几个入口：启动、签发会话、备份、准备恢复、提交恢复。出错时抛出带着给用户看的原因的异常。
  - JNI 按函数名找入口，入口要不改名地导出（`#[unsafe(no_mangle)]`），Rust 把它算作不安全代码。所以这个 crate 不用工作区禁止 `unsafe` 的设置，改为默认禁止、在每个入口上单独放行；除此之外没有 `unsafe`。
  - 启动、签发会话和备份在 crate 自己的 tokio 运行时上同步执行，服务端的后台任务也在这个运行时上，一直到进程结束。
- 新增自定义的 `Application`（`NextTodoApp`）。`Restart` 所在的单独进程什么也不做，否则它会等主进程手里的锁。主进程的 `onCreate` 里读到本机模式时，按顺序：
  1. 清掉 Preferences 里旧的 `server` 和 `token`。
  2. 同步启动服务端（[启动](#启动)的全部步骤）。模拟器上实测：已有数据库时约 1 毫秒；新建并迁移时 12～19 毫秒；偶尔有一次 60 毫秒。
  3. 按[数据代号](#数据代号)决定是否清空小组件和提醒。
  4. 签发会话，写入新的 `server` 和 `token`。

  启动失败时只记日志：页面打开时向原生部分要地址、令牌、用户 ID 和代号（插件的 `openLocal`），这时在同一进程里再试一次，仍然失败就显示原因；拿不到锁时点“重试”也是这样。
- App、小组件、提醒、定时刷新，不管哪个让进程启动，都会先经过 `onCreate`。所以小组件读到的时候，服务端一定已经在了。小组件照旧从 Preferences 读地址和令牌，经 HTTP 取列表、勾选完成，进行中的操作照旧按令牌判断是否作废。
- 每次启动按当前模式重新登记小组件的定时刷新：本机模式下不要求联网。用更新已有任务的方式登记，已装的 App 原来那个要求联网的任务也会改过来。
- 网页版本：本机模式只用 APK 自带的网页，网页和服务端打在同一个 APK 里，版本始终一致。
  - 本机模式下启动时，删掉从服务器热更新下来的版本，把 `serverBasePath` 换回 APK 自带的。
  - 本机模式下不查 `web.json`。
- 明文 HTTP：网络安全配置只放行到 `127.0.0.1` 的明文请求，其他地址照旧只能用 HTTPS。
- 进程在后台会被冻结或结束，服务端只在进程存在时运行，不保证 AI 整理在后台做完：
  - 冻结期间整理暂停，回到前台后接着做，或者按超时失败。
  - 进程被结束的，下次启动时记为失败（“整理中断”），可以重试。
- 设置里不显示令牌一组：服务端只监听本机，手机上又没有命令行，agent 接不进来。

## 界面

本机模式下设置页的不同（其余见[界面](ui.md)）：

- 最上面的账号卡片换成“本机模式”卡片，写明数据只存在这台设备上；点开是说明、“借网盘同步”“备份”“恢复”“改用服务器”。
- 开着[借网盘同步](#借网盘同步)时，卡片写明同步到哪个网盘、上次同步的时间；出错时（连不上、要更新 App、文件夹换过）写原因。点开的“借网盘同步”里是配置和“停止同步”。
- 不显示：修改密码、显示名、邀请码、已登录的设备、退出登录。
- agent 接入：桌面照常显示，手机不显示。
- AI 整理不显示保存位置，配置只存在页面里（“仅本机”）：本机服务端没有加密用的密钥（`NEXTTODO_SECRET_KEY`）。清除配置的确认也不提服务器。

## 备份和恢复

备份和恢复由原生部分直接调用服务端库，不走 HTTP 接口：桌面是 Rust 命令，Android 经 JNI，iOS 经 C 接口。桌面的保存和打开对话框用 Tauri 官方的 `tauri-plugin-dialog`，由 Rust 命令打开，路径不经过页面；Android 用系统的存储访问框架，iOS 用系统的文件选择器，都经临时文件交给 Rust。

### 备份

1. 等待待发队列清空，包括正在保存的改动。被拒绝的照现有方式提示。本机服务端一直在，通常立即完成；几秒内没清空就提示稍后重试。
2. 服务端用 `VACUUM INTO` 在数据目录里生成一份数据库的副本 `backup.part`，和每日快照一样，运行中也能得到一致的副本；再和副本的 `files` 表里列出的、还没清理的附件文件（在用的，和删除后还能撤销的）一起打成一个 tar，打完删掉副本。借网盘同步时，其中本机还没有的先从网盘下载，下载不了就提示稍后重试；文件清单就取自这份副本，所以备份过程中读入的改动不会让两者对不上。tar 的第一项是 `backup.json`（`{"format": 1}`，见[格式版本](#格式版本)），然后是 `files/<附件 ID>`，最后是 `nexttodo.db`，这样在两项之间截断的备份没有数据库，恢复时认得出。附件的文件写入后不再变，不用停下服务端；这期间被每天的清理删掉的跳过，它们在副本里也早已没人用；还在用的文件不见了，备份失败。
3. 保存到用户选的位置，默认文件名 `NextTodo-备份-<日期>.tar`：先写成旁边的 `<文件名>.partial`，再改名换上，不会留下写了一半的备份。选在数据目录 `local/` 里就提示，不保存：那样可能换掉正在用的数据库。

备份里有：

- 全部数据，包括改动记录，撤销还能用。
- 附件的文件。
- API 令牌，只存哈希，恢复后重新生效。

备份里没有 AI 整理的配置：它存在页面里，所以备份里也没有 API 密钥。恢复成别的本机用户（备份来自另一台设备）后，要重新填写。

### 恢复

不需要服务端在运行，所以启动失败时也能恢复。

**准备**：选一个备份文件，放到数据目录里的临时目录 `restore.part/`（同名的旧目录先删掉）：tar 的解开：第一项必须是 `backup.json`，格式不比 App 新（新了就提示“请先更新 App”），之后只能有 `nexttodo.db` 和 `files/<附件 ID>` 这些普通文件，各一份，附件的文件不超过 20 MB，有别的就不认；以前版本的备份是单独的数据库文件，原样复制。在这份副本上检查和准备，任何一步不通过，就删掉 `restore.part/`、提示原因，什么都不改：

1. 是 SQLite 数据库，`integrity_check` 和 `foreign_key_check` 通过。
2. 迁移版本合法，不比 App 新；表结构和同一版本的空数据库完全一致。这一条认出它是 NextTodo 的数据库，以前各版本的备份和服务器数据库也认得出。
3. 正好一个用户。
4. tar 里的附件文件和数据库的 `files` 表对得上：每个都在表里，大小和记录的一样；还在用的一个不缺，没人用的可以缺（备份时正好被清理掉）。
5. 跑迁移，规范为本机用户，换一个新的数据代号。恢复的即使是这台设备自己的备份，也和现在的数据不是同一份历史。

单用户的服务器数据库也能这样恢复，相当于把自己部署的数据搬到本机；多用户的不行。这样恢复的没有附件的文件，附件打开时提示“文件不存在”。准备完关闭数据库，不留 `-wal`，把文件写入磁盘（`fsync`）。

**提交**：用户确认“会用备份替换这台设备上的全部数据”，然后：

1. 把 `restore.part/` 改名为 `restore/`，从这一刻起恢复算是提交了。改名失败就提示原因，会话照常。之后同步 `local/` 目录失败只记日志：恢复已经提交，断电最多让它作废。
2. 页面结束会话，不再发送改动。
3. App 重启，第 2 步出错也照样重启。

确认框写明两件会丢的事：

- 还没发出的改动会丢弃，找不回来；队列里有改动时写出有几项。从设置里恢复时，准备之前已等待队列清空，通常没有；启动失败时恢复，就可能有。
- 现在的数据会留在 `local/` 下的旧数据目录里；从确认到 App 重启之间，小组件、AI 整理和桌面上的 agent 写入的改动，也只在那里，不会出现在恢复后的数据中。

**完成**：新进程拿到数据目录锁之后、打开数据库之前，按目录的状态续做。每一步都是 `local/` 里的目录改名：

| 状态 | 做法 |
|---|---|
| 有 `restore.part/` | 没提交的准备，删掉 |
| 有 `restore/`，也有 `db/` | 把 `db/` 改名为 `before-restore-<Unix 秒>/`（已存在就加序号，不覆盖），连同 `-wal`、`-shm` 原样保留，不自动删除；再做下一行 |
| 有 `restore/`，没有 `db/` | 把 `restore/` 改名为 `db/` |
| 没有 `restore/` | 没有要做的 |

- 保证的是进程在任何一步被结束后都能续做。断电只尽力：macOS 和 Android 上每次改名后同步 `local/` 目录；Windows 上同步目录要用不安全的系统调用（项目禁止 `unsafe`），只靠 NTFS 自己的日志。断电后回到哪一步，按上表照样续做。
- 任何一步失败（比如文件被占用、磁盘出错）就停下：不打开数据库，也不删任何东西，按启动失败显示原因，下次启动再从当时的状态续做。

**之后**：

- 页面和 Android 原生部分看到新的[数据代号](#数据代号)，丢掉旧的本地副本、待发改动、小组件列表和提醒，从头下载。
- 恢复时还没发出的改动不会作用到恢复后的数据上：用户要的是换成备份里的数据。从设置里恢复时，准备之前会先等待队列清空，所以通常没有这样的改动。

## 更新

- 本机模式没有服务器可以取更新，改从 GitHub Releases 取：用固定地址 `https://github.com/JunieXD/NextTodo/releases/latest/download/<清单>` 取 `android.json`、`desktop.json`。GitHub 会转到最新 Release 里的同名文件，不调 GitHub API。
- `deploy/build.sh` 构建时，Release 的文件里加上更新要用的全部文件：两份清单，以及 macOS 的更新包 `NextTodo.app.tar.gz` 和 `NextTodo-x64.app.tar.gz`（APK 和 Windows 安装程序本来就在）。清单里的下载地址写成这个 Release 的完整地址（`…/releases/download/v<版本>/<文件>`），不依赖跳转后的相对路径，所以清单和安装包不会对错版本。
- 只有发布 Release 才有新版本，平时部署到自己服务器的不算。
- 比较版本的规则和连服务器时一样：Android 看原生版本，桌面看版本号。iOS 不管连不连服务器都从 GitHub 取，见 [iOS](ios.md#更新)。
- 校验照旧：APK 由系统校验签名，桌面更新包用更新密钥校验。信任的是 GitHub 的 HTTPS 和这两种签名。
- 检查失败（比如连不上 GitHub）时不打扰，下次照常再查；设置页“关于”里显示上次检查的时间和结果，连不上时写“无法连接 GitHub”，点按“App 版本”可以立即再查，见[总体设计](design.md#app-更新)。
- Android 的网页部分不热更新，随 APK 更新（见[网页版本](#android)）。

## 借网盘同步

本机模式下可以借 S3 兼容的对象存储或 WebDAV 网盘（如坚果云）在几台设备之间同步，网盘里也就有了一份数据。不用部署服务器，也不用账号。每台设备照旧在本机运行服务端，页面、小组件、提醒和桌面上的 agent 都还连本机的服务端。上传的数据不加密，网盘的服务商看得到内容。

### 排定先后

网盘里的文件夹存着一串编号连续的提交，每个提交是一批改动。各设备按编号的顺序把它们写进本机的数据库，所以共享的数据完全一样：网盘替代了[同步](design.md#同步)里服务端排定先后的那部分。

- **同步任务**：本机服务端里改共享数据的请求都排进同一个同步任务，一次一个：页面的改动、HTTP 和工具接口、AI 整理的每一步（开始、失败、建议、结果）、AI 整理的说明、附件的清理。同步任务之外没有别的写入共享数据，所以执行时的数据就是写入网盘时的数据。本机的数据（见[共享的和本机的](#共享的和本机的)）照常直接写。
- **写入**：轮到一个请求时，在最新的数据上照常执行（校验、编号、工具按当前的路径和编号生成操作，都用现有的代码），在事务里得出提交的内容后回滚，再把它写成下一个编号，[只在不存在时写入](#只在不存在时写入)。写成了，再按[读入](#读入)的规则写进本机，这才回确认。
- **编号被占了**：先读入别的设备的提交。其中有这个请求的改动 ID 的，说明它已经写成（上次结果不明时，被原样重写的），不再执行；否则在新的数据上整个重新执行（工具也重新生成操作），再写下一个编号。重新执行时不成立的，照常拒绝。
- **结果不明**：写的请求发出了、没收到回应（超时、断线）时，不重新执行，先读这个编号：是自己的提交（按提交的 ID）就是写成了；是别人的就是没写成，按上一条处理；不存在，就把同一个提交原样再写一次，迟到的那次写入和它一模一样，谁先到都对。读请求本身失败的，等能读到再定。所以一个提交不会写成两次，也不会卡在这个编号上。
- **读入**：别的设备不重新执行操作，照着提交写库。提交是写入的设备在同样的数据上得出的，所以几台设备的 App 版本不同、规则改过也不会分叉。

谁在等结果：

- **页面**：`mutate` 交给同步任务后，连接照常处理别的消息和推送；写成了回 `ack`，不成立回 `reject`。连不上网盘时什么也不回，页面的待发队列照旧留着它，重连后重发，按改动 ID 去重，和连服务器时一样。所以这期间改的只在页面里，小组件和提醒要等写进网盘后才看到。
- **HTTP 和工具接口**（桌面上的 agent、小组件）：最多等 15 秒，到时就回答，不等手头的网盘请求。还没发出的，从同步任务里拿掉，返回 503 `unavailable`“暂时连不上网盘，改动没有生效”；已经发出、结果不明的，返回 503 `outcome_unknown`，带上改动 ID：这个提交照上面的规则原样重写，写成了就生效；编号被别人占了的，这项不再重做。用同一个改动 ID 重发的，排在它后面，等它有了结果再按 ID 去重，所以只生效一次，见[重试](agent.md#重试)。小组件和提醒里的“完成”照[原生发出的改动](android.md#原生发出的改动)存下，用同一个改动 ID 补发，同步开着时补发要求联网。
- **AI 整理的开始**（`POST /ai/jobs/{id}/run`）：最多等 15 秒，没写成就返回 503，页面过一会儿再试，和离线时一样。开始仍留在同步任务里，配置只在内存里跟着它，什么时候写成就什么时候开始整理；这期间再试得到 409“正在整理另一条请求”。整理出的结果写不进网盘时一直重试，不丢。

### 只在不存在时写入

两台设备同时写同一个编号时，必须只有一台写成，否则一台的改动会被覆盖掉，几台的数据从此不一样。

- **S3**：PUT 带 `If-None-Match: *`，已经存在时返回 412；同一个文件正有另一次写入时返回 409，这时文件可能还没有，按结果不明处理，读一下再定。列目录（ListObjectsV2）一页最多 1000 项，按续页标记读完。
- **WebDAV**：先 PUT 到 `tmp/<随机>`，再 `MOVE` 到目标，带 `Overwrite: F`，已经存在时返回 412（坚果云返回 409）。没写成的删掉自己的临时文件。别的文件（附件、快照、`nexttodo.json`）在 WebDAV 上也这样写，读到的总是完整的文件。
- WebDAV 不用 `If-None-Match: *` 和 `If-Match`：坚果云不理会前者，照样覆盖；后者单独用时管用，几台同时写时不止一台写成。见[已验证的](#实现前先验证)。

### 网盘里的文件

```
<文件夹>/
  nexttodo.json                {"format": 1, "id": "<这一代的代号>"}
  <代号>/log/<编号>.json        一次提交，编号从 1 起连续
  <代号>/snapshots/<编号>.db.gz 快照：读入到这个编号时的数据库，gzip 压缩
  <代号>/files/<附件 ID>        附件的文件
  tmp/<随机>                   WebDAV 写入时的临时文件
```

- **一代**：每次在空文件夹上开启都是新的一代，代号随机，`nexttodo.json` 指着当前这一代。各设备只读写开启时记下的那一代的目录：文件夹被删掉重建后，旧设备迟到的写入落在旧一代的目录里，混不进新的历史。
- **提交**：`{"id": "<提交的 ID>", "format": 1, "items": [...]}`，一个提交最多 50 项，写入时把同步任务里排着的一起执行、一起写。每项是一种：
  - 改动 `{"mutation": {id, at, via, ops, effects}}`：`at` 是写入设备上的毫秒时间，`via` 是 API 令牌名。工具接口的回复（重发同一个幂等键时原样返回）里有本机的批次号，不传上网盘，只记在执行它的设备上。
  - AI 整理的说明 `{"note": {folder_id, text, at}}`。
  - 清理附件 `{"purge": [{id, type, size, created_at, unused_at}, …]}`：清理掉的文件的记录，见[附件](#附件)。
- **快照**：写成编号是 200 的倍数的提交的设备，读入后接着上传这个编号的快照，只在不存在时写入。快照是数据库的副本（和每日快照一样用 `VACUUM INTO`），清掉其中本机的部分，表结构不变：本机的表清空，改动日志的令牌和工具接口的回复、用户的密码哈希和数据代号清空，服务器的设置恢复默认，只上传了、还没加为附件的文件记录删掉。哪些是本机的，按 `drive/snapshot.rs` 里给每张表的归类：实体的表整张共享（它们的每一列本来就随提交传给别的设备），其余的表要么整张是本机的，要么逐列写明；新加的表、这些表新加的列没归类，测试就不通过。[落后很多](#运行)的设备换上快照时，按同一份归类替换共享的表，顺序也取自这里：每张表排在它引用的表后面，排错了测试也不通过。快照里的序号只在这份快照内部有意义。
- **清理**：上传了快照的设备接着在后台清理，不占同步任务。网盘里留最新的两份快照；更早的，从最早的起，等它编号的那个提交早于 90 天（和改动日志的保留期一致），先删它前面的提交，再删它。提交从它往前 200 个一组地删，删到已经删过的那组为止：每组最后一个提交最后删，所以它还在就说明这组还没删完（删到一半被打断，或者那组的快照没传上去），一起删掉。还删掉一天以前的临时文件；`nexttodo.json` 还指着自己这一代时，也删掉一天以前、没被它指着的代号目录（开启到一半被打断、两台同时开启时输了的留下的）。文件夹里只有 NextTodo 自己的东西（见[开启](#开启)），所以按名字认得出。提交的 ID、临时文件和代号都是 UUIDv7，时间从中读出。对象存储没有真正的文件夹，删目录时逐个删其中的文件。

### 共享的和本机的

| 数据 | | 说明 |
|---|---|---|
| 文件夹、事项、依赖、附件、AI 整理请求、AI 整理的说明 | 共享 | |
| `files` 的记录，包括已清理的 | 共享 | 只上传了、还没在提交里加为附件的除外，它们是本机的暂存；文件本身在本机按需下载 |
| AI 整理请求的 `run`（新加的列） | 共享 | 正在整理的这一轮：开始那次改动的 ID |
| 改动日志 `mutations` | 共享 | 除了序号、令牌和工具接口的回复：序号由各设备自己编；别的设备写的，令牌记为空字符串，来源照旧显示令牌名；回复只在执行的设备上 |
| `users` 的 `next_task_number` | 共享 | 本机模式只有一个用户；其余的列由[规范本机用户](#本机用户)决定 |
| `users` 的 `pruned_seq`、`deliveries` | 本机 | 由本机的序号算出 |
| 令牌和会话、邀请码、`users` 的密码哈希、服务器的设置（上传前压缩图片）、数据代号、同步的记录 | 本机 | |
| AI 整理的模型配置 | 本机 | 本来就只在页面里 |

- 同步的记录是两张本机的表：这一代的代号和读到的编号，和读入的数据在同一个事务里写；这台设备开始的整理（开始那次改动的 ID），在写开始整理的提交之前记下。
- 网盘的配置（方式、地址、账号、密码或密钥、文件夹）存在 `local/sync.json`，只有本用户能读写。它不在 `db/` 里，所以备份、快照和恢复都不带它，也不会传上网盘。

### 读入

每个提交在一个事务里写完，同时记下读到的编号。照着每一项：

- 实体的变化：新建的插入，修改的按 `after` 更新，删除的删掉。
- 事项的编号：`next_task_number` 推进到不小于出现过的最大编号加一。
- 附件：新建时把这个文件的记录写成提交里的值（类型、大小来自附件，时间是提交的 `at`；上传的设备已有的记录也改成这样），标为在用；删除时标为不用，从提交的 `at` 起算。所以各设备的 `files` 一样，不看上传和读入的时间。
- 改动日志：每个改动记一行，ID、操作、变化、来源和时间都照提交，自己执行的工具接口再记上回复；`deliveries` 给本机用户记一行。然后推送给页面。写进网盘后、写进本机前被打断的，回复就没了，同一个幂等键重发时只回批次号，和超过保留期的一样。
- 说明写进 `ai_notes`；清理附件把这些文件的记录照提交写成已清理的（记录留着；没有记录的，比如别的设备只上传过的，照样补上），删掉本机的文件。
- AI 整理请求变成整理中时，`run` 记为这次改动的 ID；离开整理中时清空。

测试比较各设备全部共享的表，不只是实体。

### 附件

- 提交里新建的附件（页面上传的、工具接口加的），写提交之前先把本机的文件[只在不存在时](#只在不存在时写入)传到 `<代号>/files/<附件 ID>`。已经有了的读回来比较：一样的是上次没收到回应时传上去的；不一样的是别的设备用同一个 ID 传的，加这个附件的改动返回 409“网盘里已经有另一个文件用了这个附件 ID”，同一批的其他改动重新执行。工具接口试执行时已经把文件存进本机的 `files/`，回滚不影响它；重新执行时生成新的附件 ID，用不上的文件照本机的规则一天后删。
- **按需下载**：本机没有的文件，服务端读的时候先从网盘下载，存进本机的 `files/`。大小和记录的不一样（没传完、被换掉）的不存，这次读取出错，下次再下载。页面显示、AI 整理读图、工具接口和备份都经过这一处，所以别的设备加的图片，这台设备没显示过也能拿去整理。界面和连服务器时一样（见[界面](ui.md)）。
- **清理**：每天清理文件时，90 天没人用的文件不直接删，而是作为一项清理附件排进同步任务。它和别的提交一样在最新的数据上执行，这期间被撤销删除、又用上的不在其中。写成后，各设备读入时把记录标为已清理、删掉本机的文件，写成的设备再从网盘删掉这些文件，已经不在的不算错。已清理的记录一直留着，本机的清理和快照都不删它。清理附件之后，撤销删除这些附件时照常提示文件不存在，各设备一样。
- 清理过的 ID 留着已清理的记录，不能再上传或加为附件（返回 409“附件 ID 已被用过”）：否则这个 ID 重新上传、加回来以后，写成清理的设备迟到的删除会删掉网盘上又在用的文件。
- 本机的暂存：`files/` 里没有记录的文件（写到一半的）照本机的规则一天后删。只上传了、90 天没加为附件的，也作为清理附件写进网盘，和上面一样在最新的数据上判断：提交被拒绝前它可能已经传上网盘，别的提交也可能用着同一个 ID，所以不在被拒绝时直接删，只有写成了清理、标为已清理之后才删网盘上的文件。

### 开启

- 设置的本机模式卡片里点“借网盘同步”，选 WebDAV 或 S3：
  - WebDAV：地址（坚果云是 `https://dav.jianguoyun.com/dav/`）、用户名、密码（坚果云要用应用密码）。
  - S3：接口地址、区域、存储桶、Access Key ID、Secret Access Key、地址风格（默认虚拟主机 `<存储桶>.<接口地址>`，MinIO 这类自建的选路径）。
  - 文件夹：默认 `NextTodo`，不存在就建。
- 先检查网盘：在 `tmp/` 里写一个文件，再按[只在不存在时写入](#只在不存在时写入)的做法往它上面写一次，必须被拒绝，然后删掉它。不满足的（服务不支持，或者 S3 存储桶开了版本控制），提示“这个网盘不能用来同步：同时写入时会互相覆盖”，不开启。连不上、账号不对，如实提示。
- **没有 `nexttodo.json`**：文件夹里只能有 `tmp/` 和开启到一半留下的代号目录（名字是 UUIDv7），有别的就提示“这个文件夹里有别的文件，请换一个空文件夹或新的文件夹名”，不开启：网盘里的清理按名字删，不能删到别人的文件。可以开启时开启新的一代，把这台设备的数据传上去。开启由同步任务来做：从这一刻起，共享数据的写入都排在它后面等着。它先把这台设备正在整理的 AI 整理请求记为失败（“开启同步，整理中断”：这一轮不在网盘记着的轮次里，它迟到的结果不再写入，之后停止同步也一样），再截下快照 0，生成代号，把快照 0 里用到的附件文件和快照 0 传进 `<代号>/`，先在本机记下这一代（同步的记录），最后只在不存在时写 `nexttodo.json`，写成了才算开启，排着的写入从此写进网盘；写完之前进程就退出了的，重启后照记下的这一代同步，`nexttodo.json` 没指着它（没写成）就按[换了一代](#运行)停止同步、提示重新开启；开启失败的，照旧直接写本机。上传时不占着数据库，页面和小组件照常读。写不成或者没收到回应时，先读回 `nexttodo.json`：代号是自己的，就是写成了；是别的，说明别的设备刚开启了，删掉自己传的这一代，按下一条处理，再问一次；读不到就什么也不删，稍后再试。中途被打断的，留下的目录没有被指着，不算数，再开启时重新来。
- **已经有 `nexttodo.json`**：确认“会用网盘里的数据替换这台设备上的全部数据”。然后像[恢复](#恢复)的准备那样，在 `restore.part/` 里做一份新的数据库：下载最新的快照，读入之后的提交，规范本机用户，换一个新的[数据代号](#数据代号)（不沿用快照里的），记下同步的记录；本机的令牌和会话不带过去，数据换成了另一个本机用户的，桌面上 agent 的 API 令牌要重新生成。再按恢复的提交和完成换上，App 重启，现在的数据留在 `before-restore-*`。所以两台各自有数据的设备不合并：先在一台上开启，别的加入时用网盘里的。
- `format` 比 App 知道的新：提示“请先更新 App”，不开启。

### 运行

- 本机服务端运行时每 30 秒查一次下一个编号；写入后、App 回到前台时马上查（Android 的界面 `onResume`、iOS 回到前台、桌面的窗口获得焦点时，原生部分告诉服务端）。所以别的设备的改动几十秒内到，不是实时。
- **连不上网盘**（离线、网盘出错、限流）：同步任务按退避重试，429 和 503 也一样。谁在等结果、等多久，见[做法](#排定先后)。
- **落后很多**：同步任务启动时和一天没连上网盘之后，先列一次快照。要读的提交在 200 个以上（最新的快照比读到的编号大 200 以上）时，改为读最新的快照和之后的提交；提交被删掉的（离线超过 90 天）总在最新的快照 400 个以前，也是这样。先判断这一条再读写，所以不会往删掉的编号上写。换上时在一个事务里用它们替换本机全部共享的数据，本机的表不动，数据代号不变。改动日志里本机已有的改动保留原来的序号（工具接口回复里的批次号仍然对得上），新的接着本机的序号往后编，`deliveries` 随之重建，`pruned_seq` 推到最新，于是页面收到 `resync`，重新下载、保留待发队列并重发，和连服务器时服务端恢复了快照一样，不用重启 App。重发的改动在新数据上重新执行，不成立的照常拒绝、提示；小组件和提醒里没发出的“完成”也照常补发。
- **更新版本写的**：读到[格式](#格式版本)比 App 新的 `nexttodo.json`、提交或快照时停下，提示“请先更新 App”，更新后接着读。
- **换了一代**：同步任务启动时和每次写入前（包括结果不明、原样重写之前）读 `nexttodo.json`，代号和这台设备记着的不同（文件夹被删掉、由别的设备重新开启）时停止同步，提示重新开启，排着的改动照[停止同步](#停止)时处理。对象存储往删掉的文件夹里照样写得进，所以每次写入前都确认，改动不会写进没人读的旧一代；只读不写的设备在启动时发现。
- **iOS**：在后台被挂起时不同步。
- **Android**：进程在后台被冻结时不同步。小组件的定时刷新先让服务端查一次（经 JNI，最多等 5 秒），再取列表；同步开着时定时刷新要求联网。
- **AI 整理**：开始整理也要先写进网盘，所以两台设备不会同时整理同一条，写成的那台来整理。写之前先在本机记下这一轮（开始那次改动的 ID）。整理的结果和失败只在请求的 `run` 还是这一轮时才写，所以请求被删掉又撤销、在别的设备上重新开始以后，旧一轮迟到的结果不会算进新一轮。启动时，本机记着的、`run` 还是那一轮的记为失败，写成了开始、还没写进本机就退出，之后又跳过这个提交读了快照的，也认得出来。这些失败不等网盘，排在同步任务的最前面，服务端照常启动，离线时也能用；这台设备之后再开始的整理都排在它后面。别的设备在整理的不动；那台设备不再用了，整理中的请求可以照常删除。停止同步时，先把这台设备正在整理的记为失败，写不进网盘的留在别的设备上，可以删除。
- 改动日志的清理照旧由各设备按自己的时钟做，只影响这台设备上撤销能回溯多远：撤销只在发起的设备上执行，别的设备照着结果写，不会因此分叉。

### 停止

- 设置里“停止同步”：不再读写网盘，本机数据保留，网盘里的不动。再开启时按“已经有 `nexttodo.json`”处理。
- 停止前先下载还用得上的附件里本机还没有的文件（包括删除后还能撤销的，见[清理](#附件)），停止后就不能再从网盘下载了；同步任务停下后再下载一次停止过程中读入的，这次下载不了的，同步接着开着，停止时没能写进网盘的整理失败重新排上。网盘里本来就没有的文件不算。下载不了（离线、网盘的账号失效）时提示“有附件的文件还没有从网盘下载下来，现在停止同步，这些附件就打不开了”，确认后照样停止；这些附件之后在这台设备上打不开，在空文件夹上重新开启时，新的一代里也没有它们的文件。
- 停止时等同步任务停下、忘掉网盘之后，才照常直接写本机，所以停止以后同步任务不会再写本机。手头的网盘请求不等，它若写成了提交，别的设备照常读入。排着的改动返回服务器错误，页面重发后直接写本机。
- 同步开着时不能恢复备份，“恢复”提示先停止同步：恢复的数据和网盘里的不是同一份历史。同步时做的备份里的同步记录，恢复时清掉。要让所有设备用一份备份，先停止同步、恢复，再在一个空文件夹上开启，其他设备改为同步这个文件夹。
- 备份时，本机还没有的附件文件先从网盘下载，见[备份](#备份)。
- 离开本机模式时同步跟着停，回来后接着同步。

### 用量

- 平时每台设备 30 秒一个请求；写一个提交，先读下一个编号和 `nexttodo.json`，再写，S3 上共 3 个请求，WebDAV 上 4 个。坚果云复用连接时一个请求约 0.4～0.9 秒，新建连接约 2 秒，所以改动写进网盘要一两秒，页面上照常立即生效。
- 坚果云的 WebDAV 免费版每 30 分钟限 600 次请求，付费版 1500 次（见坚果云帮助中心《坚果云第三方应用授权 WebDAV 开启方法》）；免费版据第三方说法每月上传 1 GB、下载 3 GB。实测 20 分钟约 570 个请求没有被限流，平时远用不到；附件最占流量。
- 网盘里的提交用编号直接读写，不列目录：坚果云列目录时据说只返回前 750 个文件。

## 格式版本

写到 App 之外、会被别的版本读到的数据，各有一个格式版本：

| 数据 | 版本在哪 | 什么时候加一 |
|---|---|---|
| 网盘文件夹的布局 | `nexttodo.json` 的 `format` | 文件夹里放什么、放在哪变了 |
| 网盘里的提交 | 每个提交的 `format` | 提交的内容有旧版本读不了的变化，包括操作和变化的结构 |
| 网盘里的快照、备份里的数据库 | 数据库的迁移版本 | 加了迁移 |
| 备份文件 | 第一项 `backup.json` 的 `format` | tar 里放什么、怎么放变了 |
| 网盘的配置 | `local/sync.json` 的 `format` | 配置的结构变了 |

- 新版本读得了所有旧格式；读到比自己新的不读也不改，提示“请先更新 App”。网盘的配置比 App 新时本机服务端不启动，和数据库比 App 新时一样。
- 数据库的迁移版本只管数据库：只改本机的表也要加迁移，提交的格式不受影响；只改提交里的结构不用加迁移，但要加提交的格式。
- 提交格式 1 留了一份样例（`fixtures/drive-commits-1.json`，各种项和大多数操作都有），测试用当前的代码读入它。改了操作或变化的结构，这个测试失败，就该加一版格式，并且旧的样例照样读得进。

## 实现前先验证

还没做的，要在澎湃 OS 真机上做：

- 自动重新打开 App（ProcessPhoenix 的做法）：澎湃 OS 对后台启动和自启动管得比原生 Android 严。不行的话，改成提示手动重新打开。
- 页面直连、`Application.onCreate` 的耗时，在真机上再看一眼。

借网盘同步还没验证的：

- 阿里云 OSS、腾讯 COS：文档里只有各自的禁止覆盖请求头，没说支不支持 `If-None-Match: *`，开启时的检查会认出不支持的，有账号时再测。Cloudflare R2 据第三方说法支持。
- 坚果云限流时返回什么、要等多久。
- Android 后台定时刷新时先同步一次的耗时。

借网盘同步已验证的（2026-11-17，用 curl）：

- 坚果云的 WebDAV（`dav: 2`）：
  - PUT 带 `If-None-Match: *` 时不理会，已有的文件照样被覆盖（204）；`MKCOL` 已有的文件夹也返回 201。
  - `If-Match`：版本号不对时返回 412，版本号只认不带引号的（`GET` 的响应头和 `PROPFIND` 的 `getetag` 里有，`HEAD` 没有），由内容决定。但 8 个请求带着同一个版本号同时写，8 轮里有 3 轮不止一台写成（最多 3 台），不能用来排先后。
  - `MOVE` 带 `Overwrite: F`：目标已存在时返回 409，不存在时 201。8 个请求同时移到同一个名字，23 轮都正好一个写成。
  - 上传中途断开，不留下半个文件。
  - 能删文件和子文件夹（连同里面的），顶层文件夹（坚果云的同步文件夹）删不掉（403）。
  - 复用连接时一个请求约 0.4～0.9 秒，新建连接约 2 秒（经本机的代理）。20 分钟约 570 个请求，没有被限流。
- MinIO（Homebrew 里 2025-10-15 的版本；官方已不再提供下载）：PUT 带 `If-None-Match: *`，已存在时 412；8 个请求同时写同一个名字，30 轮都正好一个写成。

恢复时被打断后续做，由 Rust 测试在三个平台上覆盖；断电时能保证到哪一步无法实测，按[恢复](#恢复)里写的尽力而为。

已验证的（2026-11-06，macOS、Windows 11、Android 16 和 17 模拟器，用单独的实验程序）：

- 桌面重启：用 `request_restart` 时，单实例插件不会把新进程当成第二个实例；新进程等旧进程退出后拿到锁（Windows 上等了 83 毫秒）。
- 端口：监听期间别的用户抢不走。macOS 上连同一用户都绑不上同一个地址和端口；Windows 上另一个用户绑同一地址被拒（tokio 不设 `SO_REUSEADDR`），不用设 `SO_EXCLUSIVEADDRUSE`。两边绑 `0.0.0.0`（macOS 上还有 `[::]`）的，都收不到发往 `127.0.0.1` 的连接。
- 页面直连：HTTP 插件默认会把到 `127.0.0.1` 的请求发给代理环境变量里的代理；带上[页面直连](#页面直连)的设置后直连，也不跟随重定向。WebKit 和 WebView2 的 WebSocket 和 fetch 连 `127.0.0.1` 都不走代理，WebView 单独设了代理也一样。页面（`tauri://localhost`、`http://tauri.localhost`）连 `ws://127.0.0.1` 不算混合内容。
- 命令行连 HTTPS 端口（ureq，只信任这次的 CA，不经代理，不跟随重定向）：连对的运行正常；连另一次运行的端口，握手失败，对方收不到请求；连只收字节的程序，对方只收到握手的开头，没有令牌和路径；有代理环境变量也直连；一个连接不握手，不影响别的连接。生成证书在 macOS 上约 1 毫秒，Windows（ARM 上模拟 x64）上第一次 65 毫秒。
- 加密后端：桌面现有的依赖加上 `tokio-rustls`（只开 ring）和 `rcgen`，仍然只有 ring，rustls 不会 panic。
- Windows 上的改名：进程刚退出就改名它用过的目录，200 次都成功；一边读地址文件一边改名替换它，2000 次没有失败，也没读到写了一半的内容。
- Android 的页面：`https://localhost` 的页面连 `ws://127.0.0.1`、`fetch` `http://127.0.0.1`，都不算混合内容，WebView 的混合内容设置是默认最严的那档也一样。WebView 的请求在系统设了代理时也直连。带 `Authorization` 头的跨域请求（有预检）正常。
- Android 的明文配置：只放行 `127.0.0.1` 的网络安全配置生效，`HttpURLConnection` 连 `127.0.0.1` 正常，明文连别的地址被拒。
- Android 的代理：系统设了代理时，`HttpURLConnection` 默认连 `127.0.0.1` 也走代理，`Proxy.NO_PROXY` 时直连。由此改了[页面直连](#页面直连)的做法。
- Android 的启动：`Application.onCreate` 里同步启动服务端，加载动态库约 0.5 毫秒，启动见 [Android](#android)。冷启动到页面显示 570～710 毫秒，大部分是 WebView 初始化。
- Android 的重启：ProcessPhoenix 的做法在 16 和 17 上都能用，新进程约 0.1 秒后启动，拿锁不用等；`AlarmManager` 定时打开被后台启动限制拦下（即使创建 PendingIntent 时声明了允许）。
- Android 动态库的大小：见 [Android](#android)。

## 测试

- Rust：
  - 启动顺序：拿不到锁时等待和报错；拒绝版本不合法和版本更新的数据库，并且没写过它；先处理中断的整理，再接受请求；监听失败时没有启动后台任务；地址文件在监听后才写，每次运行换一张证书。
  - 命令行和 `nexttodo mcp`：地址文件过时或缺失时报错，不发出任何内容；设了代理环境变量也直连；App 重启后自动重试失败、不发给新的一次运行；`nexttodo mcp` 的请求、通知、出错时回的 JSON-RPC 错误，以及 App 重启后连上新端口。
  - 规范本机用户：没有密码、不是管理员、没有邀请码和服务器上的 AI 配置。签发会话时作废旧的。
  - 备份：拒绝存进数据目录。
  - 恢复的准备：拒绝多用户、版本更新、表结构不符、损坏的文件；接受以前版本的备份和单用户的服务器数据库；换了数据代号。
  - 恢复的完成：在每次改名前后打断，再启动都能接着做完；改名失败时停下、什么都不删。
  - 借网盘同步，用内存里的假网盘（同样只在不存在时写入，能模拟断线、写成了却没有回应）起三个本机服务端：
    - 同时写入只有一个写成，其余读入后重新执行，不成立的被拒绝；工具接口重新执行时按新的数据生成操作。
    - 最后几台全部共享的表完全一样（不只是实体：编号、`files`、改动日志）。
    - 写成了却没有回应、写进网盘后写进本机前被打断：再读到时认出是自己的，不重复生效；没写成、这个编号一直不存在的，原样重写后之后的请求照常前进；HTTP 的请求还没发出时返回“没有生效”且之后不写，发出了时返回“可能已经生效”。
    - 页面的改动在连不上时一直等，不被拒绝；读到更新版本的提交时停下。
    - 落后很多时读快照：共享的数据换掉，本机的表和数据代号不变，页面收到 `resync`，重发的改动照常生效；之前工具接口回复的批次号仍能撤销对的那一批。
    - 加入时换了数据代号；开启到一半被打断、两台同时开启、`nexttodo.json` 写成了却没有回应、换了一代后旧设备迟到的写入。
    - 清理附件：离线的设备不会删掉别处撤销后又在用的文件；清理过的 ID 不能再上传和加回来；两个改动同时把同一个上传加为附件，只有一个写成，文件仍能下载。从没显示过的附件，AI 整理和备份照样读到。
    - AI 整理：只有一台开始整理；删掉又撤销、在别的设备上重新开始后，旧一轮的结果不写进去；写成了开始、没写进本机就退出、又跳过它读了快照的，重启后记为失败。
- 网页（Vitest）：代号变了时删掉副本和待发改动、保留草稿和 AI 配置；换了用户时按登录另一个账号处理；不在本机模式时登录服务器不碰模式记录；恢复没提交时会话照常，提交了就重启。
- 实际操作：
  - 两个 App 上：选本机模式、增删改、重启后数据还在、改用服务器再切回来、备份恢复（包括恢复这台设备更早的备份、另一台设备的备份，以及启动失败时恢复）、更新检查。
  - 桌面上的命令行和 MCP（Claude Code、Codex）：App 在运行、没在运行、正在启动、中途重启这几种情况。
  - Android 的小组件和提醒：进程被结束后从小组件拉起、完全离线时刷新、从旧版本升级后定时刷新不再要求联网，以及恢复和切换模式后不留旧列表和旧提醒。
  - 借网盘同步：手机和电脑经坚果云、MinIO 同步，新设备加入、离线改动后联网、两边同时改、附件、AI 整理、停止后再开启。
