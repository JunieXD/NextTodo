# 网页端

`apps/web`：React 单页应用，也是 Android 和 macOS App 的前端。产品和界面的规格见[总体设计](design.md)和[界面](ui.md)，同步协议见 [API](api.md#同步协议)。

## 结构

| 目录 | 内容 |
|---|---|
| `src/api/` | HTTP 请求；`types/` 是从 Rust 生成的类型，不手改 |
| `src/domain/` | 派生状态和排序（`board.ts`，与 `crates/core/src/board.rs` 一致）、本地应用操作（`apply.ts`）、日期显示（`dates.ts`） |
| `src/sync/` | 本地副本和待发队列（`store.ts`）、WebSocket 连接（`socket.ts`）、IndexedDB 持久化（`persist.ts`） |
| `src/ui/` | 通用组件：图标、勾选圈、底部面板、对话框、提示条、分段控件等 |
| `src/views/` | 页面：登录、接下来、文件夹、详情、搜索、设置 |

技术选型见[总体设计](design.md#技术栈)；路由用 wouter，IndexedDB 用 idb，顺序键用 fractional-indexing，ID 用 uuid（v7）。

## 数据

客户端保存一份完整的本地副本，界面只读本地数据，从不等网络：

- **基线**：服务端确认过的数据（`/snapshot` 加上之后收到的所有变化）和对应的序号 `seq`。
- **待发队列**：本地提交、服务端还没确认的改动，按提交顺序排列。
- **视图** = 基线 + 依次应用待发队列里的改动。基线或队列变了就重新计算，界面始终显示视图。

本地应用操作的规则和服务端一致（`domain/apply.ts`），也产生同样格式的变化，所以本地也能立即撤销。服务端才知道的东西本地不猜：新事项的编号在同步后才有，界面先不显示编号。本地应用失败的改动（比如要改的事项已经被别的设备删了）在视图里跳过，等服务端拒绝后从队列移除并提示。

新建的文件夹和事项总是由客户端给出顺序键（排在最后时用 `generateKeyBetween(最后一个, null)`），这样本地和服务端的顺序一致。

## 同步

1. **启动**：先从 IndexedDB 读出基线和待发队列，马上显示；本地没有数据时请求 `/snapshot`。
2. **连接**：打开 WebSocket `/api/v1/sync`，发 `hello`（带基线的 `seq`）。服务端补发之后的变化，然后持续推送新的变化。
3. **收到变化**：按顺序应用到基线，更新 `seq`；变化对应的改动如果在待发队列里，就从队列移除（它的效果已经在基线里了）。
4. **提交**：本地改动加入待发队列，已连接就立即发 `mutate`。每次连上（含重连）后，把队列里的改动按顺序全部重发一遍；服务端按改动 ID 去重，重发不会重复生效。
5. **拒绝**：从队列移除，视图随之撤回本地效果，提示条说明哪一项、为什么没有生效。
6. **重新下载**：收到 `resync` 时重新请求 `/snapshot` 作为基线，待发队列保留。
7. **断线**：指数退避重连（1 秒起，最长 30 秒）；页面回到前台或网络恢复时立即重连。

基线、`seq` 和待发队列每次变化后写入 IndexedDB，按用户 ID 分开存；退出登录时清空。

## 登录

网页用 HttpOnly Cookie，脚本拿不到令牌。登录和注册页面提交后服务端设置 Cookie；请求 `/me` 返回 401 时回到登录页。设备名取自浏览器和系统，如“Chrome · macOS”。

## 部署

`pnpm build` 输出到 `apps/web/dist`，并为每个文件生成 `.br` 和 `.gz` 预压缩版本。服务端用 `--web <目录>` 提供这些文件：带内容哈希的资源长期缓存，`index.html` 和 Service Worker 不缓存；不是 `/api`、`/mcp` 的未知路径返回 `index.html`，由前端路由处理。

开发时 `pnpm dev` 启动 Vite（5173），把 `/api` 和 `/mcp` 转发到本地服务端（8080）。

## 测试

用 Vitest：

- `board.ts` 用 `fixtures/board.json` 校验，和 Rust 版结果一致。
- `apply.ts` 和 `store.ts`：本地应用、撤销、待发队列和基线的合并、拒绝、重连重发。

界面在浏览器里实际操作验证，不写冻结样式的测试。
