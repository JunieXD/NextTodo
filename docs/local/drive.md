# 借网盘同步

本机模式下可以借 S3 兼容的对象存储或 WebDAV 网盘（如坚果云）在几台设备之间同步，网盘里也就有了一份数据。不用部署服务器，也不用账号。每台设备照旧在本机运行服务端，页面、小组件、提醒和桌面上的 agent 都还连本机的服务端。上传的数据不加密，网盘的服务商看得到内容。

## 排定先后

网盘里的文件夹存着一串编号连续的提交，每个提交是一批改动。各设备按编号的顺序把它们写进本机的数据库，所以共享的数据完全一样：网盘替代了[同步](../design.md#同步)里服务端排定先后的那部分。

- **同步任务**：本机服务端里改共享数据的请求都排进同一个同步任务，一次一个：页面的改动、HTTP 和工具接口、AI 整理的每一步（开始、失败、建议、结果）、AI 整理的说明、附件的清理。同步任务之外没有别的写入共享数据，所以执行时的数据就是写入网盘时的数据。本机的数据（见[共享的和本机的](#共享的和本机的)）照常直接写。
- **写入**：轮到一个请求时，在最新的数据上照常执行（校验、编号、工具按当前的路径和编号生成操作，都用现有的代码），在事务里得出提交的内容后回滚，再把它写成下一个编号，[只在不存在时写入](#只在不存在时写入)。写成了，再按[读入](#读入)的规则写进本机，这才回确认。
- **编号被占了**：先读入别的设备的提交。其中有这个请求的改动 ID 的，说明它已经写成（上次结果不明时，被原样重写的），不再执行；否则在新的数据上整个重新执行（工具也重新生成操作），再写下一个编号。重新执行时不成立的，照常拒绝。
- **结果不明**：写的请求发出了、没收到回应（超时、断线）时，不重新执行，先读这个编号：是自己的提交（按提交的 ID）就是写成了；是别人的就是没写成，按上一条处理；不存在，就把同一个提交原样再写一次，迟到的那次写入和它一模一样，谁先到都对。读请求本身失败的，等能读到再定。所以一个提交不会写成两次，也不会卡在这个编号上。
- **读入**：别的设备不重新执行操作，照着提交写库。提交是写入的设备在同样的数据上得出的，所以几台设备的 App 版本不同、规则改过也不会分叉。

谁在等结果：

- **页面**：`mutate` 交给同步任务后，连接照常处理别的消息和推送；写成了回 `ack`，不成立回 `reject`。连不上网盘时什么也不回，页面的待发队列照旧留着它，重连后重发，按改动 ID 去重，和连服务器时一样。所以这期间改的只在页面里，小组件和提醒要等写进网盘后才看到。
- **HTTP 和工具接口**（桌面上的 agent、小组件）：最多等 15 秒，到时就回答，不等手头的网盘请求。还没发出的，从同步任务里拿掉，返回 503 `unavailable`“暂时无法连接网盘，改动未生效”；已经发出、结果不明的，返回 503 `outcome_unknown`，带上改动 ID：这个提交照上面的规则原样重写，写成了就生效；编号被别人占了的，这项不再重做。用同一个改动 ID 重发的，排在它后面，等它有了结果再按 ID 去重，所以只生效一次，见[重试](../agent.md#重试)。小组件和提醒里的“完成”照[原生发出的改动](../android.md#原生发出的改动)存下，用同一个改动 ID 补发，同步开着时补发要求联网。
- **AI 整理的开始**（`POST /ai/jobs/{id}/run`）：最多等 15 秒，没写成就返回 503，页面过一会儿再试，和离线时一样。开始仍留在同步任务里，配置只在内存里跟着它，什么时候写成就什么时候开始整理；这期间再试得到 409“正在整理另一条请求”。整理出的结果写不进网盘时一直重试，不丢。

## 只在不存在时写入

两台设备同时写同一个编号时，必须只有一台写成，否则一台的改动会被覆盖掉，几台的数据从此不一样。

- **S3**：PUT 带 `If-None-Match: *`，已经存在时返回 412；同一个文件正有另一次写入时返回 409，这时文件可能还没有，按结果不明处理，读一下再定。列目录（ListObjectsV2）一页最多 1000 项，按续页标记读完。
- **WebDAV**：先 PUT 到 `tmp/<随机>`，再 `MOVE` 到目标，带 `Overwrite: F`，已经存在时返回 412（坚果云返回 409）。没写成的删掉自己的临时文件。别的文件（附件、快照、`nexttodo.json`）在 WebDAV 上也这样写，读到的总是完整的文件。
- WebDAV 不用 `If-None-Match: *` 和 `If-Match`：坚果云不理会前者，照样覆盖；后者单独用时管用，几台同时写时不止一台写成。见[已验证的](#验证)。

## 网盘里的文件

```
<文件夹>/
  nexttodo.json                {"format": 1, "id": "<这一代的代号>"}
  <代号>/log/<编号>.json        一次提交，编号从 1 起连续
  <代号>/snapshots/<编号>.db.gz 快照：读入到这个编号时的数据库，gzip 压缩
  <代号>/files/<附件 ID>        附件的文件
  tmp/<随机>                   WebDAV 写入时的临时文件
```

- **一代**：每次在空文件夹上开启都是新的一代，代号随机，`nexttodo.json` 指着当前这一代。各设备只读写开启时记下的那一代的目录：文件夹被删掉重建后，旧设备迟到的写入落在旧一代的目录里，混不进新的历史。
- **提交**：`{"id": "<提交的 ID>", "format": 2, "items": [...]}`，一个提交最多 50 项，写入时把同步任务里排着的一起执行、一起写。每项是一种：
  - 改动 `{"mutation": {id, at, via, ops, effects}}`：`at` 是写入设备上的毫秒时间，`via` 是 API 令牌名。工具接口的回复（重发同一个幂等键时原样返回）里有本机的批次号，不传上网盘，只记在执行它的设备上。
  - AI 整理的说明 `{"note": {folder_id, text, at}}`。
  - 清理附件 `{"purge": [{id, type, size, created_at, unused_at}, …]}`：清理掉的文件的记录，见[附件](#附件)。
- **快照**：写成编号是 200 的倍数的提交的设备，读入后接着上传这个编号的快照，只在不存在时写入。快照是数据库的副本（和每日快照一样用 `VACUUM INTO`），清掉其中本机的部分，表结构不变：本机的表清空，改动日志的令牌和工具接口的回复、用户的密码哈希和数据代号清空，服务器的设置恢复默认，只上传了、还没加为附件的文件记录删掉。哪些是本机的，按 `drive/snapshot.rs` 里给每张表的归类：实体的表整张共享（它们的每一列本来就随提交传给别的设备），其余的表要么整张是本机的，要么逐列写明；新加的表、这些表新加的列没归类，测试就不通过。[落后很多](#运行)的设备换上快照时，按同一份归类替换共享的表，顺序也取自这里：每张表排在它引用的表后面，排错了测试也不通过。快照里的序号只在这份快照内部有意义。
- **清理**：上传了快照的设备接着在后台清理，不占同步任务。网盘里留最新的两份快照；更早的，从最早的起，等它编号的那个提交早于 90 天（和改动日志的保留期一致），先删它前面的提交，再删它。提交从它往前 200 个一组地删，删到已经删过的那组为止：每组最后一个提交最后删，所以它还在就说明这组还没删完（删到一半被打断，或者那组的快照没传上去），一起删掉。还删掉一天以前的临时文件；`nexttodo.json` 还指着自己这一代时，也删掉一天以前、没被它指着的代号目录（开启到一半被打断、两台同时开启时输了的留下的）。文件夹里只有 NextTodo 自己的东西（见[开启](#开启)），所以按名字认得出。提交的 ID、临时文件和代号都是 UUIDv7，时间从中读出。对象存储没有真正的文件夹，删目录时逐个删其中的文件。

## 共享的和本机的

| 数据 | | 说明 |
|---|---|---|
| 文件夹、事项、依赖、附件、AI 整理请求、AI 整理的说明 | 共享 | |
| `files` 的记录，包括已清理的 | 共享 | 只上传了、还没在提交里加为附件的除外，它们是本机的暂存；文件本身在本机按需下载 |
| AI 整理请求的 `run`（新加的列） | 共享 | 正在整理的这一轮：开始那次改动的 ID |
| 改动日志 `mutations` | 共享 | 除了序号、令牌和工具接口的回复：序号由各设备自己编；别的设备写的，令牌记为空字符串，来源照旧显示令牌名；回复只在执行的设备上 |
| `users` 的 `next_task_number` | 共享 | 本机模式只有一个用户；其余的列由[规范本机用户](../local.md#本机用户)决定 |
| `users` 的 `pruned_seq`、`deliveries` | 本机 | 由本机的序号算出 |
| 令牌和会话、邀请码、`users` 的密码哈希、服务器的设置（上传前压缩图片）、数据代号、同步的记录 | 本机 | |
| AI 整理的模型配置 | 本机 | 本来就只在页面里 |

- 同步的记录是两张本机的表：这一代的代号和读到的编号，和读入的数据在同一个事务里写；这台设备开始的整理（开始那次改动的 ID），在写开始整理的提交之前记下。
- 网盘的配置（方式、地址、账号、密码或密钥、文件夹）存在 `local/sync.json`，只有本用户能读写。它不在 `db/` 里，所以备份、快照和恢复都不带它，也不会传上网盘。

## 读入

每个提交在一个事务里写完，同时记下读到的编号。照着每一项：

- 实体的变化：新建的插入，修改的按 `after` 更新，删除的删掉。
- 事项的编号：`next_task_number` 推进到不小于出现过的最大编号加一。
- 附件：新建时把这个文件的记录写成提交里的值（类型、大小来自附件，时间是提交的 `at`；上传的设备已有的记录也改成这样），标为在用；删除时标为不用，从提交的 `at` 起算。所以各设备的 `files` 一样，不看上传和读入的时间。
- 改动日志：每个改动记一行，ID、操作、变化、来源和时间都照提交，自己执行的工具接口再记上回复；`deliveries` 给本机用户记一行。然后推送给页面。写进网盘后、写进本机前被打断的，回复就没了，同一个幂等键重发时只回批次号，和超过保留期的一样。
- 说明写进 `ai_notes`；清理附件把这些文件的记录照提交写成已清理的（记录留着；没有记录的，比如别的设备只上传过的，照样补上），删掉本机的文件。
- AI 整理请求变成整理中时，`run` 记为这次改动的 ID；离开整理中时清空。

测试比较各设备全部共享的表，不只是实体。

## 附件

- 提交里新建的附件（页面上传的、工具接口加的），写提交之前先把本机的文件[只在不存在时](#只在不存在时写入)传到 `<代号>/files/<附件 ID>`。已经有了的读回来比较：一样的是上次没收到回应时传上去的；不一样的是别的设备用同一个 ID 传的，加这个附件的改动返回 409“网盘里已经有另一个文件用了这个附件 ID”，同一批的其他改动重新执行。工具接口试执行时已经把文件存进本机的 `files/`，回滚不影响它；重新执行时生成新的附件 ID，用不上的文件照本机的规则一天后删。
- **按需下载**：本机没有的文件，服务端读的时候先从网盘下载，存进本机的 `files/`。大小和记录的不一样（没传完、被换掉）的不存，这次读取出错，下次再下载。页面显示、AI 整理读图、工具接口和备份都经过这一处，所以别的设备加的图片，这台设备没显示过也能拿去整理。界面和连服务器时一样（见[附件](../ui/attachments.md)）。
- **清理**：每天清理文件时，90 天没人用的文件不直接删，而是作为一项清理附件排进同步任务。它和别的提交一样在最新的数据上执行，这期间被撤销删除、又用上的不在其中。写成后，各设备读入时把记录标为已清理、删掉本机的文件，写成的设备再从网盘删掉这些文件，已经不在的不算错。已清理的记录一直留着，本机的清理和快照都不删它。清理附件之后，撤销删除这些附件时照常提示文件不存在，各设备一样。
- 清理过的 ID 留着已清理的记录，不能再上传或加为附件（返回 409“附件 ID 已被用过”）：否则这个 ID 重新上传、加回来以后，写成清理的设备迟到的删除会删掉网盘上又在用的文件。
- 本机的暂存：`files/` 里没有记录的文件（写到一半的）照本机的规则一天后删。只上传了、90 天没加为附件的，也作为清理附件写进网盘，和上面一样在最新的数据上判断：提交被拒绝前它可能已经传上网盘，别的提交也可能用着同一个 ID，所以不在被拒绝时直接删，只有写成了清理、标为已清理之后才删网盘上的文件。

## 开启

- 设置的本机模式卡片里点“借网盘同步”，开头一句说明，后面是“如何设置”，链到官网教程的[借网盘同步](https://juniexd.github.io/NextTodo/guide/local#drive)（坚果云的应用密码怎么取也在那里）。选 WebDAV 或 S3：
  - WebDAV：地址（坚果云是 `https://dav.jianguoyun.com/dav/`）、用户名、密码（坚果云要用应用密码）。
  - S3：接口地址、区域、存储桶、Access Key ID、Secret Access Key、地址风格（默认虚拟主机 `<存储桶>.<接口地址>`，MinIO 这类自建的选路径）。
  - 文件夹：默认 `NextTodo`，不存在就建。
- 先检查网盘：在 `tmp/` 里写一个文件，再按[只在不存在时写入](#只在不存在时写入)的做法往它上面写一次，必须被拒绝，然后删掉它。不满足的（服务不支持，或者 S3 存储桶开了版本控制），提示“这个网盘不能用来同步：同时写入时会互相覆盖”，不开启。连不上、账号不对，如实提示。
- **没有 `nexttodo.json`**：文件夹里只能有 `tmp/` 和开启到一半留下的代号目录（名字是 UUIDv7），有别的就提示“这个文件夹里有其他文件，请换一个空文件夹或新的文件夹名”，不开启：网盘里的清理按名字删，不能删到别人的文件。可以开启时开启新的一代，把这台设备的数据传上去。开启由同步任务来做：从这一刻起，共享数据的写入都排在它后面等着。它先把这台设备正在整理的 AI 整理请求记为失败（“开启同步，整理中断”：这一轮不在网盘记着的轮次里，它迟到的结果不再写入，之后停止同步也一样），再截下快照 0，生成代号，把快照 0 里用到的附件文件和快照 0 传进 `<代号>/`，先在本机记下这一代（同步的记录），最后只在不存在时写 `nexttodo.json`，写成了才算开启，排着的写入从此写进网盘；写完之前进程就退出了的，重启后照记下的这一代同步，`nexttodo.json` 没指着它（没写成）就按[换了一代](#运行)停止同步、提示重新开启；开启失败的，照旧直接写本机。上传时不占着数据库，页面和小组件照常读。写不成或者没收到回应时，先读回 `nexttodo.json`：代号是自己的，就是写成了；是别的，说明别的设备刚开启了，删掉自己传的这一代，按下一条处理，再问一次；读不到就什么也不删，稍后再试。中途被打断的，留下的目录没有被指着，不算数，再开启时重新来。
- **已经有 `nexttodo.json`**：确认“会用网盘里的数据替换这台设备上的全部数据”。然后像[恢复](backup.md#恢复)的准备那样，在 `restore.part/` 里做一份新的数据库：下载最新的快照，读入之后的提交，规范本机用户，换一个新的[数据代号](../local.md#数据代号)（不沿用快照里的），记下同步的记录；本机的令牌和会话不带过去，数据换成了另一个本机用户的，桌面上 agent 的 API 令牌要重新生成。再按恢复的提交和完成换上，App 重启，现在的数据留在 `before-restore-*`。所以两台各自有数据的设备不合并：先在一台上开启，别的加入时用网盘里的。
- `format` 比 App 知道的新：提示“请先更新 App”，不开启。

## 运行

- 本机服务端运行时每 30 秒查一次下一个编号；写入后、App 回到前台时马上查（Android 的界面 `onResume`、iOS 回到前台、桌面的窗口获得焦点时，原生部分告诉服务端）。所以别的设备的改动几十秒内到，不是实时。
- **连不上网盘**（离线、网盘出错、限流）：同步任务按退避重试，429 和 503 也一样。谁在等结果、等多久，见[做法](#排定先后)。
- **落后很多**：同步任务启动时和一天没连上网盘之后，先列一次快照。要读的提交在 200 个以上（最新的快照比读到的编号大 200 以上）时，改为读最新的快照和之后的提交；提交被删掉的（离线超过 90 天）总在最新的快照 400 个以前，也是这样。先判断这一条再读写，所以不会往删掉的编号上写。换上时在一个事务里用它们替换本机全部共享的数据，本机的表不动，数据代号不变。改动日志里本机已有的改动保留原来的序号（工具接口回复里的批次号仍然对得上），新的接着本机的序号往后编，`deliveries` 随之重建，`pruned_seq` 推到最新，于是页面收到 `resync`，重新下载、保留待发队列并重发，和连服务器时服务端恢复了快照一样，不用重启 App。重发的改动在新数据上重新执行，不成立的照常拒绝、提示；小组件和提醒里没发出的“完成”也照常补发。
- **更新版本写的**：读到[格式](../local.md#格式版本)比 App 新的 `nexttodo.json`、提交或快照时停下，提示“请先更新 App”，更新后接着读。
- **换了一代**：同步任务启动时和每次写入前（包括结果不明、原样重写之前）读 `nexttodo.json`，代号和这台设备记着的不同（文件夹被删掉、由别的设备重新开启）时停止同步，提示重新开启，排着的改动照[停止同步](#停止)时处理。对象存储往删掉的文件夹里照样写得进，所以每次写入前都确认，改动不会写进没人读的旧一代；只读不写的设备在启动时发现。
- **iOS**：在后台被挂起时不同步。
- **Android**：进程在后台被冻结时不同步。小组件的定时刷新先让服务端查一次（经 JNI，最多等 5 秒），再取列表；同步开着时定时刷新要求联网。
- **AI 整理**：开始整理也要先写进网盘，所以两台设备不会同时整理同一条，写成的那台来整理。写之前先在本机记下这一轮（开始那次改动的 ID）。整理的结果和失败只在请求的 `run` 还是这一轮时才写，所以请求被删掉又撤销、在别的设备上重新开始以后，旧一轮迟到的结果不会算进新一轮。启动时，本机记着的、`run` 还是那一轮的记为失败，写成了开始、还没写进本机就退出，之后又跳过这个提交读了快照的，也认得出来。这些失败不等网盘，排在同步任务的最前面，服务端照常启动，离线时也能用；这台设备之后再开始的整理都排在它后面。别的设备在整理的不动；那台设备不再用了，整理中的请求可以照常删除。停止同步时，先把这台设备正在整理的记为失败，写不进网盘的留在别的设备上，可以删除。
- 改动日志的清理照旧由各设备按自己的时钟做，只影响这台设备上撤销能回溯多远：撤销只在发起的设备上执行，别的设备照着结果写，不会因此分叉。

## 停止

- 设置里“停止同步”：不再读写网盘，本机数据保留，网盘里的不动。再开启时按“已经有 `nexttodo.json`”处理。
- 停止前先下载还用得上的附件里本机还没有的文件（包括删除后还能撤销的，见[清理](#附件)），停止后就不能再从网盘下载了；同步任务停下后再下载一次停止过程中读入的，这次下载不了的，同步接着开着，停止时没能写进网盘的整理失败重新排上。网盘里本来就没有的文件不算。下载不了（离线、网盘的账号失效）时提示“部分附件的文件尚未从网盘下载，现在停止同步将无法打开这些附件”，确认后照样停止；这些附件之后在这台设备上打不开，在空文件夹上重新开启时，新的一代里也没有它们的文件。
- 停止时等同步任务停下、忘掉网盘之后，才照常直接写本机，所以停止以后同步任务不会再写本机。手头的网盘请求不等，它若写成了提交，别的设备照常读入。排着的改动返回服务器错误，页面重发后直接写本机。
- 同步开着时不能恢复备份，“恢复”提示先停止同步：恢复的数据和网盘里的不是同一份历史。同步时做的备份里的同步记录，恢复时清掉。要让所有设备用一份备份，先停止同步、恢复，再在一个空文件夹上开启，其他设备改为同步这个文件夹。
- 备份时，本机还没有的附件文件先从网盘下载，见[备份](backup.md#备份)。
- 离开本机模式时同步跟着停，回来后接着同步。

## 用量

- 平时每台设备 30 秒一个请求；写一个提交，先读下一个编号和 `nexttodo.json`，再写，S3 上共 3 个请求，WebDAV 上 4 个。坚果云复用连接时一个请求约 0.4～0.9 秒，新建连接约 2 秒，所以改动写进网盘要一两秒，页面上照常立即生效。
- 坚果云的 WebDAV 免费版每 30 分钟限 600 次请求，付费版 1500 次（见坚果云帮助中心《坚果云第三方应用授权 WebDAV 开启方法》）；免费版据第三方说法每月上传 1 GB、下载 3 GB。实测 20 分钟约 570 个请求没有被限流，平时远用不到；附件最占流量。
- 网盘里的提交用编号直接读写，不列目录：坚果云列目录时据说只返回前 750 个文件。

## 验证

还没验证的：

- 阿里云 OSS、腾讯 COS：文档里只有各自的禁止覆盖请求头，没说支不支持 `If-None-Match: *`，开启时的检查会认出不支持的，有账号时再测。Cloudflare R2 据第三方说法支持。
- 坚果云限流时返回什么、要等多久。
- Android 后台定时刷新时先同步一次的耗时。

已验证的（2026-11-17，用 curl）：

- 坚果云的 WebDAV（`dav: 2`）：
  - PUT 带 `If-None-Match: *` 时不理会，已有的文件照样被覆盖（204）；`MKCOL` 已有的文件夹也返回 201。
  - `If-Match`：版本号不对时返回 412，版本号只认不带引号的（`GET` 的响应头和 `PROPFIND` 的 `getetag` 里有，`HEAD` 没有），由内容决定。但 8 个请求带着同一个版本号同时写，8 轮里有 3 轮不止一台写成（最多 3 台），不能用来排先后。
  - `MOVE` 带 `Overwrite: F`：目标已存在时返回 409，不存在时 201。8 个请求同时移到同一个名字，23 轮都正好一个写成。
  - 上传中途断开，不留下半个文件。
  - 能删文件和子文件夹（连同里面的），顶层文件夹（坚果云的同步文件夹）删不掉（403）。
  - 复用连接时一个请求约 0.4～0.9 秒，新建连接约 2 秒（经本机的代理）。20 分钟约 570 个请求，没有被限流。
- MinIO（Homebrew 里 2025-10-15 的版本；官方已不再提供下载）：PUT 带 `If-None-Match: *`，已存在时 412；8 个请求同时写同一个名字，30 轮都正好一个写成。

## 测试

- Rust，用内存里的假网盘（同样只在不存在时写入，能模拟断线、写成了却没有回应）起三个本机服务端：
  - 同时写入只有一个写成，其余读入后重新执行，不成立的被拒绝；工具接口重新执行时按新的数据生成操作。
  - 最后几台全部共享的表完全一样（不只是实体：编号、`files`、改动日志）。
  - 写成了却没有回应、写进网盘后写进本机前被打断：再读到时认出是自己的，不重复生效；没写成、这个编号一直不存在的，原样重写后之后的请求照常前进；HTTP 的请求还没发出时返回“没有生效”且之后不写，发出了时返回“可能已经生效”。
  - 页面的改动在连不上时一直等，不被拒绝；读到更新版本的提交时停下。
  - 落后很多时读快照：共享的数据换掉，本机的表和数据代号不变，页面收到 `resync`，重发的改动照常生效；之前工具接口回复的批次号仍能撤销对的那一批。
  - 加入时换了数据代号；开启到一半被打断、两台同时开启、`nexttodo.json` 写成了却没有回应、换了一代后旧设备迟到的写入。
  - 清理附件：离线的设备不会删掉别处撤销后又在用的文件；清理过的 ID 不能再上传和加回来；两个改动同时把同一个上传加为附件，只有一个写成，文件仍能下载。从没显示过的附件，AI 整理和备份照样读到。
  - AI 整理：只有一台开始整理；删掉又撤销、在别的设备上重新开始后，旧一轮的结果不写进去；写成了开始、没写进本机就退出、又跳过它读了快照的，重启后记为失败。
- 实际操作：手机和电脑经坚果云、MinIO 同步，新设备加入、离线改动后联网、两边同时改、附件、AI 整理、停止后再开启。
